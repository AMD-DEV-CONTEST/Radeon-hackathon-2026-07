# 智能发票理赔 Agent 系统 — 设计文档

> 版本：v1.0
> 场景：商业健康险 / 医疗费用报销的智能发票理赔审核
> 参赛赛道：AMD 黑客松 · 赛道二（私有 AI Agent 开发与本地部署）

---

## 文档导读

本设计文档描述如何在现有「发票真伪查验系统」基础上，扩展为一个**完全本地化部署、基于 LangChain 的智能理赔 Agent 系统**。系统以 AMD Radeon GPU + ROCm 作为大模型推理后端，通过多模态提取、真伪查验、RAG 药品目录比对与理赔规则决策，实现「上传发票 → 自动得出理赔结论」的全流程自动化，并支持多轮追问交互。

各章节与黑客松评分标准的对应关系见 [第 13 章 评分对齐表](#十三黑客松评分对齐表)。

---

## 关键设计决策速览

| 维度 | 决策 | 理由 |
|------|------|------|
| Agent 框架 | LangChain（tool-calling / ReAct Agent） | 生态成熟，工具调用/RAG/记忆全覆盖，与 OpenAI 兼容端点无缝对接 |
| 推理后端 | vLLM 暴露 OpenAI 兼容端点 | 上层 Agent 与硬件解耦，CUDA→ROCm 迁移零改动 |
| 硬件平台 | AMD Radeon GPU + ROCm | 满足赛道二要求；核心推理本地执行 |
| 多模态模型 | 沿用现有 VLM，扩展药品明细提取 | 复用已验证的 OCR 能力 |
| Embedding | 本地 bge 系列（sentence-transformers，PyTorch ROCm） | 不依赖远程 API，隐私可控 |
| 向量库 | Chroma（本地持久化） | 轻量、零运维、支持本地磁盘持久化 |
| 药品目录 | 国家医保药品目录典型字段样例库 | 无需真实敏感数据即可演示完整链路 |
| 前端 | Gradio 升级为对话式（保留图片上传） | 复用现有 UI，增加多轮交互体验 |
| 能力覆盖 | RAG + 工具调用 + 多步规划 + 多轮记忆 + 权限隐私 | 覆盖「5 选 2+」全部 5 项以争取加分 |

## 一、项目概述与场景定位

### 1.1 应用场景

**商业健康险 / 企业医疗报销的「智能发票理赔审核助手」。**

保险公司理赔员或企业 HR 在处理医疗报销时，需要对每一张医疗/药品发票执行以下人工操作：

1. 核验发票**真伪**（是否伪造、是否重复报销）；
2. 识别发票上的**药品明细**（药品名、规格、金额）；
3. 判断每项药品是否在**报销目录**（医保甲类/乙类，或商保约定目录）内；
4. 按目录的**报销比例、自付比例、封顶线**计算**可报销金额**；
5. 给出**理赔结论**（全额通过 / 部分通过 / 拒赔）及理由。

### 1.2 痛点

- 人工逐张审核**效率低**，高峰期积压严重；
- 药品目录庞大（数万条），人工比对**易漏易错**；
- 真伪查验、目录查询、金额计算**分散在多个系统**，需反复切换；
- 结论缺乏**可追溯的理由说明**，客户申诉时难以复核。

### 1.3 系统目标

用户只需**上传一张发票图片并提问**，Agent 自动完成「提取 → 查验 → 目录比对 → 理赔决策」全流程，输出：

- 结构化的理赔结论（可报金额、通过状态、逐项药品明细）；
- 人类可读的理由说明；
- 支持**多轮追问**（如「为什么这一项被拒赔？」「如果按乙类算能报多少？」）。

### 1.4 创意亮点

- **多模态 + RAG + 规则引擎**三位一体：视觉提取、语义检索、确定性计算各司其职；
- **全本地化**：发票图片、药品信息、理赔数据均不出内网，符合金融/医疗数据合规要求；
- **Agent 自主编排**：模型自主决定调用哪个工具、何时短路（如真伪不通过则不再计算金额），而非硬编码流水线。

## 二、系统总体架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  交互层  Gradio ChatInterface（图片上传 + 多轮对话 + 流式）      │
└───────────────────────────┬─────────────────────────────────┘
                            │ 用户消息 / 图片 / 会话历史
┌───────────────────────────▼─────────────────────────────────┐
│  Agent 编排层  LangChain AgentExecutor                        │
│   - 系统提示 / 角色设定                                        │
│   - 任务规划（多步 ReAct / tool-calling）                      │
│   - 记忆管理（会话级多轮记忆）                                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 工具调用 (function calling)
┌───────────────────────────▼─────────────────────────────────┐
│  工具层  Tools                                                │
│   ┌──────────────┐ ┌──────────────┐ ┌───────────────┐        │
│   │invoice_ocr   │ │invoice_verify│ │drug_catalog   │        │
│   │_tool         │ │_tool         │ │_rag_tool      │        │
│   └──────┬───────┘ └──────┬───────┘ └──────┬────────┘        │
│          │                │                │  ┌─────────────┐ │
│          │                │                │  │claim_       │ │
│          │                │                │  │decision_tool│ │
│          │                │                │  └─────────────┘ │
└──────────┼────────────────┼────────────────┼─────────────────┘
           │ VLM 推理        │ HTTP           │ 向量检索
┌──────────▼────────────┐   │       ┌────────▼─────────────────┐
│ 推理后端  vLLM         │   │       │ 数据层                    │
│ (AMD Radeon + ROCm)   │   │       │  - Chroma 向量库          │
│  OpenAI 兼容端点       │   │       │  - 医保药品目录(样例)      │
│  - 多模态模型          │   │       │  - 本地 Embedding 模型     │
│  - (可选)Embedding端点 │   │       └───────────────────────────┘
└───────────────────────┘   │
                            ▼
              官方发票查验接口（外部辅助工具，非核心推理）
```

### 2.2 端到端数据流

1. 用户在 Gradio 界面上传发票图片并发送消息（如「帮我审核这张发票能报多少」）。
2. Agent 编排层接收消息 + 图片路径 + 会话历史，LLM 进行**任务规划**。
3. Agent 调用 `invoice_ocr_tool`：多模态模型提取发票字段（代码、号码、日期、价税合计、**药品明细列表**）。
4. Agent 调用 `invoice_verify_tool`：调官方接口核验真伪；**若不通过则短路**，直接返回拒赔理由。
5. 对每一项药品，Agent 调用 `drug_catalog_rag_tool`：在药品目录向量库中检索匹配条目（甲/乙类、报销比例等）。
6. Agent 调用 `claim_decision_tool`：结合真伪结果 + 目录匹配结果，按规则计算**可报销金额与结论**。
7. Agent 汇总结构化结果 + 自然语言解释，流式返回给用户；结果写入**会话记忆**。
8. 用户可继续追问，Agent 基于记忆中的上一张发票上下文回答，必要时重新调用工具重算。

### 2.3 关键设计原则

- **硬件解耦**：Agent 层只认「OpenAI 兼容端点」，不感知底层是 CUDA 还是 ROCm。
- **确定性与智能分离**：金额计算等确定性逻辑放入工具（Python 代码），LLM 只负责编排与解释，避免大模型算错数字。
- **短路优化**：真伪不通过、提取失败等异常场景尽早终止，减少无谓推理与检索开销。

## 三、AMD Radeon + ROCm 推理后端

> 本章对齐评分「核心推理运行在 AMD Radeon GPU（20 分）」与「推理速度定向优化（20 分）」。

### 3.1 定位

AMD Radeon GPU + ROCm **仅承担大模型推理**（多模态 VLM，及可选的 Embedding），通过 vLLM 暴露标准 OpenAI 兼容 HTTP 端点。Agent 编排、工具、RAG 检索等均在 CPU/内存中运行，不依赖特定 GPU 厂商。

### 3.2 vLLM on ROCm 部署方案

**推理服务契约（不变量）：**

| 项目 | 值 |
|------|-----|
| 端点 | `http://<backend-host>:8000/v1/chat/completions` |
| 协议 | OpenAI Chat Completions（含多模态 `image_url`） |
| 模型标识 | `model` 字段（如 `/model`） |
| 流式 | 支持 `stream: true`（SSE） |

**ROCm 环境部署步骤（设计建议）：**

1. 使用官方 ROCm 版 vLLM 镜像（`rocm/vllm` 系列）或基于 `rocm/pytorch` 自建。
2. 启动示例（参数在 3.5 节详述）：

```bash
# AMD ROCm 后端启动 vLLM（示例）
docker run -it --rm \
  --device=/dev/kfd --device=/dev/dri \
  --group-add video --ipc=host \
  -p 8000:8000 \
  -v /path/to/model:/model \
  rocm/vllm:latest \
  python -m vllm.entrypoints.openai.api_server \
    --model /model \
    --served-model-name /model \
    --dtype float16 \
    --gpu-memory-utilization 0.90 \
    --max-model-len 8192 \
    --max-num-seqs 16
```

3. Agent 侧仅需将 `MODEL_URL` 指向该端点，**无需任何代码改动**。

### 3.3 本地 Embedding 部署

RAG 所需的文本向量化在本地完成，两种可选方案：

- **方案 A（推荐，简单）**：在 Agent 进程内用 `sentence-transformers` 加载 `bge-small-zh-v1.5` / `bge-m3`，底层 PyTorch 走 ROCm（`torch` 的 ROCm 构建）或 CPU。
- **方案 B（统一后端）**：用 vLLM/其他推理服务暴露 embedding 端点，Agent 通过 HTTP 调用，与 LLM 后端一致管理。

无论哪种方案，**均本地执行、不调用远程 API**，满足隐私要求。

### 3.4 CUDA → ROCm 迁移论证

> 这是本作品「可迁移性」的核心论点。

vLLM 在 CUDA 与 ROCm 上对外暴露**完全一致的 OpenAI 兼容接口**。因此：

| 层级 | CUDA 环境 | ROCm 环境 | 是否改动 |
|------|-----------|-----------|:--------:|
| Agent 编排层 | 调 `:8000/v1` | 调 `:8000/v1` | 否 |
| 工具层 | 同上 | 同上 | 否 |
| 推理后端启动参数 | `--dtype float16` 等 | 同名参数 | 后端侧微调 |
| 硬件驱动 | CUDA + NVIDIA 驱动 | ROCm + AMDGPU 驱动 | 仅底层 |

**结论**：当前用 NVIDIA+CUDA 驱动模型完成开发，迁移到 AMD Radeon+ROCm 时，只需在后端机器上换用 ROCm 版 vLLM 镜像并重新拉起服务，**Agent 层零改动**。这既降低了开发期成本，又满足赛道二「核心推理运行在 AMD Radeon GPU」的最终部署要求。

### 3.5 推理性能优化（定向优化）

| 优化方向 | 手段 | 预期收益 |
|----------|------|----------|
| 显存利用 | `--gpu-memory-utilization 0.9`，合理 `--max-model-len` | 提升并发 batch，吞吐↑ |
| 模型量化 | AWQ / GPTQ 权重量化 | 显存占用↓、吞吐↑，精度基本无损 |
| 连续批处理 | vLLM continuous batching + `--max-num-seqs` | 多请求并发，GPU 利用率↑ |
| KV Cache | vLLM PagedAttention（默认开启） | 长上下文显存碎片↓ |
| 图片预处理 | Agent 侧压缩/降分辨率后再编码 base64 | 传输与视觉编码耗时↓ |
| 流式输出 | `stream: true` | 首 token 更快，交互体感↑ |
| Embedding 缓存 | 目录向量**离线构建一次**并持久化到 Chroma；查询侧对相同 query 结果做 LRU 缓存 | 检索延迟↓ |
| 短路编排 | 真伪不通过即终止后续推理/检索 | 平均端到端耗时↓ |
| Prompt 精简 | OCR 提示词精简、`max_tokens` 收紧、`temperature=0.1` | 生成 token 数↓ |

**可量化验收指标（供 Demo 展示）：**

- 首 token 延迟（TTFT）；
- 端到端单张发票处理时延；
- 并发吞吐（req/s 或 tokens/s）；
- GPU 显存占用与利用率。

建议在文档附录/Demo 中给出 CUDA 开发环境与 ROCm 目标环境的实测对比表（同一模型、同一 prompt）。

## 四、Agent 编排设计（LangChain）

> 本章对齐评分「任务分解、工具调用、RAG 和记忆管理（20 分）」。

### 4.1 Agent 类型选择

采用 **tool-calling Agent**（`create_tool_calling_agent` + `AgentExecutor`）为主，ReAct 为备选：

- vLLM 端点若支持 OpenAI function-calling，则优先用 tool-calling（更稳定、结构化）；
- 若模型不支持工具调用协议，则退化为 **ReAct**（`create_react_agent`，靠提示词让模型输出 Thought/Action/Observation），保证兼容性。

LLM 通过 `langchain_openai.ChatOpenAI` 接入本地 vLLM 端点：

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="/model",
    base_url="http://192.168.31.250:8000/v1",
    api_key="EMPTY",            # 本地 vLLM 无需真实 key
    temperature=0.1,
    streaming=True,
)
```

### 4.2 系统提示与角色设定

```
你是"智能理赔审核助手"。你的职责是审核用户上传的医疗/药品发票并给出理赔结论。
请严格遵循以下工作流程：
1. 调用 invoice_ocr_tool 提取发票字段与药品明细；
2. 调用 invoice_verify_tool 核验发票真伪；若查验不通过，直接判定拒赔并说明理由，不再继续；
3. 对每一项药品调用 drug_catalog_rag_tool 检索报销目录；
4. 调用 claim_decision_tool 计算可报销金额与结论；
5. 用中文清晰汇总：逐项药品、可报金额、结论、理由。
不要自行编造药品目录信息或凭空计算金额，一切以工具返回为准。
```

### 4.3 多步任务规划

Agent 按「提取 → 查验 → 检索 → 决策」推进，并支持**条件分支/短路**：

```
用户请求
  │
  ▼ invoice_ocr_tool
提取成功? ──否──► 回复"图片不清晰，请重传" (终止)
  │是
  ▼ invoice_verify_tool
真伪通过? ──否──► 结论=拒赔(发票存疑) (终止)
  │是
  ▼ 对每项药品 drug_catalog_rag_tool（可并行/循环）
  ▼ claim_decision_tool
汇总结论 ──► 返回用户 + 写入记忆
```

规划由 LLM 自主驱动（而非硬编码 if-else），但通过系统提示强约束顺序，兼顾自主性与可靠性。

### 4.4 记忆管理（多轮）

- 使用 `RunnableWithMessageHistory` + `ChatMessageHistory`，以 `session_id` 隔离会话。
- 记忆内容包含：历史对话、上一张发票的 OCR 结果与理赔结论（作为结构化上下文注入）。
- 长对话采用 `ConversationSummaryBufferMemory` 思路：超出 token 阈值时对早期轮次做摘要，保留关键结论。
- 典型多轮场景：用户上传发票得到结论后，追问「为什么 X 药品被拒？」——Agent 直接引用记忆中的决策明细回答，**无需重复调用工具**；若用户要求「按乙类重算」，则携带新参数重新调用 `claim_decision_tool`。

## 五、工具集设计

> 本章对齐评分「工具调用」能力。每个工具用 LangChain `@tool` 或 `StructuredTool` 定义，入参用 Pydantic 模型约束。

### 5.1 `invoice_ocr_tool` — 发票多模态提取

- **职责**：调用本地多模态模型提取发票字段与药品明细。
- **入参**：`image_path: str`（发票图片本地路径）。
- **出参**（JSON）：

```json
{
  "fpdm": "发票代码（数电票留空）",
  "fphm": "发票号码",
  "date": "开票日期 yyyyMMdd",
  "code": "价税合计金额",
  "items": [
    {"name": "药品名称", "spec": "规格", "amount": "数量", "priceSum": "金额"}
  ]
}
```

- **实现要点**：复用现有 `stream_model` / `parse_model_output` 逻辑；提示词扩展为提取 `items` 药品明细数组；图片先压缩再编码。

### 5.2 `invoice_verify_tool` — 官方真伪查验

- **职责**：调用官方发票查验接口核验真伪（**外部辅助工具，非核心推理**，符合「核心推理本地」要求）。
- **入参**：`fpdm: str, fphm: str, date: str, code: str`。
- **出参**（JSON）：

```json
{
  "verified": true,
  "code": "0",
  "message": "获取成功",
  "official": {
    "fphm": "官方发票号码",
    "jshj": "官方价税合计",
    "kprq": "官方开票日期",
    "xfmc": "销售方", "gfmc": "购买方",
    "summary": [ {"name": "...", "priceSum": "..."} ]
  },
  "field_match": {"fphm": true, "jshj": true}
}
```

- **实现要点**：复用现有 `verify_invoice`；注意响应 **GBK 编码**解码；将字段比对结果结构化返回，供决策工具与解释使用。

### 5.3 `drug_catalog_rag_tool` — 药品目录语义检索

- **职责**：在药品目录向量库中检索与给定药品名最匹配的目录条目。
- **入参**：`drug_name: str, top_k: int = 3`。
- **出参**（JSON）：

```json
{
  "query": "阿莫西林胶囊",
  "matches": [
    {
      "matched_name": "阿莫西林胶囊",
      "generic_name": "阿莫西林",
      "spec": "0.25g*24粒",
      "category": "甲类",
      "commercial_innovative": false,
      "self_pay_1": 0.0,
      "self_pay_2": 0.0,
      "reimburse_ratio": 0.7,
      "cap": null,
      "score": 0.93,
      "in_catalog": true
    }
  ]
}
```

- **实现要点**：本地 embedding 向量化 query → Chroma 相似度检索 → 阈值过滤；`score` 低于阈值且非商保创新药时 `in_catalog=false`（视为目录外）。

### 5.4 `claim_decision_tool` — 理赔规则计算

- **职责**：结合真伪结果与目录匹配结果，按规则**确定性计算**可报销金额与结论。
- **入参**：

```json
{
  "verified": true,
  "items": [
    {"name": "阿莫西林胶囊", "priceSum": 120.0,
     "in_catalog": true, "category": "甲类", "commercial_innovative": false,
     "self_pay_2": 0.0, "reimburse_ratio": 0.7, "cap": null}
  ]
}
```

- **出参**（JSON）：见 [第 7 章](#七理赔决策逻辑)。
- **实现要点**：纯 Python 计算，不经过 LLM，保证金额准确、可复核。

## 六、RAG 药品目录知识库设计

> 本章对齐评分「本地知识检索（RAG）」能力。

### 6.1 报销分类规则（权威依据：国家医保局）

医保药品目录内的西药和中成药分为**甲类、乙类**；目录外药品即**不予报销**。判定口径如下（来源：国家医保局《哪些药品能报销》及《2024年药品目录》）：

| 类别 | 定义 | 能否报销 | 报销方式 |
|------|------|:--------:|----------|
| **甲类** | 临床必需、使用广泛、疗效确切、同类中价格较低 | ✅ 可报 | **全额**纳入报销基数，按规定比例报销（无先行自付） |
| **乙类** | 可供临床选择、疗效确切、价格略高 | ✅ 部分可报 | 个人**先行自付一定比例**，剩余部分再纳入基数按比例报销 |
| **目录外（众称丙类）** | 未纳入基本医保目录 | ❌ 不可报 | 基本医保**不予支付**，个人全额承担 |
| **商保创新药目录** | 创新程度高、超出基本医保范围（首版 19 种） | ❌ 基本医保不报 | 基本医保不予报销，供**商业健康险**参考支付 |

> 发票单据上的“自付一/自付二”：仅有“自付一”的为甲类；同时有“自付一、自付二”的为乙类（自付二即乙类先行自付部分）。
>
> **商业健康险场景特别提示**：本系统服务于商保理赔，判定链路为——基本医保目录内（甲/乙类）医保先报、商保补差额；目录外普通药看商保约定目录；商保创新药目录（医保不报）恰是商保核心报销对象。

### 6.1.1 样例数据结构（医保目录字段）

以国家医保药品目录字段构造样例（`data/drug_catalog.json` / CSV）：

| 字段 | 说明 | 示例 |
|------|------|------|
| `drug_name` | 药品名称（商品名） | 阿莫西林胶囊 |
| `generic_name` | 通用名 | 阿莫西林 |
| `spec` | 规格 | 0.25g*24 粒 |
| `dosage_form` | 剂型 | 胶囊剂 |
| `category` | 甲类 / 乙类 / 目录外 | 甲类 |
| `commercial_innovative` | 是否商保创新药目录 | false |
| `self_pay_1` | 自付一比例（甲/乙类均可能有） | 0.0 |
| `self_pay_2` | 自付二比例（仅乙类先行自付） | 0.1 |
| `reimburse_ratio` | 纳入基数后的统筹报销比例 | 0.7 |
| `cap` | 单项封顶线（可空） | null |
| `note` | 限定支付范围备注 | 限工伤保险 |
| `catalog_source` | 数据来源版本 | 国家医保目录 2024 |

> 说明：为演示完整链路，采用**样例数据**（基于真实分类规则构造）而非全量目录；字段结构与真实医保目录一致。落地时建议导入国家医保局发布的《国家基本医疗保险、工伤保险和生育保险药品目录（2024年）》结构化版本（共 3159 个药品，2025-01-01 执行）及首版《商业健康保险创新药品目录》（19 种）。

### 6.2 构建流程

```
drug_catalog.json ──► 清洗/规范化 ──► 文本化(拼接可检索字段)
   ──► 本地 embedding(bge) ──► Chroma 持久化(带 metadata)
```

- **文本化**：将 `drug_name + generic_name + spec + dosage_form` 拼成检索文本；其余字段（category/ratio/cap 等）作为 metadata 存储，检索命中后直接取用。
- **离线构建一次**：`rag/build_index.py` 一次性建库并持久化到磁盘，服务启动时直接加载，避免重复计算。

### 6.3 检索策略

1. **精确/模糊名称匹配**：先按 `generic_name`/`drug_name` 做规范化字符串匹配（去规格、去剂量）；命中则高置信直接返回。
2. **语义召回**：未精确命中时，用 embedding 相似度在 Chroma 检索 top_k。
3. **阈值过滤**：相似度低于阈值（如 0.6）且未命中商保创新药目录时，判定为**目录外**（不予报销）。命中后需回传 metadata 中的 `category` / `commercial_innovative` 供决策使用。
4. **（可选）重排**：top_k 结果用 rerank 模型或规则（规格/剂型一致性）再排序，提升准确率。

## 七、理赔决策逻辑

> 确定性规则引擎，纯 Python 实现，保证金额可复核。

### 7.1 决策规则（三层判定）

面向商业健康险场景，逐项药品按“医保可报”与“商保可报”两条线分别计算：

```
若 verified == false:
    结论 = 拒赔，理由 = "发票真伪查验未通过/信息不匹配"，可报金额 = 0

否则，逐项药品按三层判定：

  【第一层：基本医保目录内】
  若 category == "甲类":
      医保可报 = priceSum * reimburse_ratio        # 全额纳入基数，无先行自付
  若 category == "乙类":
      先行自付 = priceSum * self_pay_2              # 自付二
      医保可报 = (priceSum - 先行自付) * reimburse_ratio

  【第二层：商保创新药目录】
  若 commercial_innovative == true:
      医保可报 = 0                                 # 基本医保不报
      商保可报 = priceSum * 商保约定比例            # 商保核心报销对象

  【第三层：目录外】
  若 in_catalog == false 且 commercial_innovative == false:
      医保可报 = 0，标记"目录外，医保不予报销"
      商保可报 = 按商保约定目录判定（命中则按约定比例，否则 0）

  若存在 cap 且 该项可报 > cap:
      该项可报 = cap                                # 封顶

总医保可报 = Σ 各项医保可报
总商保可报 = Σ 各项商保可报
总可报金额 = 总医保可报 + 总商保可报
结论：
    总可报 == 总金额       → 全额通过
    0 < 总可报 < 总金额   → 部分通过
    总可报 == 0          → 拒赔
```

> 说明：`reimburse_ratio`（统筹报销比例）与商保约定比例为可配置参数，因统筹地区/保单而异，默认值写入 `config.py`。

### 7.2 决策输出结构

```json

  "verified": true,
  "total_amount": 400.0,
  "total_reimbursable": 284.0,

     "medical_reimbursable": 84.0, "commercial_reimbursable": 0.0,
```

## 八、多轮交互与记忆体验

> 本章对齐评分「流畅的多轮交互体验（20 分）」。

### 8.1 交互原则

- **一次处理，多轮复用**：首轮完成完整审核后，结果存入记忆；后续追问优先基于记忆回答，避免重复重推理。
- **流式反馈**：提取/推理过程流式展示（工具调用轨迹可见），提升可解释性与体感。
- **澄清式提问**：缺少关键信息（如图片不清、无药品明细）时，Agent 主动反问。

### 8.2 典型对话脚本

```
用户：[上传发票图片] 帮我审核这张发票能报多少？
助手：（流式）正在识别发票... 正在核验真伪... 正在比对药品目录...
      ✅ 发票真伪：通过
      结论：部分通过，价税合计 260 元，可报销 188 元。
      - 阿莫西林胶囊 120 元（甲类，全额 120 元）
      - 某进口保健品 140 元（目录外，不予报销）

用户：为什么那个保健品不能报？
助手：（基于记忆，无需重新调工具）该保健品未命中医保报销目录...

用户：如果按乙类 80% 算，能报多少？
助手：（携带新参数重调 claim_decision_tool）若按乙类 80%、先行自付 10% 计算...
```

## 九、权限控制与隐私保护

> 本章对齐评分「清晰的权限控制与隐私保护机制」能力。

- **全本地推理**：发票图片、OCR 结果、药品/理赔数据均在本地/内网处理，核心推理不出网。
- **外部调用最小化**：仅发票真伪查验调官方接口（业务必需），且不传递患者隐私信息（仅传发票号/金额等发票自身字段）。
- **敏感字段脱敏**：日志中对购买方名称、纳税人识别号等敏感信息脱敏；不记录原始图片到持久日志。
- **会话隔离**：以 `session_id` 隔离不同用户会话，记忆不跨会话泄露。
- **（可选）角色权限**：审核员/管理员区分，仅管理员可修改报销规则参数。
