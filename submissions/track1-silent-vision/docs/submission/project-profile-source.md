## 1. Project Background

Audio is not always a dependable control channel. A creator may be standing away
from a keyboard, working beside loud equipment, or avoiding an always-listening
microphone. A service desk may also need a visual alternative for a Deaf or
hard-of-hearing visitor.

Silent Vision explores one narrow response to that problem: recognize a small,
personalized catalog of fixed phrases from a short camera clip. The system asks
which registered phrase best fits the visible mouth sequence. It does not claim
open-vocabulary lipreading or arbitrary speech transcription.

The browser records a 2-5 second WebM clip with audio disabled. The service
returns a structured command decision and an agent result. The current source
does not control a physical device or create a media artifact; those downstream
actions require a separate, explicit integration.

The current catalog is one four-phrase bilingual catalog. The user selects the
language (`zh` or `en`) before recording; the service does not infer it from the
visible clip. The Torch classifier applies selected-language softmax only to the
enabled entries for that selected language.

| phraseId | Exact displayed text | Language | Mapped intent |
| --- | --- | --- | --- |
| `zh_light_on_hello` | `你好，请帮我打开灯` | `zh` | `LIGHT_ON` |
| `zh_chat_meal` | `你吃饭了吗？` | `zh` | `CHAT_OTHER` |
| `en_light_on_hello` | `Hello, please turn on the light.` | `en` | `LIGHT_ON` |
| `en_chat_meal` | `Have you eaten?` | `en` | `CHAT_OTHER` |

`UNKNOWN` is a rejection result, not a trained class. Accepted text and intent
are copied exactly from the checkpoint catalog rather than generated by the
model. It is a calibrated heuristic rejection, not a guarantee that every
unseen phrase will be rejected.

## 2. Target Users and Application Scenarios

The first target is a single user who can record personalized examples in the
same general camera setup used for recognition. This keeps the claim aligned
with the available data and avoids implying cross-speaker generalization.

Practical scenarios include:

- a creator who wants a deliberate hands-free input that another application can
  map to capture, cue, or editing actions;
- an accessibility counter where a small visual phrase set supplements other
  communication channels;
- a noisy work area where microphone recognition is unreliable; and
- a privacy-sensitive room where the operator does not want continuous audio
  capture.

The repository implements the recognition boundary, not those downstream
applications. An integration must still define which accepted intents are
allowed, whether confirmation is required, and how failures are handled.

## 3. Product Workflow and Safety Boundary

The current workflow is one shot:

1. The user selects the language and starts a capture with camera permission.
2. The browser records one silent command clip.
3. CPU preprocessing decodes the clip, detects one face, aligns the face, and
   extracts a 96 x 96 grayscale mouth sequence at 25 FPS.
4. The Torch classifier applies selected-language softmax, then predicts a
   registered `phraseId` and an embedding.
5. The decision is accepted only if both the checkpoint probability threshold
   and that phrase's maximum centroid-distance threshold pass.
6. Accepted output receives exact text and intent from the catalog. Rejected
   output becomes `UNKNOWN` and cannot execute.

Top-1 margin remains visible as diagnostic data but is not an acceptance gate for
the fixed-phrase Torch classifier. The probability and centroid-distance rule is
a calibrated heuristic, not a guarantee that every unrelated phrase will be
rejected.

The current agent policy marks `LIGHT_ON` executable, `CHAT_OTHER` ignored, and
`UNKNOWN` rejected. There is no device adapter, so an `execute` result is data,
not evidence that a real-world action happened.

## 4. System Architecture

The frontend uses `getUserMedia` with `audio: false` and `MediaRecorder` to
produce WebM. FastAPI creates a short-lived session and receives the complete
clip over a WebSocket. PyAV decodes and resamples frames. MediaPipe detects one
face and provides landmarks for alignment and mouth cropping.

All decode, face-detection, alignment, and crop operations run on CPU. The
resulting mouth tensor is transferred to `cuda:0`, PyTorch's device name for the
ROCm accelerator. The model runs there and returns phrase logits plus a
normalized embedding. The runtime applies the same probability and
centroid-distance decision function used by final evaluation.

Prototype mode is retained only for recording and data inspection. Fake mode is
used by deterministic tests. The official demonstration defaults to the Torch
backend and does not fall back to either mode.

Source recordings remain immutable. The manifest builder scans only the global
profile, maps exact normalized text through the catalog, retains the original
source intent for audit, deduplicates by sample ID and mouth-array SHA-256, and
creates disjoint train, calibration, and final-evaluation partitions.

## 5. Model and Algorithm

Input is a `[batch, time, 96, 96]` mouth sequence. The model normalizes pixels,
downsamples each frame to 16 x 16, computes the signed difference from the
previous frame, and concatenates the appearance and motion maps. A learned
projection produces 64 features per frame.

Two residual depthwise-separable temporal convolution blocks model short motion
patterns. Attention pools the temporal sequence. A normalized 64-dimensional
embedding feeds a linear phrase head whose size equals the number of enabled
catalog entries. The implementation rejects model configurations at or above a
150,000 trainable-parameter cap.

Training uses the same feature path as runtime. Training-only augmentation can
change brightness, spatial position, and temporal sampling. Calibration and
evaluation clips are not augmented.

After training, normalized training embeddings produce one centroid per phrase.
Known and unrelated calibration partitions select one minimum probability plus
a maximum cosine distance for each predicted phrase. Those thresholds are
stored in the checkpoint and frozen before final evaluation. The final report
includes metric numerators and denominators, per-phrase counts, a confusion
matrix, threshold provenance, checkpoint hash, manifest hashes, backend, and
device.

The official data gate requires 15 independent takes per phrase: 10 training, 2
calibration, and 3 final evaluation. It also requires 15 unrelated clips across
both selected languages: 5 calibration and 10 final evaluation. `--allow-small-dataset`
exists only to test execution and marks its artifacts non-evidentiary.

## 6. AMD Radeon / ROCm Adaptation and Reproduction

The AMD adaptation is explicit rather than automatic. Training and production
Torch inference require a ROCm-compatible PyTorch build, non-empty
`torch.version.hip`, an available accelerator, and a visible `cuda:0`. The code
fails closed when any condition is missing. There is no CPU fallback for the
Torch classifier.

The startup scripts preserve CPU work where it belongs: PyAV decode, MediaPipe
face detection, alignment, and mouth cropping. Only the learned fixed-phrase
model and its tensor operations run on Radeon through ROCm.

The reproducible workflow is:

1. record personalized and unrelated samples in explicit prototype mode;
2. build hashed, disjoint manifests from the immutable global profile;
3. train and calibrate the fixed-phrase checkpoint on Radeon;
4. run the frozen checkpoint on untouched final manifests; and
5. start the official WebSocket demo through the ROCm-guarded launcher.

Commands, dependencies, artifact locations, and evidence rules are documented in
the repository README and Radeon runbook. Private recordings and checkpoints
remain outside Git; the public bundle contains source, catalog, documentation,
profile, poster, and demo script.

## 7. Measured Radeon Evidence

The official run completed on 2026-08-06 with 73 known clips across the four
registered phrases and 15 unrelated clips split across Chinese and English. The
inventory, checkpoint, and final report are all marked `evidentiary: true`; the
final evaluator verified the complete manifest lineage and used frozen
checkpoint thresholds.

On the untouched final partitions, phrase top-1 accuracy was 12/12 (100%) and
mapped-intent accuracy was 12/12 (100%). Five of 12 known clips passed both
acceptance gates; all five accepted known clips had the correct phrase. Nine of
10 unrelated clips were rejected, while one was falsely accepted, giving 5/6
(83.3%) accepted precision across accepted known and unrelated clips.

Training and evaluation ran with PyTorch 2.9.1 on ROCm HIP 7.2 using `cuda:0`
on one `gfx1100` AMD GPU. The trained model has 46,405 parameters. The frozen
checkpoint SHA-256 is
`c70d28ae2ed84ee4b2cb0811ebff18870e7b905c1540bc96a782656fba385453`.
A real WebSocket test replayed an untouched Chinese light-on clip through the
complete video pipeline and returned the exact registered sentence with
`backend: torch`, `device: cuda:0`, `accepted: true`, and `action: execute`.

These are small, personalized, same-speaker fixed-phrase results. They do not
establish open-vocabulary lipreading, cross-speaker generalization, or guaranteed
rejection of arbitrary unseen phrases. The recorded demonstration is still
pending.
