## 3. 架构边界

- `app/ui/gradio_app.py` 只编排服务和 view-model，不包含第二套 Agent 规则；
- `CaseService` 复用 CaseWorkspace、Evidence Graph 与既有审计表；
- `WorkflowService` 复用 LangGraph、CaseState 和 SQLite checkpointer；
- `ReportService` 读取同一案件导出及工作流状态；
- 高成本证据节点通过 `inputs_hash` 与既有结果判断缓存命中；
- UI 中对原始材料的“修正”只追加材料角色变更事件，不修改原始证据；
- 对外状态上限为 `approved_for_manual_submission`。

## 5. 故障恢复验收

| 故障 | 预期与结果 |
|---|---|
| 本地模型超时/不可用 | local_vllm doctor 阻止启动；工作流故障注入保留前序 checkpoint |
| 节点 JSON/schema 错误 | 节点标记 failed，记录原因和 retry_count；从失败前 checkpoint 重试后成功 |
| 文档/视频解析失败 | 来源状态与错误进入 Evidence Graph/审计；已完成节点不清空 |
| 进程中断 | SQLite 保存最新 checkpoint；重启后用 case_id/thread_id 恢复 |
| 高成本节点缓存 | inputs_hash 未变化时复用 evidence 结果；恢复测试确认对象未变化 |

## 9. 2026-07-30 现场演示缺陷修复

首次由用户在 Mac 实际操作时发现：

- Golden Case 顶部显示已加载，但事故时间、地点等输入框没有回填；
- 点击“载入合成案件”和“刷新 / 恢复案件”后出现
  `[Errno 24] Too many open files`。

根因与修复：

1. Python SQLite 连接的上下文管理只提交/回滚事务，并不会自动关闭连接。
   Evidence Store、Case Memory Store 和 Legal Corpus Store 的读取路径已
   统一通过带 `finally: close()` 的事务上下文；doctor 单次检查也显式关闭；
2. `load_case` 原来只返回工作流视图，没有返回五个案件元数据字段，现已
   回填事故时间、地点、地区、角色和送达日期；
3. 程序更新下拉框也会触发 Gradio `change`，导致“载入合成案件”双重加载。
   现改为用户选择使用 `input`，按钮使用显式串行 `.then(load_case)`；
4. 案件列表对单个不可读/不完整数据库失败关闭并跳过，不再拖垮整个列表。

新增回归覆盖文件描述符计数与元数据回填。隔离环境的真实浏览器复验结果：

- Golden Case 首次打开五个字段均正确；
- 点击“载入合成案件”无错误；
- 完整运行至 100%；
- 连续点击“刷新 / 恢复案件”10 次无错误；
- 浏览器错误日志为空；
- 全量 120 项测试通过，1 项按环境条件跳过。

## 11. 车主主界面重构

用户现场体验后，确认产品关系应为：车主是主要使用者，保险公司负责协助
补件、核对和提醒，法律/理赔专家只处理争议与例外。原八页技术界面因此
调整为默认折叠的“保险公司 / 专业工作台”，车主首屏只保留：

1. 案件概览：状态、首选责任方案、车辆属性、期限和关键事实；
2. 权益行动：分析后立即显示下一步、车辆鉴定专项行动、完整任务清单、
   分阶段申请书与沟通记录；
3. 案件材料：车主/保险公司协作补件及提供方审计。

主界面不展示 case/thread、Fact/Evidence/Law ID、inputs hash、checkpoint 或
Policy Gate 等技术字段，但所有内容仍直接读取同一真实 CaseState。新增
的任务完成、协作补件和沟通结果均追加审计事件，不修改原始证据，也不
触发任何外部发送。

隔离数据副本的真实浏览器验收确认：

- 默认只显示三个车主入口，Golden Case 自动恢复；
- 当前责任方案、88.6% 支持度、车辆属性和 7 月 31 日期限正确显示；
- 沟通助手按四种程序阶段生成车辆属性检验鉴定、重新检验鉴定、补充鉴定
  或诉讼鉴定申请书，并明确不会自动提交；
- 案件材料显示分类和提供方；
- 保险公司协作台只保留协助、补件、审核三个入口；
- 高级详情与技术诊断默认折叠且完整保留。

## 12. 车辆鉴定行动与保险协作台简化（2026-07-30）

- 案件概览顶部直接显示当前最紧急行动，责任阶段性结论不再停留在分析；
- 车辆参数申请事项固定覆盖车速/动力输出、解除限速、整车质量、电机功率、

- 根据程序阶段区分 `《车辆属性检验、鉴定申请书》`、

## 13. 真实使用反馈后的文书与收件证据链修复（2026-07-30）

本轮只采用用户本人陈述的办案过程作为产品设计输入，并对姓名、电话、
车牌、具体单位和地址做脱敏。第三方对话中由模型生成的判例、法条和法律
结论全部排除，不进入法律语料、文书模板或规则引擎。

完成项：

1. 沟通助手的交管申请、相对方沟通稿和保险协作稿移除责任方向、概率、
   支持度和赔偿比例，只保留可回溯事实、证据索引、证据缺口与鉴定事项；
2. 申请书增加当面递交留存件、EMS 内件品名/附件目录、运单、付款凭证、
   物流轨迹、签收/拒收/退回及后续入卷确认的完整留痕清单；
3. 明确“当面 + EMS”为稳妥的证据固定建议，不将其表述为法定必经程序；
4. 修复车主与保险协作补件在未选择文件时抛异常、整张表显示 Error 的问题；
5. 保险协作台增加同一案件存储上的直接补件入口；
6. 文书审核页显示具体文书名称、版本、事实引用数、附件数、程序依据和
   中文补正事项，说明审核目标与通过后的人工递交流程；
7. 程序阶段或沟通对象变化时即时重新生成草稿，避免旧的法院文书与当前
   “交管部门尚未委托鉴定”选项同时显示。

设计依据和数据边界记录在 `docs/case_action_design_notes.md`。

验收结果：

- 在用户现有 `127.0.0.1:7860` 页面载入 Golden Case；
- 生成的交管申请包含事实/证据索引、鉴定事项、当面和 EMS 留痕清单，
  不包含“主要责任/次要责任/支持度/责任比例”；
- 程序阶段在法院鉴定与交管首次鉴定之间切换后，标题和收件机关同步更新，
  没有残留上一份草稿；
- 车主“加入当前事故材料”和保险“补充到当前事故”在未选择文件时均保持
  材料表不变、显示中文提示，页面无 Error；
- 保险文书审核明确显示 `《道路交通事故认定复核申请书》草稿 v1`、18 项
  事实引用、15 份附件索引、2 条程序依据及三项中文补正事项；
- 最新 Gradio 运行日志无 Traceback、Error、Exception 或 ValueError；
- 全量测试 `140 passed, 1 skipped`，mypy 82 个源文件通过；
- 法律引用离线快照/人工指纹审计 `59/59` 通过，失败数为 0。
