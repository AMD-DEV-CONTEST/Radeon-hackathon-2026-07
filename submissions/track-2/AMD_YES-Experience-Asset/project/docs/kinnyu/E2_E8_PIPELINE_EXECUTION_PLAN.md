## 1. 决策摘要

E2–E7 改为“单里程碑单一负责人、两位开发者错峰流水线开发”：

- 每个里程碑只有一位最终负责人，对后端、前端、测试、证据和 PR 的完整交付
  负责，但不要求其成为唯一贡献者；

本方案只改变执行和所有权，不改变 P0 产品范围、AC-01–AC-30、分阶段
RAG、Runtime 权限、隐私批准或比赛证据要求。

## 3. 阶段定义

### E2 — 首个可用产品切片

必须完成：

- 对话、粘贴文本、`.txt`、`.md` 输入；
- 来源范围和 provenance；
- 可编辑、自动保存的 `Experience Brief v0.1`；
- 事实、用户判断、Agent 推断和未解决信息分类；
- 回答、编辑、跳过、推迟、暂停、恢复、按当前证据生成；
- 一次可见的计划、当前来源检索、结构化 Tool Call、Runtime 裁决、
  真实效果、验证和终态；
- `Serving Reference S1` 和 `Vertical Slice V1`。

不得做：跨资产 RAG；把 S1/V1 称为正式 Baseline；自动处理 PDF、图片、
音频或视频；把导入文本中的指令当作系统指令。

### E3 — 时间线与关键时刻

必须完成：有序事件、变化、线索、意外、冲突和转折点；可编辑的
`Critical Moment Map`；时间缺失和来源冲突的可见状态；M1 修改后的
M2 失效和重算。

不得做：猜测缺失日期；为完整故事发明冲突、结果或转折；M1 版本变化后
继续把旧时间线显示为当前结果。

### E4 — 决策、行动、结果和证据

必须完成：替代方案、理由、最终决策、行动和观察结果；重要陈述的来源与
可信状态；`Decision and Evidence Ledger`；有限次数的结构化输出修复；
Runtime 的 allowlist、参数、身份、权限和审批检查。

不得做：把模型提议视为权限；用推断替代用户未提供的结果；隐藏工具拒绝、
验证失败或安全停止。

### E5 — 经验总结、边界与受控 RAG

必须完成：经验、反事实、限制、反例和迁移条件；可编辑的
`Insight and Boundary Map`；绑定当前资产版本/哈希的
`KnowledgeCardReady`；摘要候选检索；用户逐项确认或拒绝关系；确认后
只检索选中资产的有限详情；无匹配正常可见。

不得做：M4 就绪前搜索其他 Experience Asset；关系确认前读取历史详情；
用历史内容自动改写当前资产；把个人经历泛化成无条件建议。

### E6 — 路线、隐私和批准

必须完成：五个 `RouteDecision`；eligible、ineligible、
eligible-after-privacy-approval、blocked 状态；`Route Readiness Matrix`；
身份、健康、位置、购买支付、第三方、版权、品牌主张和专业建议等风险；
keep、generalize、remove、acknowledge；绑定资产版本/哈希的外部交付批准。

不得做：把预览、下载或内容生成视为外部批准；自动发布；内容修改后复用
旧批准；为路线资格补造信息。

### E7 — 确定性输出与删除

必须完成：用户选择中文或英文的路线草稿；应用内预览、自包含 HTML、
Markdown 和 canonical JSON；四种形态版本/哈希/事实一致；旧输出的
superseded 状态；二次确认、幂等删除、失败重试和审计。

不得做：强制同时生成双语版本；让不同格式基于不同资产版本；删除失败后
显示成功；直接向抖音、小红书或其他平台发布。

### E8 — 完整产品 Baseline

必须完成：七类公共夹具的相关路径；一次连续 Track 2 Agent 演示；真实
W7900、ROCm、PyTorch、vLLM 和模型记录；服务层、Agent 任务层、打磨体验层
指标；失败、重试、恢复、交互、后台并发和压力记录；不可变
`Baseline v1`。

不得做：在 Baseline 中混入量化或其他优化变量；只保留最好运行；用 E1-A3
或 E2 S1 替代完整产品 Baseline；没有可比 Baseline 时宣称性能提升。

## 5. 三个强制工程检查点与合并式深审

E2–E7 的每个 Issue 和 PR 都必须显式列出并依次通过以下三个工程检查点。
前两个检查点由负责人、自动化和异步代码审查完成，不要求质量负责人或用户
同步在线。第三个检查点按下文的轻量门/深审门节奏执行。

### 5.1 Contract / Schema + Fixture Checkpoint

- 冻结本阶段输入、输出、错误、进度和失效合同；
- 列出受影响的 canonical schema、API、migration 和共享入口；
- 冻结公共 fixture、失败用例、AC/L1/L2/Track 2 映射；
- 记录跨 Lane 支持范围、Reviewer 和证据模板；
- 未通过时不得接入真实前序状态或修改共享入口。

### 5.2 Runnable Backend / UI Vertical-Slice Checkpoint

- 后端、typed client 和 UI 在真实本地服务上跑通本阶段主路径；
- 至少一个失败/拒绝/恢复路径产生明确终态；
- 状态、进度、权限和失效信息来自真实持久化/API，不由 UI 编造；
- 当前阶段负责人完成联调；N+1 Draft 仍不得接入未通过门禁的真实数据。

### 5.3 Evidence / Promotion Checkpoint

- 相关公共测试、真实联调、浏览器或 GPU 检查通过；
- 证据包绑定准确 commit、fixture、命令、结果、失败和回滚；
- 无凭据、私有数据、隐藏 QA、权重或原始私密 Trace；
- 轻量门由公开检查、代码/联调审查和最小证据完成；深审门增加私有盲测和
  业务验收；
- 质量负责人给出 `PASS`，或给出带负责人、剩余风险和期限的
  `CONDITIONAL`；
- 只有 Critical/High 实质风险、失败的必要检查或无法判断风险所缺少的最小
  证据阻止 Ready/合并；格式、注释和文案偏好不单独阻断。

### 5.4 E7 前审计节奏

| 阶段 | 门禁 | 覆盖范围 | 用户是否需要同步参与 |
|---|---|---|---|
| E2 | 技术深审 + 异步产品审阅 | 首个有用切片、持久化、真实 Agent 闭环与初次 UX | 异步审阅；不锁 E3，意见须在 E4 提升前处理 |
| E3 | 轻量异步门 | M2 代码、公共测试与联调；私有盲测并入 E4 | 否 |
| E4 | E3+E4 合并深审 | 时间线、证据账本、Tool/Runtime/验证闭环 | 否，除非出现新的产品决策 |
| E5 | 轻量异步门 | M4 代码、公共 RAG 拒绝/非污染测试；私有盲测并入 E6 | 否 |
| E6 | E5+E6 合并深审 | Knowledge Card、分阶段 RAG、路线、隐私与批准 | 通常否；仅新的策略选择需要 |
| E7 | 完整深审 | 全链路、渲染、删除与功能冻结 | 是，最终产品确认 |

因此 E7 开始前只有 E2、E4、E6 三次技术深审；包含 E7 验收共四次。E7 前用户
只有一次 E2 异步产品审阅、没有计划内同步硬锁；E2 技术门通过后 E3 可继续，
但用户意见必须在 E4 提升前处理或明确裁决。E7 是唯一计划内必须由用户确认的
最终产品硬门。其余代码审查、CI、W7900 检查和私有盲测由质量负责人异步执行。
若公开测试或 diff 出现具体 Critical/High 风险，质量负责人可以把某个轻量门
临时升级为深审，并必须说明业务/比赛影响、证据和最小修复。

## 6. 错峰流水线规则

任意时间最多存在两个相邻阶段：

```text
阶段 N：正式实现、联调、证据和 PR
阶段 N+1：合同、Mock、测试和隔离模块准备
阶段 N+2：不得开工
```

下一阶段可提前做：

- 阅读需求和现有合同；
- 准备 Issue、AC/L1/L2 映射和验收用例；
- 构造公共 fixture、Mock 和失败用例；
- 编写不依赖前一阶段真实实现的隔离模块、纯函数和 UI 结构；
- 创建标记为 `blocked-by-E*-gate` 的 Draft PR；
- 准备证据模板。

下一阶段暂时不得做：

- 修改共享 canonical schema、API 主入口或迁移编号；
- 接入未经合并的前一阶段真实数据；
- 将 Draft 标为 Ready for review；
- 宣称里程碑完成；
- 绕过前置质量门禁合并。

正式依赖保持不变：阶段 N+1 只有在阶段 N 合并并通过质量门禁后，才能同步
最新 `main`、完成真实联调、转为 Ready、接受审核和合并。

## 7. 并行冲突控制

当前后端集中在 `api/main.py`、`domain/models.py` 和统一 repository，前端
集中在 `App.tsx` 与状态面板。两个里程碑同时修改这些文件会产生高冲突。

E2 起采用按里程碑隔离的目标结构：

```text
app/experience_asset/
  application/m1/
  application/m2/
  application/m3/
  application/m4/
  application/m5/
  api/routes/
  renderers/

web/src/
  features/m1/
  features/m2/
  features/m3/
  features/m4/
  features/m5/
  features/delivery/
```

规则：

- 正式阶段负责人拥有共享入口文件修改权；
- 下一阶段负责人只修改自己的新目录、Mock 和测试；
- SQLite migration 编号只由当前正式阶段创建；
- 下一阶段在前一阶段合并后同步最新 `main`，再进行真实联调；
- 不以 force-push 或共享历史改写解决依赖；
- 一个 Issue 对应一个分支和一个 PR；
- 最多两个实现 PR：一个正式审核，一个依赖阻塞的 Draft。

### 8.1 三类冻结语义

- **范围冻结（Scope Freeze）**：自 P0/L3 批准起已经生效。它禁止未经显式
  Change Control 的新 P0 需求，但不阻止实现已经批准的 E2–E7 行为。
- **功能冻结（Functional Freeze）**：只有 E7 完成真实试用并通过质量门禁
  后才生效。此后只接收阻塞正确性、隐私、权限、可复现性的问题修复和
  证据/材料工作；8月1日不能被称为功能冻结。
- **E8 Baseline 冻结（Baseline Freeze）**：只有完整正确性优先产品通过
  E8、不可变 Manifest 和 Baseline v1 被质量负责人接受后才生效。冻结后
  任何产品行为、合同、模型或 Runtime 变化都必须创建新的 Baseline 版本并
  重跑相同证据，不能改写 Baseline v1。

治理和证据准备，不得用于宣称 M1–M5、完整 Agent 或性能 Baseline 已通过。

## 11. 替代与回滚

本方案在质量负责人接受后，替代 L3 中 E2–E7 “每阶段 A/B 两个工作包”的
默认执行方式，但不改写历史 E1 证据。

若流水线准备造成持续合同漂移、共享文件冲突或质量门禁积压，质量负责人可
停止 N+1 准备，恢复单阶段串行开发。已接受里程碑和 Baseline 历史保持不变。
