# E5 边界 — 交付什么，不交付什么

这份文档不新增工作项。它把已经散在 issue #24 的 Non-goals、GraphRAG spec 的
Out of Scope 和各票 Owns 行里的边界收在一处，并为每条「不做」写明失败机制和注意力
该去哪里。

只写「不要做 A」会失败：禁令排除了一个行为，却没有给 Agent 的时间和判断提供新去向。
它可能停下 A，但同样可能转去做 C 或 D，或者无目标地探索。所以下面每条「不做」都配
一条「做什么」；说不清可信替代的，就只讲失败机制，并允许 Agent 自行选路。

---

## 一、交付什么（MECE：五项产品交付 + 三项支撑）

E5 的产品交付恰好五项，来自流水线执行计划的 E5 段。RAG 只占其中两项——把 E5 当成
「做一个 RAG」会让另外三项被当作附属品草草处理，而其中第一项风险最高。

| # | 交付 | 票 | 完成的判据 |
|---|---|---|---|
| ① | 提炼经验、反事实、限制、反例、迁移条件 | 02 | 用户能看到一份有边界的洞察，而不是一句无条件建议 |
| ② | 可编辑的《洞察与边界图》，每条证据可点开 | 02 | 用户能改，且能追到每条结论背后的语句与来源 |
| ③ | 绑定当前资产版本与哈希的 `KnowledgeCardReady` | 03 | 就绪指向一个确切版本，后续编辑无法继承旧关系 |
| ④ | 第一跳：摘要候选检索 | 04, 05, 06 | 显式点击后返回零或一个可解释候选，重复点击结果一致 |
| ⑤ | 第二跳：确认后只读选中资产的限定详情 | 07, 08 | 确认前读不到，确认后只读得到那一个资产的可达证据 |

三项支撑不是额外交付，而是让上面五项成立的必要条件：

| 支撑 | 票 | 没有它会怎样 |
|---|---|---|
| 合同与 fixture 冻结 | 01 | 每一票各自改一遍生成物，E6/E7 的 mock 被反复打断 |
| 失效、过期与重启恢复 | 09 | 关系活过被修正的证据，重启后权限状态不可知 |
| 证据包与真模型门 | 10, 11 | 无法向第三方证明上面任何一项真的成立 |

## 二、不交付什么

### A. 检索技术：不引入第二个数据存储

**不做**：embeddings、向量检索、reranker、外部图数据库、TiDB、Supabase、PGlite，或
任何第二个 canonical 数据存储。

**失败机制**：每引入一个存储，就多出一份 canonical 状态的副本，而这份副本必须与
SQLite 在同一个失效事件里同步。任何一次部分失败都会让两者分叉，而分叉的表现是
「某条关系在一个视图里已作废、在另一个视图里仍可点开」——这类不一致在测试里极难
构造，通常要到用户报告才被发现。

**注意力去哪**：把预算花在确定性预筛上——先按权限与生命周期过滤活跃就绪投影，再按
关系兼容的角色签名过滤，最后用 FTS5/BM25 摘要相关度做有界排序。只有当这套确定性
预筛跑完仍有实测检索失败时，向量方案才值得评估。

**不做**：graph-community 检测、全局摘要、开放式实体抽取。

**失败机制**：这些方法产出的节点没有 canonical owner。用户之后修正一条语句时，没有
机械手段找出哪些抽取结果依赖它，失效只能靠猜，而猜出来的失效意味着过期结论活过了
被修正的证据。

**注意力去哪**：确定性角色投影——只把已接受的 canonical 字段映射成角色，失效退化成
一次查表。

### B. 模型权限：模型提议，Runtime 裁决

**不做**：Agentic RAG 的难易路由，或任何让模型自行判断「这个任务简单/困难」从而切换
检索阶段的策略。

**失败机制**：难易判断没有可验证的依据，模型说「这个复杂，我需要更多历史」时，系统
无法反驳。范围扩大因此不需要任何人批准就发生了，而扩大后的检索仍显示为一次正常调用。

**注意力去哪**：固定阶段路由——M1–M4 只查当前资产，就绪且显式点击后才允许摘要级
跨资产，确认关系后才允许限定详情。三条边界都由 Runtime 持有。

**不做**：模型创建关系类型、事实、节点、边或因果链接。

**失败机制**：模型造出的关系类型对用户显示为一个正式标签，但它背后没有可采性规则，
Runtime 无法校验，用户也无从判断它和固定六种类型有何区别。

**注意力去哪**：闭合的六种类型加版本化角色对可采性表。没有标签合适时，no-match 比
一个近义词更能保住含义。

**不做**：第二次 LLM 调用来总结确认后的对照，或生成建议、下一步、新结论。

**失败机制**：用户审阅并确认的是一条具体关系——一个类型、一组角色映射、一条边界。
对它的生成式总结是用户没有审阅过的新产物，且产生于本该是最后一道检查的确认门之后。
它会偏离用户同意的那个东西，而偏离是不可见的，因为总结读起来就像是在描述它。

**注意力去哪**：应用代码确定性渲染——把双方的 canonical 语句、证据、来源标识摆出来，
判断留给同时经历过两段经验的人。

### C. 交互：用户的注意力是稀缺资源

**不做**：`KnowledgeCardReady` 之后自动发现。

**失败机制**：它花掉本地模型时间，并把历史摘要推到一个没有要求比较的人面前。更麻烦
的是，用户此刻刚完成自己的经验梳理，自动出现的历史内容会锚定他们对刚写完的东西的
判断，而这种锚定事后不可见——结论看起来像是自己想出来的。

**注意力去哪**：一次显式点击。它让比较成为一次有意的注意力分配，而不是完成自己工作
时的副作用。

**不做**：用户自由文本的跨资产比较查询。

**失败机制**：关系要长期存续，查询词是一次性提问。用措辞驱动发现，同一对资产在不同
问法下会得到不同关系，关系的含义退化成「上次那句话问出来的结果」，跨会话不可复现。

**注意力去哪**：整张已就绪卡片加 Runtime 拥有的发现意图版本作为输入；结果的稳定性
由完整指纹与幂等缓存保证。

**不做**：展示多于一个候选，或为填满 `top_k` 而补位。

**失败机制**：展示一条弱关系比漏掉一条可能的关系代价更大——它花掉用户注意力，让一份
本来可解释的资产显得不那么可信，还可能把之后的推理带向一段本不相关的经验。多给几条
不能修复这个伤害，只会让用户要评估的弱主张从一条变成几条。

**注意力去哪**：把模型和 Runtime 的注意力投在「这一条到底站不站得住」——角色对可采性、
必需的迁移边界、双边溯源。站不住就弃权。

**不做**：复杂置信度评分、学习排序、校验失败后的弱关系兜底。

**失败机制**：分数看起来精确，但它并不证明关联成立。一个 0.73 会让用户以为系统对这条
关系有量化把握，而实际上它可能连溯源都不完整。

**注意力去哪**：完整的已校验证据包作为准入规则——有固定类型、双边映射、来源支撑的
边界、双边溯源就展示，缺一样就不展示。

**不做**：确认前泄露历史详情；一次确认后开放广泛历史权限。

**失败机制**：确认前给出详情会让确认这一步失去意义——用户在决定「要不要看」之前已经
看完了。一次确认开放广泛权限则让授予的范围大于用户做出的决定：他们同意的是这段经验
值得和那一段比，不是打开自己的档案。

**注意力去哪**：把权限做成和决定一样大——绑定到那一个确认过的资产，且只覆盖已校验
映射与边界包可达的证据。

### D. 规模与发布：先证明最小任务

**不做**：50 或 100 资产的容量承诺、压测声明、性能优化。

**失败机制**：在功能与安全合同闭合之前谈容量，会让实现为了通过容量指标而放宽校验或
预筛——而那些正是这个功能的全部价值所在。

**注意力去哪**：三资产、一次批量调用，把正例、硬负例、非法提案三种行为钉死。容量
冒烟是功能闭合之后的可选证据，不是 MVP 验收门。

**不做**：对外发布，或把预览、下载、内容生成当作外部批准。

**失败机制**：这属于 E6/E7 的批准与投递边界，在 E5 里做等于绕过尚未实现的隐私处置和
版本/哈希绑定批准。

**注意力去哪**：E5 的产出停在「用户看到一张可检验的证据对照卡」，之后的路线与投递
交给 E6/E7。

### E. 阶段边界：不替其他人交付

**不做**：E6 的路线实现、E7 的渲染与删除实现、E8 的 Baseline 或性能。

**失败机制**：E6 与 E7 正在并行开发，同一批共享入口被两条线各改一遍时，冲突要到集成
当天才暴露，而那时三条线都已接近 `INTEGRATION_READY`，返工面是三倍。

**注意力去哪**：E5 拥有首个共享入口整合权，把那次整合做干净；E6/E7 需要的东西以冻结
合同的形式交出去，不代他们实现。

## 三、如何使用这份边界

遇到一个不确定要不要做的东西时，按顺序问：

1. 它是否属于第一节的五项交付或三项支撑之一？是 → 找到对应票，在那一票里做。
2. 它是否命中第二节任何一条「不做」？是 → 读该条的失败机制，把注意力转向「注意力
   去哪」那一行。
3. 两节都不覆盖？说明这是合同缺口。按并行合同的升级规则，在对应票面记录最小变更；
   只有新的重大产品、架构、隐私或权限选择才需要提前请求裁决。**不要就地自行决定并
   继续实现**——那会造成一个没有任何人审阅过的边界，而它会在 E6 集成时才被发现。
