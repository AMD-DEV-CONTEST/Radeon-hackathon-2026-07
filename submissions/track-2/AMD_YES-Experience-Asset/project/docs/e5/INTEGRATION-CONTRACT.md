# E5 集成合同 — Wave 0 与 Wave 1

**适用范围仅到 W1 结束。** W2 及之后（03、05、07、09、10、11）暂不并行，等 W1 跑完
拿到实测再决定。现在就为深链票准备 fake 层会失败：那些 fake 描述的是尚未存在的行为，
而写 fake 的 agent 只能按自己的猜测填充；猜错的部分会同时进入 fake 和断言，于是测试
全绿而实现是错的，直到集成当天才暴露。W1 跑完之后，02/04 的真实产物就能替代猜测。

**产出**（W1 四票全部只消费这些，不消费彼此）：

| 三份场景 fixture（正例、硬负例、非法提案） | 供后续票 |

**端点为什么要在 01 一次注册完**：`api/main.py` 只有一处 `include_router` 注册点。
四条分支各自往那里加一行，必然三方冲突，而冲突发生在一个每次都要重新生成的 151 KB
OpenAPI 上，人工解冲突极易漏字段。由 01 创建各 route 模块骨架并一次性注册，之后每票
只在自己的 route 文件里填 handler，`main.py` 全程只被动过一次。

骨架里未实现的 handler 返回一个类型化的未实现结果。**它不是可交付行为**：票 10 的
公开 QA 必须验证没有任何未实现 handler 残留在证据头上，否则一个 501 会被误读成
「功能存在但坏了」，而实际是「功能还没写」。

## 四、共享文件与写入权

并行下最贵的错误不是逻辑错，是两条分支改同一个生成物。下表规定 W1 期间谁能写什么。

| 文件 / 目录 | W1 期间可写者 | 其他票 |
|---|---|---|
| `app/experience_asset/domain/models.py` | 无人（01 已冻结） | 只读；需要改形状 → 回 01 走 contract-change review |
| `app/experience_asset/persistence/migrations/` | 按下方「迁移号认领」逐号分配 | 01 交付 `0008`；02 已认领 `0009` |
| `app/experience_asset/persistence/repository.py` | **四票均可，仅限追加** | 见下方「追加式共享文件」 |
| `contracts/openapi.json`、`contracts/json-schema/`、`contracts/examples/` | 无人（01 已生成） | 只读 |
| `web/src/contracts/types.ts` | 无人（01 已生成） | 只读 |
| `app/experience_asset/api/main.py` | 无人（01 已注册全部路由） | 只读；构造参数不足以驱动 handler 时 → 回 01 |
| `web/src/App.tsx` | **四票均可，仅限追加** | 见下方「追加式共享文件」 |
| `app/experience_asset/api/routes/m4.py` | **02** | — |
| `app/experience_asset/api/routes/relation.py` | **08**（仅证据读取 handler） | 05/07 在 W2+ 填各自 handler |
| `app/experience_asset/application/m4/`、`workflow/m4_*` | **02** | — |
| 投影与检索模块 | **04** | — |
| attempt 与指纹模块 | **06** | — |
| 证据卡与详情读取模块 | **08** | — |
| `web/src/features/m4/` | **02** | — |
| 关系相关前端组件 | **08**（仅证据卡视图） | 05/07 在 W2+ |

**规则**：一条分支发现自己需要写不属于它的文件时，不要就地改。那会造成一次没有 owner
的形状变更，而另一条分支正基于旧形状写断言，冲突要到合并时才出现，且看起来像是无害的
文本冲突。正确做法是在票面记录这个需求，按并行合同的升级规则处理。

### 追加式共享文件

`repository.py` 是四票都要写的，因为每票的持久化方法只有它自己知道要什么形状，而把它们
拆进四个文件会让一个类的事务边界散在四处。它不适用「无人可写」，改用**追加规则**：

- 每票只在类尾部追加自己里程碑前缀的方法（`*_m4_*`、`*_projection_*`、`*_attempt_*`…），
  不改、不重排、不重命名他票已有的方法；
- 跨票共用的读取器（如 `get_workflow_run_context`）只允许**增加返回字典的 key**，不允许
  改动或删除已有 key。已有 key 一旦改动，另外三票的游标校验会在合并当天同时失效，而每票
  单独跑测试时都是绿的；
- 合并冲突预期发生在类尾部，属于纯追加冲突，按先后顺序拼接即可，不需要语义裁决。

`web/src/App.tsx` 同理。它是工作区外壳，而每张有界面的票都必须挂进去——票 02 的票面直接
写明「the M4 workspace joins the existing workspace shell alongside M1–M3」，理由是：另建
独立页面会让用户的资产同时存在于两处，而两处会在版本与失效状态上漂移，用户无从判断哪个是
当前的。所以外壳不能设为「无人可写」。规则：每票只加自己的 tab 常量、按钮与一个分支，不动
他票的分支；`activeView` 的联合类型按字母序追加成员。

### 迁移号认领

迁移按文件名前缀顺序执行，`schema_migrations` 表记录已应用的编号与 checksum，启动时只跑
编号更大的；同一编号只会被记录一次。两条分支各自新建 `0009_*.sql` 的后果不是冲突报错，而是
先合并的那个被记录为「9 已应用」，后合并的那个**永远不会执行**，于是它的表在生产库里不
存在，而代码假定存在——症状要到运行时缺表才出现。

因此：需要新表的票，先在本节登记编号再写文件。

| 编号 | 票 | 内容 |
|---|---|---|
| `0008` | 01 | E5 关系账本、M4 artifact 表、readiness sidecar |
| `0009` | 02 | M4 run 记账：`m4_model_proposals`、`m4_run_commits`、`m4_policy_decisions`，以及 `workflow_run_contexts` 的四个 M4 列 |
| `0010` | 03/04/08 | `retrieval_phase_events`：产品路径写入冻结的 retrieval-phase-trace |

`0009` 是 01 冻结的补齐，不是 02 的新需求：0008 给了 M4 的 artifact 表，但没给 M3 在 `0006`
里拿到的 run 侧表，于是 M4 的 run 无处记录被校验的提案、重启后无法幂等提交、票 02 验收
标准第 7 条要求记录的 context 上界无处可存。同理 `api/main.py` 的 `build_m4_router`
签名不收 graph，01 落地的那次注册无法服务任何需要 graph 的 handler。两处都由 02 就地补齐
并在此登记；04/06/08 需要的表 `0008` 已全部给出，不受影响。

`0010` 同理是补齐而非新需求：retrieval-phase-trace 的 schema、检查脚本与前端消费方都已存在，
但产品路径没有生产者——只有 E2 的证据采集脚本在写。票 03/04/08 各自的验收标准都要求在这个轨迹上
可观测，三票共用一张事件表，因此登记为一个编号而不是三个。

票 09 不新增迁移：`0008` 已经给出全部生命周期列（`knowledge_card_readiness`、
`role_graph_projections`、`relation_candidates`、`confirmed_asset_relations`）与 FTS 触发器，
失效所需的状态迁移在既有列上完成。

## 五、fixture 债务与「完成」的定义

W1 的 04、06、08 是对着 fixture 构建的。这意味着它们在 W1 结束时达到的是
**「已构建」而不是「已完成」**。

**债务记在消费方。** 04 用了 M4 图 fixture，就由 04 负责在 02 落地后把测试改跑真实
产物；08 同理，等 05/07 落地后跑真实候选与确认关系。让生产方（02、05、07）去改消费方
的测试会失败：生产方不知道消费方对 fixture 做了哪些假设，改到哪里算改完没有判据，而
消费方对自己的假设一清二楚。

| 票 | W1 结束时状态 | 何时可标 `INTEGRATION_READY` |
|---|---|---|
| 02 | 已完成 | W1 内即可 |
| 04 | 已构建，fixture 债务未清 | 02 与 03 落地并跑通真实投影输入之后 |
| 06 | 已构建，fixture 债务未清 | 05 落地并跑通真实发现输入之后 |
| 08 | 已构建，fixture 债务未清 | 07 落地并跑通真实确认关系之后 |

把「已构建」当成「已完成」会失败：证据包会声称某项行为通过，而那次通过用的是本项目
自己编的输入。第三方复核时无法复现，整包可信度受损——不是只损失那一条。

## 七、W1 结束时要回答的问题

这一波的另一个目的是取得实测，用来决定 W2 及之后是否继续并行。跑完记录：

1. 四条分支合并时实际发生了几次冲突，分别在哪些文件？如果出现在本文档标为「无人可写」
   的文件上，说明 01 的冻结不够完整。
2. 04/06/08 各自对 fixture 做了哪些超出 fixture 明示内容的假设？数量越多，说明深链票
   并行的风险越高。
3. 实施模型在哪些地方越过了票面边界（做了 `Not in this ticket` 里的事）？
4. 并行实际省下的时间，与集成和债务清偿花掉的时间，孰多孰少？

这四个问题不需要精确度量，但需要有事实回答。没有它们，W2 是否并行只能靠感觉决定，
而感觉在这里通常偏向乐观——并行的收益立刻可见，成本要到集成时才到账。
