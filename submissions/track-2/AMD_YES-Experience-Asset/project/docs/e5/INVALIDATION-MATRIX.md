# E5 失效矩阵 — 变更事件 × 制品

票 09 的第一交付物。写在代码之前，因为没有矩阵时每个事件都变成一次「这八个制品里该动哪几个」
的临时判断，而**没人想到的那个会继续活着**——一条留着的权限从外部完全看不出来，不像一个
写错的状态那样会有人报。

矩阵的唯一事实来源是 `app/experience_asset/application/invalidation/matrix.py`，本文是它的
可读版本。两者不一致时以代码为准，并把本文修正过来；测试
`tests/integration/test_e5_invalidation.py` 直接读矩阵数据驱动，因此往矩阵里加一个制品却没有
实现，会在那里失败，而不是安静地留下一个可达的制品。

## 一、矩阵

行是事件，列是制品。事件命名的是**发生变更的那个资产**。

| 事件 | 就绪 | 投影 | 索引可用性 | attempt | 候选 | 决定 | 关系 | 详情权限 |
|---|---|---|---|---|---|---|---|---|
| 当前资产修正/重开 | 失效 | 失效 | 撤销 | 保留供审计 | 失效 | 保留供审计 | 失效 | 撤销 |
| 相关资产变更 | **不变** | 失效 | 撤销 | 保留供审计 | 过期 | 保留供审计 | 过期 | 撤销 |
| 资产删除 | 失效 | 失效 | 撤销 | 保留供审计 | 失效 | 保留供审计 | 失效 | 撤销 |
| 隐私范围收窄 | 失效 | 失效 | 撤销 | 保留供审计 | 失效 | 保留供审计 | 失效 | 撤销 |
| 投影 schema 变更 | **不变** | 失效 | 撤销 | 保留供审计 | 过期 | 保留供审计 | 过期 | 撤销 |
| 模型/prompt/配置变更 | 不变 | 不变 | 不变 | 保留供审计 | 不变 | 保留供审计 | 不变 | 不变 |

## 二、几个格子为什么是那个值

**「过期」与「失效」不是同一件事。** 过期指比较所依据的东西动了，用户必须自己选择再看一次；
失效指它描述的东西已经没了。合并两者的代价是二选一：要么强迫用户在一个没人动过的资产上重做
工作，要么留下一条主体已不存在却仍可达的关系。

**相关资产变更时，引用方的就绪必须活着（GRAG-16）。** 这是最容易顺手做过头的地方：把引用方
的卡也失效掉，会让上面那条测试因为错误的原因通过，并且强迫用户在一个他们没有碰过的资产上重新
接受一次。动的是比较的依据，所以过期的是比较本身。

**attempt 与决定任何事件都不动。** 它们是「当时发生过什么」的记录。删掉或改写会让一条被作废的
关系与一条从未存在的关系无法区分，而这正是复核者需要分辨的。

**模型/prompt/配置变更什么都不撤销。** 新的模型、prompt 或配置产生新的 discovery 指纹，于是
旧答案不会被拿来回答新问题——机制是指纹，不是失效。在这里做失效，等于因为一个无关组件升级就
丢掉用户已经确认过的关系。

**索引可用性与详情权限单独列，因为它们是会静默失败的两个。** 一行残留的索引仍然为已经不存在的
canonical 状态授予可比性；一条残留的权限仍然为重放的请求或另一个标签页授权详情读取。两者都不会
在界面上表现出来。

## 三、走账本的哪一侧

同一次物理变更，随着被改资产在候选里担任的角色不同，是不同的事件：

| 事件 | 匹配 `current_asset_id` | 匹配 `related_asset_id` |
|---|---|---|
| 当前资产修正/重开 | ✓ | — |
| 相关资产变更 | — | ✓ |
| 资产删除 | ✓ | ✓ |
| 隐私范围收窄 | ✓ | ✓ |
| 投影 schema 变更 | ✓ | ✓ |

每个事件都走两侧，会把用户在一个他们没动过的资产上确认的关系一起作废；删除只走一侧，会让账本的
另一半继续指向已经没有的内容。

## 四、删除时的内容删除，与隐私收窄时的不删

候选行里带着描述对方资产的标题与摘要。资产被删除后仍保留这两个字段，等于在审计轨迹内部重建了
删除请求本要移除的那份副本。因此**只有删除**会把标题与摘要替换为占位文本
(`REDACTS_COPIED_CONTENT`)。

标识与哈希保留：它们是这条记录之所以可审计的原因，而它们不是内容。节点映射同样保留——那是节点
标识，不是被要求删除的文本。

**隐私范围收窄刻意不在此列。** 它撤销的是对仍然存在、用户也没要求抹掉的内容的访问；在那里删字段
等于在没有任何删除请求的前提下销毁审计细节。

## 五、原子性

投影生命周期迁移与索引行移除必须同一事务，否则中间崩溃会留下一行索引，它仍然为已经不存在的
canonical 状态授予可用性。FTS 行的删除挂在 `trg_relation_summary_fts_projection_deactivated`
触发器上，正是为了让它无法与生命周期迁移分开。

候选的生命周期同时存在于列与 `content_json` 里，两者必须一起改。只改列会让快照继续宣称旧状态，
而每一次读取都是从快照重建候选的——于是同一行对 SQL 报 `INVALIDATED`，对产品报 `PROPOSED`。

## 六、版本绑定是第二道防线

`read_confirmed_relation` 与 `list_confirmed_relations` 现在绑定资产的当前版本，和就绪记录
一直以来的做法一致。这条不依赖任何人记得调用失效服务：资产一旦推进到新版本，确认的读取就自己
收口了。

在此之前，确认会比它所依据的卡活得更久——就绪已经撤回，关系列表还在回答，两者对「这张卡还能不能
用」给出相反的答案。修在读取处而不是调用方，因为授权在每次策略评估时都从仓储重新投影，检查放在
别处就会被下一个忘记检查的调用方绕过。

原先把这个洞钉成测试的
`test_a_confirmed_relation_outlives_the_card_it_was_confirmed_against` 已按票 09 改写为
`test_a_confirmed_relation_does_not_outlive_the_card_it_was_confirmed_against`，保留了它
曾经存在过的记录。
