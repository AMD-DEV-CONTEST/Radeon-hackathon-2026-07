# Experience Asset — 当前产品方向与后续演进

## 这份文档的用途

这是一份团队内部的产品判断说明，不是新的开发计划，也不替代
`SUBMISSION_FACTS.md`、验收条件或团队的证据。它回答三件事：当前版本
为什么这样收敛、现在最容易被误解的地方是什么、比赛结束后哪些方向值得
继续补。

评委材料只吸收其中已经实现且有证据的判断。未来方向不得写成当前能力。

## 审计结论

当前版本的方向是成立的，并且比最初较宽泛的“帮助普通人做自媒体”更适合
本次黑客松。

最初方向包含定位、选平台、起号、学习、内容、私域和增长等多个问题，真实
需求存在，但在一个 Demo 里很难形成可验证的任务终点，也容易退化成模型
给建议。当前版本把问题收敛为：

> 帮助用户把一段真实经历整理成一份有来源、有边界、可纠正、可恢复、可
> 复用并能安全交付的 Experience Asset。

这个收敛带来三个实际收益：

1. 用户从零散输入走到规范资产和可交付结果，形成可观察闭环；
2. LangGraph、RAG、Tool Calling、memory、privacy/permission 都对应真实
   产品行为，而不是为了满足赛道标签而拼装；
3. 本地推理、证据约束和用户批准成为产品成立条件，而不是附加宣传点。

## 当前版本的核心判断

### 1. 先形成资产，再生成内容

产品不以“一次生成一篇文章”为核心。先区分事实、判断、推断和待确认信息，
再建立关键时刻、决策证据、经验边界和受众路线。文章、演示、复盘或自媒体
内容是同一资产的下游表达。

这样做的价值不是让文案更华丽，而是让用户以后能够纠正、更新、复用和解释
一项主张为什么成立。

### 2. 用户不需要先成为专家

用户可以以专家、实践者或学习者身份开始。共同门槛不是工作年限，而是有一段
真实经历、实践、专业能力、产品雏形或长期问题，并愿意确认其中的事实与边界。

当前 P0 没有把三种身份做成单独的用户入口。这仍是一个有价值的易用性改进，
但不影响核心资产模型成立。

### 3. 自媒体是下游场景，不是当前全部定位

抖音、小红书等平台仍可作为重要应用场景，但当前版本不承诺平台增长、流量
预测、自动发布或代替用户运营。现阶段更合理的产品关系是：

```text
真实经历 / 实践 / 专业认识
-> Experience Asset
-> 受众路线与隐私批准
-> 平台内容简报、系列选题、表达素材或复盘
```

这样既保留最初帮助普通人表达和成长的愿景，也不会把难以证明的平台建议冒充
为 Agent 已完成的结果。

### 4. 模型负责建议，系统负责权力

模型可以提议结构、关系或工具调用，但不能自行授权历史检索、执行工具、通过
隐私检查或批准外部分享。LangGraph 维护步骤与恢复，确定性 Runtime 负责
权限、身份、验证、终态和审计。

这是当前项目最重要、也最值得保留的技术产品判断。

## 当前版本的优势

- 有清楚的 M1–M5 用户旅程和中间产物，不是聊天壳；
- 规范资产、版本身份、批准失效和恢复机制使任务真正可继续；
- M4 后才允许跨资产发现，详细检索必须再次确认，RAG 边界有辨识度；
- 本地推理和私有数据边界与赛道二直接相关；
- Preview 与 HTML/Markdown/JSON 导出给任务一个明确终点；
- 当前材料能诚实区分本地集成、历史实机证据、服务层证据与完整产品 A0。

## 当前版本最需要防止的误解

### 产品名和中间产物偏抽象

“Experience Asset”“Decision and Evidence Ledger”等术语准确，但新用户和
评委可能需要先看一个具体前后对比，才能理解它解决了什么。因此 Demo 和 PPT
应该先展示输入碎片与最终可用结果，再解释 M1–M5。

### 工程治理可能压过用户价值

证据 hash、版本身份、approval binding 和 fail-closed 很重要，但不能成为
主叙事。评委首先需要看见用户完成了什么；技术机制随后解释为什么这个结果
值得相信。

### 多条模型证据容易造成混淆

历史 M1/M2 使用 Qwen2.5-14B，Stage 1 服务测试使用 Qwen3.5-9B，而最终
应用 A0 模型仍待冻结。最终材料必须只给一个明确的提交模型，不应让评委自己
判断哪一个才是产品模型。

### 导出格式不等于最终用户价值

HTML、Markdown、JSON 证明了交付闭环，但真正的价值是“同一份证据资产可以
安全适配不同受众”。最终 Demo 应展示一个实际可读的受众结果，而不是只展示
文件下载成功。

## 提交前最值得优先补齐的内容

以下是给团队取舍的提交建议，不是本文档新增的审核或批准门槛：

1. 冻结一个包含完整用户路径的应用提交；
2. 用最终本地模型在 W7900 上跑通一条连续 M1→M5→批准→预览/导出流程；
3. 固定模型 revision、运行环境、测试账本和可追溯证据；
4. 用同一公开案例完成 3–5 分钟 Demo；
5. 在开头直接展示“零散经历 → 可复用资产”的前后变化；
6. 统一最终应用模型、Commit、截图、测试数量和公开链接；
7. 保留一个真实纠错、隐私阻断或安全失败时刻，证明它不是顺滑脚本演示。

根据剩余时间，优先补真实提交证据与用户价值表达；是否扩展其他
内容由团队自行决定。

## 提交后优先演进方向

### 第一优先：降低普通用户的理解成本

- 用“发生了什么、为什么这样做、学到了什么、准备分享给谁”等自然语言替代
  UI 中过重的工程术语；
- 增加专家、实践者、学习者三种起始身份，引导不同深度的提问；
- 把缺失信息、证据强弱和下一步行动做成直观卡片；
- 支持更顺畅的局部编辑、差异对比和批准失效解释。

这一阶段不改变核心数据模型，主要提升上手速度和 Demo 说服力。

### 第二优先：把自媒体愿景接回产品

- 为小红书、抖音等增加“平台表达适配器”，输出内容简报、系列选题图和素材
  清单，而不是直接承诺流量结果；
- 根据用户的专家/实践者/学习者身份，给出不同的表达边界与学习任务；
- 保存发布后的用户反馈和复盘，由用户主动导入本地，形成下一轮经验资产；
- 明确区分事实建议、平台规则、经验判断和仍需验证的增长假设。

这能恢复项目最初“帮助普通人找到方向并持续成长”的目标，同时保持当前的
证据与隐私架构。

### 第三优先：深化本地知识资产系统

- 扩展经用户授权的 PDF、Word、Markdown、代码仓库与历史内容导入；
- 建立跨 Experience Asset 的关系图、来源追踪和冲突提示；
- 继续坚持摘要级候选发现与用户确认后的详细检索；
- 增加可解释的检索质量、引用覆盖率和污染检测。

### 第四优先：性能与部署产品化

- 基于完整产品 A0 做可比的 Stage 2 优化，而不是只比较服务吞吐；
- 优化模型选择、上下文预算、缓存和结构化输出可靠性；
- 提供一键本地部署、模型完整性验证、资源检测和故障恢复；
- 在不牺牲证据质量、隐私门禁和完成率的前提下降低等待时间。

## 暂不建议的扩展

- 自动发布或代管平台账号；
- 爬取受限平台数据作为核心依赖；
- 用流量预测替代用户定位判断；
- 在没有可靠评价方法前增加大量 Agent 角色；
- 为展示“功能多”而加入图像、视频生成或自动剪辑；
- 让历史资产在用户确认前直接改写当前经历；
- 在完整产品 A0 之前进行大规模性能优化或模型切换。

这些方向会明显扩大权限、数据、评价和演示风险，但不会优先增强当前作品最
核心的说服力。

## 材料使用原则

修改建议按三类处理：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 事实更新 | Commit、测试、模型、W7900 结果、Demo URL | 使用可追溯信息更新 `SUBMISSION_FACTS.md`；格式由团队自定 |
| 表达改进 | 标题、示例、视觉顺序、术语解释 | 优先维护英文提交材料；中文版是可选参考 |
| 产品方向变化 | 新目标用户、新平台能力、改变 M1–M5 或权限规则 | 先由团队确认；不能仅通过改 PPT 使其成为当前能力 |

对评委材料的默认判断是：增加内容不一定更好。只有能让评委更快看懂用户结果、
更相信实机证据，或消除一个真实误解的内容，才值得进入 PDF/PPT；其余保留在
本文件作为后续演进依据。
