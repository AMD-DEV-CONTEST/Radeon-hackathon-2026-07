# openpi (ROCm edition · arbitrary cameras + one-click training/inference)

This repository is based on [Physical Intelligence](https://www.physicalintelligence.company/)'s openpi, tailored for the π05 (π0.5) model and adapted for delivery on **AMD ROCm (gfx1100 / RDNA3) single GPU**:

- **ROCm-only**: The entire install/train/inference chain runs only on AMD ROCm (system python3.12 + apt ffmpeg + `.venv`, gfx1100).
- **Feature 1: Arbitrary number of cameras**. π05 no longer hardcodes 3 cameras; it supports 1–8 (and more) freely named cameras. Declare on the command line "which keys in the dataset correspond to which camera image".
- **Feature 2: One-click training + HTTP inference**. The repo root provides entry scripts such as `compute_norm_stats.py`, `train_jax.py`, and `inference_server.py`, all pure CLI — no need to write Python, no need to modify `src/openpi/training/config.py`.

> **Two companion documents (ROCm tested)**
> - Install / train / inference (including VRAM and pitfalls): [docs/amd_rocm_jax.md](docs/amd_rocm_jax.md)
> - BiGym closed-loop evaluation with 3DGS room shell + end-to-end performance benchmark: [docs/amd_rocm_bigym_eval.md](docs/amd_rocm_bigym_eval.md)

The data layer uses LeRobot Dataset v3.0 (lerobot>=0.6.0), pointed directly at a local dataset directory via `--data-dir`. The BiGym training/evaluation data tested in this repo is generated by [bigym_plus](https://github.com/WuChao-2024/bigym_plus) (see each doc).

## Installation (.venv + apt)

Ubuntu 24.04 ships with **python3.12** (AMD ROCm JAX 0.6.0 only releases cp312 wheels, a perfect match), and `apt`'s **ffmpeg 6.1.1** falls within torchcodec 0.5's supported range of 4–7 — so system python + apt + a single `.venv` is enough to set up the entire ROCm stack, **no conda needed**. The following flow has been tested and reproduced on gfx1100 / ROCm 7.2.1 (apt ffmpeg → venv → JAX sees the GPU → normalization stats → training → HTTP inference, all working end-to-end).

```bash
git clone https://github.com/WuChao-2024/openpi_lerobot_plus openpi
cd openpi

# (1) apt: ffmpeg (video decoding) + python3.12-venv. Ubuntu 24.04's ffmpeg is 6.1.1 (torchcodec 0.5 compatible)
sudo apt-get update
sudo apt-get install -y --no-install-recommends ffmpeg python3.12-venv

# (2) Create venv (system python3.12) and upgrade pip
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip

# (3) AMD ROCm JAX 0.6.0 (repo.radeon.com proprietary wheel) + jax/jaxlib/scipy/numpy
pip install \
  https://repo.radeon.com/rocm/manylinux/rocm-rel-7.0.2/jax_rocm7_pjrt-0.6.0-py3-none-manylinux_2_28_x86_64.whl \
  https://repo.radeon.com/rocm/manylinux/rocm-rel-7.0.2/jax_rocm7_plugin-0.6.0-cp312-cp312-manylinux_2_28_x86_64.whl \
  "jax==0.6.0" "jaxlib==0.6.0" "scipy>=1.11.1" "numpy>=1.26,<2.3.0"

# (4) ml-dtypes 0.5.4 (--no-deps to prevent being pulled back)
pip install --no-deps "ml-dtypes==0.5.4"

# (5) CPU torch / torchvision (avoid dual ROCm runtime conflict between jax-rocm and torch-rocm)
pip install --index-url https://download.pytorch.org/whl/cpu "torch==2.7.1" "torchvision==0.22.1"

# (6) openpi ecosystem dependencies: requirements_rocm.txt with jax/torch/ml-dtypes/lerobot (already installed in previous steps) stripped out
grep -v -E '^\s*(jax\[|jax==|jaxlib|ml-dtypes|torch==|torchvision|lerobot\[)|^https://repo.radeon.com' \
  requirements_rocm.txt > /tmp/req_rocm.txt
pip install -r /tmp/req_rocm.txt

# (7) lerobot runtime dependencies + torchcodec 0.5 CPU build
pip install "av==15.1.0" "datasets==4.8.5" "pyarrow==25.0.0" "pandas==2.3.3" \
            "draccus==0.10.0" "gymnasium==1.3.0" "jsonlines==4.0.0" \
            "opencv-python==4.11.0.86" "opencv-python-headless==4.11.0.86"
pip install --index-url https://pypi.org/simple "torchcodec==0.5"

# (8) lerobot (--no-deps to bypass hub conflict) + openpi editable (--no-deps to bypass pyproject's cuda pin)
pip install --no-deps "lerobot==0.6.0"
pip install -e . --no-deps

# (9) Apply the PyTorch backend transformers patch
cp -r src/openpi/models_pytorch/transformers_replace/* \
  "$(python -c 'import transformers,os;print(os.path.dirname(transformers.__file__))')"

# (10) Write ROCm library paths into the venv activation hook once (equivalent to conda's activate.d)
cat >> .venv/bin/activate <<'EOF'
export LD_LIBRARY_PATH="/opt/rocm/lib:${LD_LIBRARY_PATH:-}"
EOF
```

Prerequisite: the host has ROCm installed (`/opt/rocm`), and `rocminfo` can recognize gfx1100. Version pins and dependency list are in `requirements_rocm.txt`.

Afterward, for each new shell: `source .venv/bin/activate` (the activation hook has already automatically set `LD_LIBRARY_PATH=/opt/rocm/lib`, so JAX can dlopen the HIP/MIOpen libraries under `/opt/rocm/lib`).

**Why a single `pip install -r requirements_rocm.txt` won't work** (the stepwise flow above is precisely to work around these pitfalls):

1. **lerobot conflicts with huggingface-hub**: lerobot 0.6.0 metadata declares `huggingface-hub>=1.0`, but transformers 4.53.2 and requirements both require `<1.0`, so the pip resolver errors out directly. In practice lerobot works with hub 0.36.x (metadata is too strict); install lerobot with `--no-deps` to bypass.
2. **ffmpeg version**: Ubuntu 24.04's apt default is **ffmpeg 6.1.1** (`libavutil.so.59`), which falls within torchcodec 0.5's supported range of 4–7, so `apt install ffmpeg` works directly — no need to pin like with conda (conda-forge defaults to 8, out of range).
3. **torchcodec build**: the default index pulls `0.5+cu128` (depends on `libnppicc`); use `--index-url https://pypi.org/simple` to pull the CPU build `torchcodec==0.5`.
4. **ml-dtypes must be 0.5.4**: jaxlib 0.6.0 requires `float4_e2m1fn` at runtime; 0.4.1 lacks it and will crash on `import jax`.
5. **torch goes CPU**: avoid the dual ROCm runtime symbol conflict between jax-rocm7 and torch-rocm6.4.
6. **openpi installed with `--no-deps`**: bypass the upstream legacy cuda pin in pyproject (`jax[cuda12]==0.5.3`), keeping the AMD jax 0.6.0 installed by this flow.

Key pins (do not change): `jax==0.6.0` (rocm7.0.2), `jaxlib==0.6.0`, `ml-dtypes==0.5.4`, `torch==2.7.1+cpu`, `lerobot==0.6.0`, `transformers==4.53.2`, `huggingface-hub<1.0`, `numpy<2.3.0`, `ffmpeg 6.1.1` (apt).

> The repo still ships `install_rocm.sh` (conda route, legacy). The **.venv + apt** route above is the one this document recommends and has reproduced on gfx1100.
>
> **VRAM coexistence note**: within the same process, jax will pre-allocate ~75% of VRAM, thereby squeezing out torch. If other GPU workloads in the same process need to move JAX to CPU, set `JAX_PLATFORMS=cpu`.

## pi05 base checkpoint

| Model | Purpose | Path |
| --- | --- | --- |
| pi05 | Fine-tune base model | gs://openpi-assets/checkpoints/pi05_base |

The checkpoint is downloaded and cached by default to `~/.cache/openpi`, overridable with `OPENPI_DATA_HOME`. If the ROCm host has no GCP credentials, the anonymous download in `train_jax.py` may fail — pre-fill the local cache first with `python3 prefetch_base.py` (see entry script overview).

## Entry script overview

The customer entry scripts in the repo root (all pure CLI, no modification to `src/openpi/training/config.py`):

| Script | Purpose |
| --- | --- |
| compute_norm_stats.py | Manually compute state/actions normalization stats, write out norm_stats.json |
| train_jax.py | **JAX backend training (mainline)**, requires --norm-stats |
| inference_server.py | Load checkpoint (JAX `params/`) and start an HTTP inference service |
| inference_post.py | POST endpoint handler logic for inference_server.py (msgpack unpack → inference → pack) |
| inference_server_bigym.py | BiGym evaluation adapter: adapts the `/process_frame` protocol (the evaluation side connects to the real policy without code changes) |
| prefetch_base.py | ROCm helper: anonymously prefetch pi05_base from GCS to the local cache, avoiding download failures in train_jax.py |
| run_train_loop.sh | ROCm helper: training auto `--resume` continuation, sidestepping sporadic gemm-fusion segfaults on gfx1100/jax0.6.0 |
| gpu_poll.py | ROCm helper: background sampling of `rocm-smi`, logging VRAM/GPU usage |

Each script is independent and self-contained with its own argparse, relying on no shared modules: command-line arguments directly construct openpi's `TrainConfig` within the script (no `config.py` registration, no dataclass). Training and inference each construct the same `Pi0Config` (camera order and action dimension must match), otherwise the inputs won't align.

## Feature 1: Arbitrary number of cameras

### Principle

π05's network architecture is agnostic to the number of cameras: vision is encoded image-by-image by a shared SigLIP encoder and then concatenated, positional encoding (RoPE) is generated dynamically by sequence length, and there are no learned parameters tied to camera count. Changing the number of cameras does not change any weight shape, so the base checkpoint can be loaded directly to continue fine-tuning.

The previous hardcoding of 3 cameras (`base_0_rgb / left_wrist_0_rgb / right_wrist_0_rgb`) was merely hardcoded in the data/preprocessing layer. This repo removes that hardcoding: the model layer handles the actually-passed camera set, and camera identity depends only on **input order**.

### Usage: declaring cameras on the command line

Cameras are declared entirely via three parameters, corresponding to the underlying `CameraSpec(name, source, is_wrist)`:

- `--camera-names`: model-side camera keys, freely named, 1–8 allowed. The order of the entire list is the order of the model's image-tokens.
- `--camera-sources`: flattened key paths in the LeRobot dataset, one-to-one with `--camera-names`, in the same order.
- `--wrist-names`: a subset of `--camera-names`; cameras in this set skip geometric augmentation (RandomCrop/Rotate) during training, to avoid breaking wrist grasp reference points.

These three parameters have exactly the same meaning in `train_jax.py` and `inference_server.py`, ensuring training and inference use the same camera declaration. `compute_norm_stats.py` needs no camera parameters — it only reads the state/action columns of the parquet to compute stats.

### Key constraints

- **Camera order must be consistent between training and inference**. Camera identity depends solely on input order; there are no parameters learned by camera name. Renaming cameras is harmless; swapping the order is harmful.
- **Wrist cameras are declared via `--wrist-names`, not by name**. The old logic decided augmentation by "whether the name contains wrist"; under free naming this has been changed to explicit declaration.
- Missing cameras are zero-filled and masked out (pi05), so when using ≤3 cameras there is no need to change model constants — just reuse the existing mask fill mechanism.

### Inference input contract

The inference client must send an `images` dictionary keyed by camera name, with (H,W,3) uint8 images as values:

```python
from openpi.policies.multi_camera_policy import make_multi_camera_example
example = make_multi_camera_example(("high", "l_wrist", "r_wrist"))
# example = {"images": {name: (224,224,3) uint8, ...}, "state": ..., "prompt": "..."}
action = policy.infer(example)["actions"]
```

## Arbitrary action dimension (robot configuration adaptation)

pi05_base is trained with 32-dim actions (official openpi comment: "pi05 is trained with 32-dim actions"). Different robots have different action dimensions (BiGym uses 16, etc.); openpi's adaptation is: **the model's action projection stays at 32-dim to match the base, the data-side action is zero-padded to 32, and the inference output is sliced back to the robot's true dimension**.

Two parameters control this separately:

| Parameter | Meaning |
| --- | --- |
| --action-dim | The robot's true action dimension (dataset/inference dimension), e.g. 16 for BiGym |
| --model-action-dim | The action dimension of the base checkpoint, default 32 (pi05_base). The model's action_in_proj/out_proj uses this dimension and must match the base, otherwise a shape mismatch is reported on load |

Data flow: during training, PadStatesAndActions zero-pads the action to --model-action-dim (32) to match the base; normalization is performed on the original dimensions before padding (so norm_stats are computed at the robot's true dimension). During inference, MultiCameraOutputs slices the 32-dim output back to --action-dim, and the client directly receives the robot-dimension action.

In most cases just pass `--action-dim <robot dimension>` and leave `--model-action-dim` at the default 32. You only need to specify it explicitly when switching to a base with a different action_dim.

## Feature 2: One-click training + HTTP inference

The dataset is pointed at a local LeRobot Dataset v3.0 directory (containing `meta/`, `data/`, `videos/`) via `--data-dir`, for example:

```
~/BiGym_Dev/data/bigym_plus/cupboards_close_all/
├── data/
│   └── chunk-000/
├── images/
│   ├── observation.images.cam_high/
│   ├── observation.images.cam_left_wrist/
│   └── observation.images.cam_right_wrist/
├── meta/
│   ├── episodes/
│   ├── info.json
│   ├── stats.json
│   └── tasks.parquet
├── videos/
│   ├── observation.images.cam_high/
│   ├── observation.images.cam_left_wrist/
│   └── observation.images.cam_right_wrist/
└── progress.json
```

Below, a unified example walks through the entire flow: BiGym's 3-camera dataset `cupboards_close_all` (`cam_high` plus left and right wrist cameras), action dimension 16. First compute normalization stats, then train, and finally start the inference service.

### Step 1: Compute normalization stats (one-time, manual)

```bash
python3 compute_norm_stats.py \
    --data-dir ~/BiGym_Dev/data/bigym_plus/cupboards_close_all \
    --output-dir ./assets/cupboards_close_all
```

`compute_norm_stats.py` is a self-contained script that needs only `--data-dir` (a local LeRobot v3.0 directory) and `--output-dir`: it reads the state/action columns of the parquet via the lerobot interface (without decoding video) and computes mean/std/q01/q99 across the full table frame-by-frame. `--state-source` (default `observation.state`) and `--action-source` (default `action`) can be overridden when dataset column names differ.

Output is `./assets/cupboards_close_all/norm_stats.json`. Must be recomputed when the dataset changes.

### Step 2: Training

> **AMD gfx1100 single GPU**: running pi05 **requires `--lora`** (full fine-tune doesn't fit on a single card); the stable config is `--lora --batch-size 4 --num-workers 0` (the prefix `XLA_PYTHON_CLIENT_MEM_FRACTION=0.9` is already in the example). **action-horizon must be consistent across training/inference/evaluation**: the demo weights delivered in this repo and the BiGym evaluation both use **horizon 20**, so the example uses 20 (h20 training occasionally segfaults on gfx1100; set `XLA_FLAGS=--xla_gpu_autotune_level=1`; inference must **not** set this flag, otherwise output is all NaN). For VRAM/GPU usage, OOM troubleshooting and resumption see [docs/amd_rocm_jax.md](docs/amd_rocm_jax.md) §Performance and [docs/amd_rocm_bigym_eval.md](docs/amd_rocm_bigym_eval.md) §5.

Fine-tune from the official JAX base model, weights loaded via `--base-checkpoint`:

```bash
XLA_PYTHON_CLIENT_MEM_FRACTION=0.9 python3 train_jax.py \
    --action-dim 16 --action-horizon 20 \
    --camera-names high l_wrist r_wrist \
    --camera-sources observation.images.cam_high observation.images.cam_left_wrist observation.images.cam_right_wrist \
    --wrist-names l_wrist r_wrist \
    --data-dir ~/BiGym_Dev/data/bigym_plus/cupboards_close_all \
    --exp-name run1 --norm-stats ./assets/cupboards_close_all \
    --base-checkpoint gs://openpi-assets/checkpoints/pi05_base \
    --lora --batch-size 4 --num-workers 0 \
    --num-train-steps 20000 --overwrite
```

The checkpoint is saved to `checkpoints/<config_name>/<exp_name>/`, where `<config_name>` defaults to the last segment of `--data-dir`'s directory name (overridable with `--config-name`). The example above is therefore `checkpoints/cupboards_close_all/run1/`. When training `--num-train-steps 20000`, the final checkpoint lands in the **19999** step directory (step number counts from 0), so for inference use `--checkpoint-dir checkpoints/cupboards_close_all/run1/19999`.

Common training parameters (all overridable via the command line):

| Parameter | Default | Meaning |
| --- | --- | --- |
| --num-train-steps | 30000 | Total training steps |
| --batch-size | 32 | Global batch |
| --save-interval | 1000 | Save checkpoint every N steps |
| --log-interval | 100 | Print metrics every N steps |
| --peak-lr | 2.5e-5 | Cosine annealing peak learning rate |
| --warmup-steps | 1000 | Learning rate warmup steps |
| --decay-steps | 30000 | Cosine annealing decay steps |
| --weight-decay | 1e-10 | AdamW weight decay |
| --grad-clip | 1.0 | Gradient clip norm |
| --fsdp-devices | 1 | Number of JAX FSDP sharding devices |
| --overwrite | False | Overwrite existing checkpoint directory |
| --resume | False | Resume training from the latest checkpoint |
| --no-wandb | enabled | Disable wandb logging |

For the full parameter list see `python3 train_jax.py --help`.

### Step 3: HTTP inference service

Demo weights (pre-trained pi05 LoRA, horizon 20, directly downloadable for inference / BiGym evaluation): https://huggingface.co/WuChao-Cauchy/AMD_OpenSource_dishwasher_unload_cutlery_long_pi05_lora

`inference_server.py` loads the checkpoint and starts an HTTP service; the backend (JAX's `params/` or PyTorch's `model.safetensors`) is auto-detected from the checkpoint directory, and the command-line usage is identical for both backends. Weights and norm_stats are both loaded from `--checkpoint-dir`.

```bash
python3 inference_server.py \
    --action-dim 16 --action-horizon 20 \
    --camera-names high l_wrist r_wrist \
    --camera-sources observation.images.cam_high observation.images.cam_left_wrist observation.images.cam_right_wrist \
    --wrist-names l_wrist r_wrist \
    --data-dir ~/BiGym_Dev/data/bigym_plus/cupboards_close_all \
    --checkpoint-dir checkpoints/cupboards_close_all/run1/19999 \
    --host 0.0.0.0 --port 8000
```

Endpoints:

- `POST /infer`: body is a msgpack-encoded observation dictionary; returns a msgpack-encoded action dictionary.
- `GET /healthz`: liveness probe.
- `GET /metadata`: policy metadata JSON.

Client call (images must use msgpack, not JSON):

```python
import requests
from openpi_client import msgpack_numpy as mn
from openpi.policies.multi_camera_policy import make_multi_camera_example

obs = make_multi_camera_example(("high", "l_wrist", "r_wrist"))
resp = requests.post(
    "http://<host>:8000/infer",
    data=mn.packb(obs),
    headers={"Content-Type": "application/msgpack"},
)
action = mn.unpackb(resp.content)
```

> The BiGym closed-loop evaluation (with 3DGS room shell) uses the `/process_frame` protocol of `inference_server_bigym.py` + a two-process evaluation client; full steps and performance benchmarks are in [docs/amd_rocm_bigym_eval.md](docs/amd_rocm_bigym_eval.md).

## Weight format

Training in this repo (`train_jax.py`) produces JAX weights (Orbax directory tree):

| Content | Description |
| --- | --- |
| `<ckpt>/params/` | Orbax weight directory tree |
| `<ckpt>/assets/<asset_id>/norm_stats` | Normalization stats (same as during training) |

During inference, `inference_server.py` loads `params/` and norm_stats from `--checkpoint-dir`. (`inference_server.py` still retains a compatibility check for `model.safetensors` internally, but this repo no longer provides training / conversion scripts that produce that PyTorch format.)

## Data: LeRobot Dataset v3.0

Training data uses the LeRobot Dataset v3.0 format (lerobot>=0.6.0). The entry scripts in this repo use `--data-dir` to point directly at a local dataset directory (containing `meta/`, `data/`, `videos/`); lerobot uses that directory as `root` and loads directly from disk, fully offline, without accessing the Hugging Face Hub. The dataset is always located by this local path throughout the pipeline, independent of the network.

BiGym training/evaluation data is produced by the recording/replay generation tools of [bigym_plus](https://github.com/WuChao-2024/bigym_plus), written directly to disk in the v3.0 directory structure above, with no extra conversion needed. Existing v2.1 datasets can be upgraded with the official conversion tool:

```bash
python -m lerobot.scripts.convert_dataset_v21_to_v30 --repo-id <org>/<dataset>
```

For normalization stats computation and field meanings see [docs/norm_stats.md](docs/norm_stats.md).
