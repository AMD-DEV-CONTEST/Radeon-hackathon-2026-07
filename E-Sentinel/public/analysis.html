2. my-app：FeishuFlow → FeishuFlow Pro 演进

2.1 架构变化

大改动前 · FeishuFlow
  • 单一线性派发流程
  • 飞书事件即时处理，无持久化
  • 指派人提取失败时无兜底
  • 通知文案硬编码在组件中
  • 无可视化 Pipeline 状态
大改动后 · FeishuFlow Pro 升级
  • 8 状态 Pipeline 状态机 — 严格的状态转换校验
  • 事件总线三重保障 — 持久化 + 幂等 + 死信恢复
  • HITL 人工介入 — 低置信度自动挂起等人工确认
  • 模板引擎 — {{var}} 变量替换 + Zod 边界约束
  • 监控面板 — 30s 自动刷新 + 死信队列管理

2.2 状态机 + 事件总线 — 可靠性的质变

问题：改版前的飞书事件处理是"即用即弃"模式——收到事件 → 处理 → 返回。如果处理中途崩溃，事件永久丢失。

旧流程： 飞书回调 → 内存处理 → ⚠ 崩溃则丢失
新流程： 飞书回调 → 持久化写入 DB → 幂等去重 → 处理业务 → 返回 200 未处理 → 死信队列
机制大改动前大改动后
事件持久化无，内存处理feishu_raw_events 表，ON CONFLICT 去重
状态管理无显式状态9 状态 + validateTransition() 严格校验
超时处理无SUSPENDED_ASR(5min) / SUSPENDED_HITL(30min)
重试机制无FAILED → PENDING 可重试，ASR 最多 3 次
死信恢复无GET /api/pipeline/dead-letter + POST 重试

2.3 HITL 人工介入 — 从自动化到人机协同

问题：AI 提取指派人时可能出现歧义（如"老赵"匹配到 3 个候选人），之前只能随机选一个或直接失败。

LLM 提取 → 置信度 < 100%? → SUSPENDED_HITL → 飞书卡片候选人列表 → 用户点击选择 → PROCESSING 继续

关键实现：dispatch/route.ts 中 buildHitlCandidateCard() 构建飞书交互卡片，card-action/route.ts 处理 hitl_select 动作， pipeline 从 SUSPENDED_HITL 恢复到 PROCESSING。30 分钟超时后由 pg_cron 自动标记失败。

  • 单页面质检面板（AI 评分 + 飞书派发）

3.3 数据闭环 — 从发现问题到修复验证

大改动前：质检发现问题 → 飞书通知 → 到此为止。

大改动后：

质检发现违规 → LLM 聚类分析 → 生成优化任务 → 更新话术/知识库 → 复检验证 闭环！

核心引擎：src/lib/pipeline.ts — triggerTaskPipeline() 在任意分析完成后自动调用 optimization-tasks/auto-generate， 将聚类结果转化为可追踪的优化任务，并记录审计日志。

🔑 关键结论
my-app 的质变方向：深度

从"能跑"到"可靠"。核心解决 流程不丢数据 的问题——状态机确保状态转换合法， 事件总线三重保障确保飞书回调永不丢失，HITL 让机器在不确定时优雅地请求人类帮助。

qa-system 的质变方向：广度

从"单点质检"到"全链路运营"。核心解决 运营职责全覆盖 的问题——8 个面板、10 个 LLM 功能、 6 层工程保障，让一个 AI 平台覆盖电商客服机器人运营的完整工作流。
