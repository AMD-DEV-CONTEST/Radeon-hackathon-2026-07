# KlintCode TUI 人机交互设计

## 1. 文档目的

本文档定义 KlintCode 交互式 TUI 的产品与交互基线。设计参考了
OpenCode 等 Coding Agent 的优点，但针对 KlintCode 的特点做了调整：

- 完全离线、面向隔离网络环境；
- 使用 64K–128K 上下文窗口的本地模型；
- 64K 模型最多使用 48K Token 作为输入上下文；
- 通过 TeaQL、编译器和多级验证保证生成结果；
- 对框架、命令、文件和 TeaQL 写法执行不可绕过的内置规则。

TUI 应持续、明确地回答用户以下问题：

1. 当前任务的目标是什么？
2. Agent 现在执行到计划的哪一步？
3. Agent 此刻正在做什么，或者正在等待谁？
4. Agent 当前携带了哪些上下文？
5. 本轮、当前任务和整个会话分别消耗了多少 Token？
6. 哪些结果已经通过验证，哪些仍然存在风险？

## 2. 设计原则

### 2.1 状态必须显式

不能用同一个 Spinner 表达“思考中”“执行命令”“等待用户”和“自动修复”。
每个状态都必须有固定名称、图标和颜色，并且即使终端不支持颜色，也能通过
文字正确理解。

### 2.2 计划是一级对象

计划不是聊天记录中的一段 Markdown。计划应拥有独立的数据结构、状态和视图，
并与消息、工具调用、文件变更、验证结果和 Token 使用量关联。

### 2.3 上下文必须透明

用户应当知道请求包含哪些上下文，并能管理可移除内容。Token 数字只采用模型
服务已经报告的 Usage，不展示本地分项估算。

### 2.4 验证过程可见

KlintCode 的核心价值是确定性验证。L1–L8 的执行状态、失败原因、修复次数和最终
结论不能隐藏在日志中。

### 2.5 复杂内容结构化渲染

表格、Chart、Diff、日志、计划和验证结果由结构化数据驱动，不允许模型直接生成
终端控制字符模拟 GUI。

### 2.6 危险操作执行前拦截

框架限制、TeaQL 规则、工作区边界和命令权限必须在工具执行或文件落盘前检查。
最终输出还需要再次检查，防止流式生成或跨步骤操作绕过规则。

## 3. 主界面

默认主界面采用内容流优先的极简布局。统计组件不常驻，不使用边框切割整个画面：

```text
 KlintCode  coding agent                              ┌───────────────┐
 local-model · /workspace                            │ ● GENERATING  │
                                                     │ Plan 2/6      │
 ❯ 用户消息                                          │ 生成领域模型  │
                                                     └───────────────┘
 ● Agent 回复
 ⎿ 工具与验证活动

────────────────────────────────────────────────────────────────────
  █ 描述你希望 coding agent 完成的任务……
────────────────────────────────────────────────────────────────────
  Enter 发送 · Shift+Enter 换行 · /stats 统计 · ? shortcuts
```

输入区只有上下两根横线，不绘制左右边框。内容与终端边缘至少保留一格内边距，
高亮实心块光标在输入位置闪烁。输入区默认显示一行；每次显式换行增加一行，
最多显示八行。超过八行后继续接受输入，视窗只显示最后八行。

进程型 Tool Use 紧贴输入区下方显示，不额外绘制边框，只显示仍在运行的命令，
最多占用三行。进程结束后立即从输入区下方移除，并在主对话流中追加一条成功或
失败记录，不显示退出码。完整 Tool 调用历史保留在 `/stats` 的
`Tool History` 单元中。命令必须在进程启动前写入状态流，结束后原位更新，
耗时进程不得阻塞 TUI 的绘制、输入或光标闪烁。

右上角状态卡适当加宽，只显示计划步骤，不显示 `IDLE`、`GENERATING`、
`VALIDATING` 或 `COMPLETED` 等 Pipeline 状态文字。计划步骤统一收敛为三种
视觉状态：`○` 未执行、明暗呼吸的 `●` 正在执行、`✓` 已完成。等待用户的当前
步骤仍映射为正在执行；失败、阻塞、跳过和取消的步骤在这个轻量区域中映射为
未执行，详细原因留在主对话和 Stats 诊断中。状态卡仅绘制带标题的顶部横线，
不绘制底部横线。高度随计划步骤数量增长并设置上限；窄屏时移动到内容流上方。

计划、Validation、Context 和 Token 统一放入独立统计界面，通过 `/stats`
打开，通过 `/main` 返回。发送普通任务和切换画面使用同一个命令输入区。

交互输入必须在创建 Run 之前完成路由：

- 模型名称、Endpoint 和服务健康状态从本地配置直接回答；
- 普通问题使用轻量 Klint 问答，不创建计划、Artifact 或 TeaQL 验证任务；
- 只有带明确执行动作的开发请求进入完整计划和验证流水线；
- `/task <request>` 强制进入任务流水线，`/ask <question>` 强制进入轻量问答。

轻量问答时主界面不继续展示上一个任务的计划；历史计划、验证和 Tool 信息仍可
通过 `/stats` 查看。

Stats 页面沿用主界面的轻量视觉语言：组件之间只画横向分隔线，不画左右边框
或贯穿页面的竖线。宽屏双栏之间保留三格空白沟槽，以留白形成竖向分区。

主界面由以下区域组成：

| 区域 | 内容 |
|---|---|
| 对话与执行流 | 消息、工具调用、文件修改、验证和修复记录 |
| 紧凑状态卡 | 右上角显示状态、计划进度、当前动作和后端 |
| 输入区 | Prompt、文件引用、命令补全和待发送附件 |
| Tool 运行流 | 输入区下方最多三行，只显示仍在运行的进程命令 |
| 底部提示 | 发送、换行、Slash 命令和快捷键提示 |
| Stats 界面 | Plan、Validation、Context、Token 和诊断详情 |

主对话不得直接铺开长代码、XML 或 Tool 输出。模型生成候选结果后只显示总行数和
最多六行预览，剩余内容通过 `/candidate` 查看。任务开始后将三行 FLINT 标识、
Slogan 和署名收敛为单行紧凑头部，为执行记录释放垂直空间；endpoint 保持暗灰
元数据样式，只有健康检查结果使用成功或失败色。

主对话默认锚定最新事件。导航模式下使用 `k` 向上浏览、`j` 回到更新内容；
离开最新位置后在右下显示“回到最新”和向上行数。新的模型输出、验证结果和
Artifact 事件在用户位于底部时自动保持可见。最终完成事件在主对话中使用绿色
`✓ 任务完成 · Artifact <path>`，不在右上计划区重复显示终态文字。

## 4. Agent 状态模型

建议至少定义以下用户可见状态：

| 状态 | 建议图标 | 含义 |
|---|---:|---|
| `IDLE` | `○` | 可以输入新任务 |
| `PLANNING` | `●` | 正在制定或调整计划 |
| `GENERATING` | `●` | 模型正在生成内容 |
| `RUNNING_TOOL` | `●` | 正在运行本地工具 |
| `VALIDATING` | `●` | 正在执行 TeaQL、编译或规则验证 |
| `REPAIRING` | `↻` | 验证失败后正在自动修复 |
| `WAITING_USER` | `◆` | 任务暂停，等待用户输入 |
| `BLOCKED` | `■` | 因规则、环境或连续失败无法继续 |
| `COMPLETED` | `✓` | 任务和必要验证均已完成 |
| `FAILED` | `✗` | 任务失败且未能恢复 |
| `CANCELLED` | `–` | 用户取消 |

状态卡使用具体动作，不使用模糊的 `Thinking...`：

```text
RUNNING_TOOL · 正在运行 cargo check · 计划 4/6
VALIDATING · L6 Assist Discovery · 计划 4/6
REPAIRING · 编译修复 1/3 · 计划 5/6
```

执行过程中输入新消息时，用户应明确选择：

- **立即打断**：取消当前可取消步骤，处理新要求；
- **加入队列**：当前步骤结束后处理。

## 5. 计划与任务导航

### 5.1 计划结构

复杂计划最多使用三层：

```text
任务目标
 ├─ 阶段
 │   ├─ 步骤
 │   └─ 步骤
 └─ 阶段
     └─ 步骤
```

计划描述用户可理解的目标和结果。读取文件、执行一次搜索等工具调用属于执行记录，
不应全部提升为计划步骤。

### 5.2 步骤状态

每个步骤支持：

- `Pending`
- `InProgress`
- `WaitingUser`
- `Blocked`
- `Completed`
- `Skipped`
- `Cancelled`

当前步骤应显示具体动作、已生成 Artifact、耗时和风险：

```text
● 4. 生成业务代码
  当前：依据 assist 输出实现 Order 查询
  已修改：2 个文件
  已用时：1m 42s
  风险：尚未执行最终 cargo check
```

即使 Stats 界面关闭，右上状态卡仍显示：

```text
计划 4/6 · 依据 Assist 输出生成业务代码
```

### 5.3 计划与执行记录关联

点击计划步骤应能查看或定位以下关联信息：

- 原始用户要求；
- Agent 的分析和关键决策；
- 工具调用；
- 文件修改；
- 验证结果；
- Artifact；
- Token 使用量。

对话中的工具卡片也应标记所属步骤：

```text
● cargo check · 计划步骤 5/6
```

### 5.4 计划变更

Agent 不应静默改变方向。重大调整需要展示计划 Diff 和原因：

```text
计划需要调整

原因：L3 领域验证表明原模型缺少 OrderItem 关联。

原计划：
3. 生成 Rust Core

建议：
3. 补充领域关联
4. 重新执行 L3 验证
5. 生成 Rust Core

[接受调整] [继续原计划] [编辑计划]
```

小范围调整可以自动执行，但必须留下“计划已更新”记录。

### 5.5 会话恢复

恢复旧会话时优先展示任务检查点，而不是要求用户阅读完整聊天历史：

```text
继续上次任务

目标：生成可编译的学校服务
进度：5/8
当前步骤：L6 Assist Discovery

已经完成：
- KSML 生成
- 领域语义验证
- rust-lib-core 生成
- 第一次 cargo check

待处理：
- 依据真实 API 生成业务逻辑
- 最终 cargo check

[继续执行] [查看计划] [重新规划]
```

## 6. 上下文与 Token

### 6.1 常驻 Context Meter

状态栏不展示发送前估算值。模型调用完成并返回 Usage 后，才显示最近一次
调用的实际输入 Token：

```text
发送前      Context reported after response
生成中      Context waiting for model usage
完成后      Context 31.8K / 48K · 66% · reported
```

Context Builder 仍在内部执行预算估算和超限拒绝，但该估算不得进入用户可见
Token 指标。

对于 64K 模型：

- 48K：系统 Prompt、规则、历史、引用文件和工具输出的可用输入预算；
- 8K：内部安全预留；
- 8K：输出预留。

建议阈值：

| 占用 | 状态 |
|---:|---|
| 0–60% | 正常 |
| 60–80% | 提醒 |
| 80–90% | 警告 |
| 90%以上 | 高风险，建议压缩或清理 |

### 6.2 上下文详情

点击 Context Meter 后展示模型已经报告的总量和本次请求包含的来源。除非模型
服务提供分项 Usage，否则不展示各来源的估算 Token：

```text
最近一次模型报告                     31,820 / 48,000

包含：系统 Prompt、组织规则、AGENTS.md、会话历史、
      用户引用文件、TeaQL Assist、工具输出、当前输入

各来源 Token                         Provider 未报告

[管理上下文] [立即压缩] [查看详情]
```

每个来源标记其生命周期：

- `Pinned`：不可自动裁剪；
- `Temporary`：仅当前请求使用；
- `History`：来自历史消息；
- `Summary`：已经压缩为摘要；
- `Prunable`：空间不足时可以清理；
- `Cached`：Provider 报告命中 Prompt Cache。

用户可以移除引用文件、清理大体积工具输出、固定重要规则或将旧消息压缩为摘要。
压缩后必须留下可查看的检查点。

### 6.3 Token 统计口径

必须区分 Context 与累计 Token：

```text
Context 31.8K/48K · ↑84K ↓7.2K
```

- `Context`：最近一次已完成模型请求报告的实际输入 Token；
- `↑`：当前会话累计输入 Token；
- `↓`：当前会话累计输出 Token。

没有模型 Usage 时，上述三个指标统一显示未知，不回退到本地估算。

详细视图按三个层级统计：

```text
最近一次模型调用
输入 Token              18,420
缓存输入                12,600
输出 Token               2,140
推理 Token               1,280
耗时                     18.4s

当前用户任务
输入 Token              42,810
输出 Token               5,320
模型调用                     4

整个会话
输入 Token              84,200
输出 Token               7,240
模型调用                    11
```

如果模型服务没有返回缓存或推理 Token，不应伪造数据，应显示 `N/A` 或隐藏该指标。

## 7. 等待用户输入

`WAITING_USER` 是一个阻塞状态，优先级高于普通执行状态。使用固定信号：

```text
◆ 等待你的回复
```

设计要求：

- 使用琥珀色或黄色，但不能只依赖颜色；
- 停止所有运行中的 Spinner；
- 自动滚动到待回复卡片；
- 输入框自动获得焦点；
- 问题固定在输入框上方，不能被日志淹没；
- 状态栏持续显示具体需要用户完成的事情；
- 计划步骤同步变为 `WaitingUser`。

示例：

```text
┌ ◆ 需要你的决定 ────────────────────────────────────────┐
│ 检测到现有代码使用了项目规则禁止的框架。               │
│                                                        │
│ [按允许框架重写] [停止任务] [查看冲突]                 │
└────────────────────────────────────────────────────────┘

◆ 等待你选择处理方式 · 计划 3/6 · 任务已暂停
```

根据实际原因使用具体文案：

- 等待你的确认；
- 等待你选择方案；
- 等待你补充信息；
- 等待操作授权；
- 等待登录完成；
- 等待你解决冲突。

终端不在前台时，可选触发一次 Terminal Bell。未来桌面客户端可以增加系统通知和
任务栏角标，但同一个等待节点只能通知一次。

## 8. 工具、文件修改与验证

### 8.1 工具卡片

```text
● Bash · 计划 5/6
  cargo check

  Exit code: 1 · 12.4s
  3 errors

  [查看输出] [重新运行] [查看 Artifact]
```

文件修改：

```text
● 修改 3 个文件
  src/order.rs          +18 -7
  src/service.rs        +12 -3
  tests/order_test.rs   +24 -0

  [查看 Diff] [接受] [撤销]
```

危险操作：

```text
◆ Agent 请求运行
  cargo teaql --input school-service rust-lib-core

原因：生成 TeaQL runtime code
影响：将在工作区生成受保护目录

[允许一次] [本任务允许] [拒绝]
```

### 8.2 KlintCode 验证流水线

L1–L8 应作为专用 Progress/Timeline 组件呈现：

```text
验证流水线

✓ L1 XML well-formedness          0.1s
✓ L2 Schema conformance           0.2s
✓ L3 TeaQL domain validation      1.0s
✓ L4 rust-lib-core generation     6.2s
✓ L5 cargo check                 22.1s
● L6 Assist discovery            5/8 objects
○ L7 Business logic
○ L8 Final cargo check
```

自动修复不能覆盖失败历史：

```text
↻ L5 cargo check · 修复 1/3
  原因：Order::customer() 方法不存在
  动作：读取 Order assist 输出后重新生成
```

完成状态只有在必要验证全部通过后才能显示。仅生成了代码时，应使用
“生成完成，等待验证”，而不是 `COMPLETED`。

## 9. Rich Block 组件系统

### 9.1 组件外壳

所有复杂组件使用统一结构：

```text
┌ Benchmark 对比 ───────────── Chart · 计划 6/8 ┐
│                                               │
│ 组件内容                                      │
│                                               │
├───────────────────────────────────────────────┤
│ V 表格视图 · E 展开 · C 复制 · X 导出         │
└───────────────────────────────────────────────┘
```

统一元数据：

- ID 和类型；
- 标题；
- 数据来源；
- 所属计划步骤；
- 更新时间；
- 展开/折叠状态；
- 可用操作；
- 纯文本降级内容。

### 9.2 首批组件

| 组件 | 适用内容 |
|---|---|
| `Table` | Benchmark、模型对比、文件和错误列表 |
| `Chart` | 性能、Token、耗时和上下文趋势 |
| `Metrics` | KPI、通过率和资源占用 |
| `Progress` | 计划和 L1–L8 流水线 |
| `Diff` | 文件修改 |
| `Log` | Shell、编译和验证输出 |
| `Tree` | 文件、调用关系和计划层级 |
| `Timeline` | 执行历史、修复和计划变更 |
| `Alert` | 错误、警告和等待用户 |
| `Form` | 审批、问题和方案选择 |

### 9.3 Table

```text
Model             TTFT       TPS      VRAM      Status
Llama-70B         820ms      42.1     76GB      ✓
Qwen-72B          940ms      38.7     81GB      ✓
DeepSeek          1.2s       51.4     92GB      !
```

支持排序、过滤、滚动、固定关键列、单位格式化和 CSV/JSON 导出。窄屏自动转换为
Key-Value 卡片。

### 9.4 Chart

终端优先支持：

- 水平条形图；
- 折线图；
- Sparkline；
- 直方图；
- Heatmap；
- 散点图；
- 堆叠条形图。

不优先实现饼图。

```text
Tokens by plan step

分析需求       ████████████████  18.4K
生成领域模型   ██████             6.8K
验证与修复     █████████████      14.2K
生成业务代码   █████████          10.1K
```

Chart 必须可以切换为 Table，以便查看精确数据和兼容低能力终端。

### 9.5 焦点与快捷键

复杂组件获得焦点时必须使用明显边框和 `FOCUSED` 标记。建议统一操作：

| 按键 | 操作 |
|---|---|
| 方向键 | 移动行、列或数据点 |
| `Enter` | 查看详情 |
| `V` | Chart/Table 切换 |
| `E` | 展开或全屏 |
| `C` | 复制数据 |
| `X` | 导出 |
| `Esc` | 返回输入框 |

终端降级顺序：

```text
交互 Chart → 静态 Unicode Chart → Table → Key-Value 文本
```

需考虑无颜色终端、ASCII 模式、SSH 高延迟、中文字符宽度和 Screen Reader。

### 9.6 结构化协议

模型和工具只生成结构化描述，TUI 负责渲染：

```json
{
  "type": "chart",
  "id": "benchmark-tps",
  "title": "TPS Comparison",
  "chart": "bar",
  "labels": ["Llama", "Qwen", "DeepSeek"],
  "series": [
    {
      "name": "TPS",
      "values": [42.1, 38.7, 51.4],
      "unit": "tok/s"
    }
  ],
  "fallback": "table"
}
```

渲染层负责 Schema 校验、尺寸计算、字符选择、颜色、焦点、降级和导出。任何字符串
中的终端 Escape Sequence 都必须清理。

## 10. 内置规则与自动召回

### 10.1 规则检查位置

规则引擎覆盖完整链路：

```text
用户输入
  → 输入规则
  → 模型生成/流式规则
  → 输出规则
  → 工具参数规则
  → 文件 Diff 规则
  → TeaQL/编译验证
  → 最终交付
```

不能只检查最终回复。安装被禁止依赖、修改生成目录等行为必须在工具执行前阻止。

### 10.2 KlintCode 强制规则

至少内置以下不可绕过规则：

- 输入上下文不超过 48K 可用预算；
- 编写 TeaQL 业务代码前必须读取本地 `AGENTS.md` 和对象 Assist 输出；
- 禁止编辑 `rust-lib-core/`、`java-lib-core/`、`java-web-spring-boot/` 和
  `bizcore/` 下的生成文件；
- `execute_for_list()` 或 `execute()` 前必须有 `.purpose("why")` 和
  `.comment("what")`；
- `.save()` 或 `.update()` 前必须有 `.audit_as("description")`；
- Rust TeaQL 操作必须使用 `cargo teaql --input <model> <command>`；
- `cargo-teaql` 版本必须严格为 `2.0.8`；
- 项目或组织配置中声明的禁用框架、依赖和命令；
- 禁止终端控制字符、零宽字符和其他配置的特征字符。

框架规则同时检查：

- Package manifest；
- Import/Require；
- 配置文件；
- 新增依赖命令；
- 生成的脚手架；
- 文件 Diff。

特征字符匹配前执行 Unicode NFKC 归一化，并区分普通文本、代码块、工具参数和
文件内容，减少误报。

### 10.3 规则动作

每条规则声明以下动作之一：

- `Warn`：允许继续，显示警告；
- `Sanitize`：自动清理字符或格式；
- `Block`：阻止输出或工具执行；
- `Regenerate`：撤回本次候选内容并自动重新生成；
- `Ask`：转为 `WAITING_USER`；
- `Abort`：终止任务。

强制规则应包含 ID、严重级别、作用范围、检测器、修复提示、最大重试次数和是否
允许覆盖。

### 10.4 流式拦截与重新生成

涉及禁止展示内容的规则使用小范围流式缓冲：

```text
模型输出 → 安全缓冲 → 增量检查 → 展示已确认内容
```

命中强制规则后：

1. 停止当前生成；
2. 撤回未完成候选消息；
3. 记录规则 ID、位置和证据；
4. 将结构化修正要求加入下一次请求；
5. 自动重新生成；
6. 再执行完整校验。

用户可见反馈：

```text
◆ 输出已被规则拦截

规则：teaql.query-requires-purpose
位置：src/order_service.rs:42
处理：正在补充 purpose/comment 后重新生成
重试：1/2
```

状态栏：

```text
REPAIRING · 规则拦截后重新生成 1/2 · 计划 4/6
```

达到最大重试次数后禁止无限循环，转为 `BLOCKED` 或 `WAITING_USER`：

```text
◆ 无法自动满足强制规则

连续两次命中：禁止编辑 rust-lib-core/

[查看冲突] [修改任务] [停止任务]
```

### 10.5 规则面板

提供 `/rules` 或等价入口：

```text
项目规则                              18 条启用

✓ teaql.generated-files-readonly     强制 · 不可覆盖
✓ teaql.query-requires-purpose       强制 · 不可覆盖
✓ teaql.save-requires-audit          强制 · 不可覆盖
✓ dependencies.denylist              强制 · 组织配置
✓ output.no-control-chars            自动清理

最近命中：
teaql.query-requires-purpose · 计划 4/6 · 已自动修复
```

规则优先级：

```text
系统安全规则
> 组织规则
> 项目规则
> Agent 规则
> 会话临时规则
> 当前用户 Prompt
```

## 11. 建议的内部数据边界

### `crates/agent-core`

- 定义 Agent 顶层状态和状态转换；
- 保存计划、当前步骤、等待原因和消息队列；
- 产生工具、验证、规则命中和 Token 更新事件；
- Reducer 保持纯函数和可测试性。

### `crates/context-builder`

- 内部估算并检查 48K 可用预算，但不作为用户可见 Usage；
- 按来源管理上下文内容；
- 定义 Pinned/Temporary/Prunable 生命周期；
- 产生 Context Snapshot 和压缩建议。

### `crates/model-vllm`

- 接收流式 Usage；
- 区分输入、输出、缓存和推理 Token；
- 在服务端不提供 Usage 时标记未知，不静默估算为精确值。

### `crates/validation`

- 定义规则 Schema 和检测结果；
- 实现文本、工具参数、文件 Diff 和 TeaQL 语义规则；
- 输出稳定的 Rule ID、证据、修复提示和严重级别。

### `crates/pipeline`

- 将 L1–L8 作为结构化阶段事件发布；
- 管理自动修复次数；
- 保存每轮验证输入、输出和 Artifact。

### `crates/artifact-store`

- 保存计划版本、规则命中、验证报告、Chart/Table 原始数据和导出文件；
- 支持从 UI 结果定位到可复现 Artifact。

### `apps/klintcode-tui`

- 只消费结构化状态与事件；
- 实现 Plan、Context、Token、Validation 和 Rich Block Widget；
- 处理焦点、窄屏、自适应布局和终端能力降级；
- 不在 Widget 中实现业务规则。

## 13. 分阶段实现

### 第一阶段：任务可定位

1. Agent 显式状态；
2. 常驻计划步骤；
3. `WAITING_USER` 阻塞信号；
4. L1–L8 验证 Progress；
5. 工具和文件 Diff 卡片；
6. 停止、立即打断和消息队列。

### 第二阶段：资源透明

1. Context Meter；
2. 按来源拆分上下文；
3. 最近调用、当前任务和会话 Token；
4. 上下文压缩与检查点；
5. 会话恢复摘要。

### 第三阶段：规则与 Rich Block

1. 统一规则协议；
2. 工具执行前和文件 Diff 规则；
3. 流式拦截与自动重新生成；
4. Table、Chart、Tree 和 Timeline；
5. 终端降级、导出和 Artifact 关联。

## 14. 验收标准

核心交互达到以下标准，才可认为 TUI 基线完整：

- 用户无需阅读聊天历史即可知道当前目标、步骤和下一步；
- 等待用户时，界面不再表现为 Agent 运行中；
- 用户可以解释当前 Context 的主要组成和剩余预算；
- Context 与累计输入 Token 不会被混为同一指标；
- 每个工具调用、文件修改和验证结果可以关联到计划步骤；
- 计划改变时留下原因和前后差异；
- L1–L8 失败及自动修复历史可追踪；
- 强制规则在危险工具执行或文件落盘前拦截；
- 自动重新生成达到上限后停止并明确请求用户处理；
- Chart 在不支持 Unicode、颜色或宽度不足时仍能降级为可读文本；
- 所有关键结果都能定位到原始 Artifact。
