1. Project Background

1.1 Problem Statement

AI image generation has become mainstream, yet existing tools fall into two extremes:

  • Node-based tools (e.g., ComfyUI): Powerful but steep learning curve — users must understand checkpoints, VAEs, LoRAs, samplers, and CLIP, then manually wire node graphs. Barrier to entry is high.
  • Text-box generators (e.g., Jimeng, Liblib): Easy to use but lack creative engagement — users type text into a box and receive a packaged result. The creative process feels transactional, not expressive.

Meanwhile, the AI inference ecosystem is heavily dependent on NVIDIA CUDA. Most open-source diffusion tooling assumes CUDA, and AMD Radeon GPU users have limited options despite competitive hardware (e.g., the W7900 with 48 GB VRAM at a fraction of NVIDIA's cost).

1.2 Our Solution

NodeFlow bridges this gap by combining infinite-canvas hand-drawing with diffusion-model generation, running entirely on AMD Radeon GPUs via native ROCm:

  • Users sketch on an infinite Excalidraw canvas — the canvas is the creative space, not a passive upload box.
  • AI transforms sketches into stylized artwork using state-of-the-art diffusion models (SDXL-Lightning, FLUX.2-klein, NoobAI XL, etc.).
  • Dual-mode design covers both rapid prototyping (Fast: 4-step distilled models) and high-fidelity rendering (Expert: full-parameter models with LoRA support).
  • The entire inference pipeline runs natively on ROCm — zero NVIDIA CUDA dependency.

1.3 Why This Matters for AMD

NodeFlow demonstrates that a production-grade AI image generation tool — with multi-model support, LoRA integration, and real-time canvas interaction — can run entirely on AMD Radeon hardware. This validates the ROCm ecosystem for creative AI workloads and showcases the W7900's 48 GB VRAM as a compelling alternative for diffusion model inference.

An illustrator draws a character pose on the canvas. They select "Anime" style with strength 0.8 and click Generate. The AI transforms the rough sketch into a polished anime illustration in ~5 seconds (Fast mode) or ~15 seconds (Expert mode with NoobAI XL).

A content creator types "a serene mountain lake at dawn" and selects "Watercolor." The backend appends a professional watercolor prompt prefix and generates a watercolor-style landscape. The result can be downloaded as PNG.

Scenario C: Multi-Model Comparison

A researcher switches between SDXL-Lightning (4-step, ~2s), FLUX.2-klein (50-step, ~20s), and NoobAI XL (28-step, ~12s) to compare quality vs. speed tradeoffs — all on the same AMD GPU without restarting the service.

Scenario D: LoRA Style Mixing

A designer loads a realistic base model, then attaches an anime-style LoRA at weight 0.7, achieving a "realistic foundation with anime aesthetic" hybrid effect — all controlled via the UI, no node-wiring required.

3.3 Thread Safety & Reliability

  • Generation Lock (_generation_lock): Ensures only one inference task runs at a time, preventing GPU OOM from concurrent requests.
  • Switch Lock (_switch_lock): Prevents concurrent model switches that could corrupt state.
  • Rollback Protection: On model switch failure, the system saves the old adapter + LoRA state, attempts to load the new model, and if it fails, automatically rolls back to the previous working model — the service never gets stuck.
  • VRAM Check: Before loading a new model, checks available VRAM via torch.cuda.mem_get_info(); refuses to load if insufficient.

4.2 Algorithm Details

4.2.1 SDXL-Lightning (Distilled Inference)

SDXL-Lightning uses progressive distillation to reduce the denoising steps from 50 (base SDXL) to 4–8 steps. The implementation loads a base SDXL checkpoint and swaps in the distilled UNet:

# Load base SDXL + distilled UNet
pipe = StableDiffusionXLPipeline.from_pretrained(
    "stabilityai/stable-diffusion-xl-base-1.0",
    torch_dtype=torch.float16
)
pipe.unet.load_state_dict(
    load_file("sdxl_lightning_4step.safetensors"),
    strict=False
)
# Use EulerDiscreteScheduler for distilled models
pipe.scheduler = EulerDiscreteScheduler.from_config(
    pipe.scheduler.config, timestep_spacing="trailing"
)
# 4-step inference: ~2 seconds on W7900
image = pipe(prompt, num_inference_steps=4, guidance_scale=1.5).images[0]
img2img optimization: The img2img pipeline reuses the text2img pipeline's weights via StableDiffusionXLImg2ImgPipeline.from_pipe(pipe), saving ~7 GB VRAM. Image dimensions are aligned to 64-pixel multiples (SDXL requirement).

4.2.2 FLUX.2-klein (Unified Pipeline)

FLUX.2-klein-4B uses a unified pipeline (Flux2KleinPipeline) that handles both text-to-image (no image parameter) and image editing (with image parameter) without a separate strength parameter. Key differences from SDXL:

  • Dimension alignment: 16-pixel multiples (vs. SDXL's 64)
  • Dtype: bfloat16 (vs. SDXL's float16) — ROCm supports BF16 natively on W7900
  • Distilled variant: 4-step with locked parameters for speed
  • Base variant: 20–100 steps with full parameter control

4.2.3 LoRA Integration

NodeFlow implements a three-layer decoupled LoRA system:

  1. Base layer (who draws): User explicitly selects the model architecture (anime / realistic / general). The system does not auto-guess.
  2. Theme layer (how to draw): Selecting a style preset auto-appends a professional prompt prefix and loads the architecture-matched LoRA.
  3. Weight layer: LoRA weights are adjustable (0–2.0), enabling hybrid effects (e.g., "realistic base + anime LoRA at 0.7").

For distilled models (SDXL-Lightning), the system automatically reduces LoRA weights (default_weight × 0.7 for general, × 0.8 for style) to prevent noise artifacts from the distillation process.

5.2 ROCm-Specific Adaptations

5.2.1 PyTorch ROCm Wheel Installation

PyTorch must be installed from the ROCm-specific wheel index — the standard PyPI build does not include ROCm support:

# Install PyTorch with ROCm support (NOT from PyPI)
pip install torch torchvision \
    --index-url https://download.pytorch.org/whl/rocm6.2

5.2.2 GPU Verification

import torch
print(torch.cuda.is_available())          # True (ROCm maps to CUDA API)
print(torch.cuda.get_device_name(0))       # "AMD Radeon Graphics"
print(torch.cuda.get_device_properties(0).total_memory / 1e9)  # ~48.0
Key insight: PyTorch's ROCm backend maps to the torch.cuda API, meaning most CUDA code works unchanged on AMD GPUs. The primary adaptation is the wheel installation — no code-level CUDA→ROCm rewrite is needed for diffusers pipelines.

5.2.3 Memory Optimization

  • Bfloat16 dtype: FLUX.2-klein uses torch.bfloat16, which halves VRAM usage vs. float32. The W7900 natively supports BF16.
  • Weight sharing: Text-to-image and image-to-image pipelines share the same model weights via from_pipe(), avoiding duplicate ~7–8 GB allocations.
  • Model hot-switching with VRAM check: Before loading a new model, torch.cuda.mem_get_info() checks available VRAM. The 48 GB W7900 can hold multiple SDXL models simultaneously (~7 GB each).
  • Model unloading: When switching architectures (e.g., SDXL → FLUX.2), the old model is explicitly unloaded via del + torch.cuda.empty_cache() before loading the new one.

5.2.4 HuggingFace Mirror

The AMD Radeon Cloud instance cannot directly reach huggingface.co. NodeFlow uses the HuggingFace mirror:

export HF_ENDPOINT=https://hf-mirror.com
export HF_HOME=/persistent/hf_cache  # Persistent storage for model cache

5.4 Engineering Lessons

  • Persistent storage is critical: /workspace is ephemeral (wiped on instance reset). Python venv and model cache must live in /persistent/ to survive resets — saving 4 GB+ PyTorch re-download and 12 GB+ model re-download.
  • torch.cuda API works on ROCm: No code changes needed for standard diffusers pipelines. The adaptation is at the installation level (ROCm wheel), not the code level.
  • BF16 is well-supported: The W7900 handles bfloat16 inference natively, making it suitable for FLUX.2-klein which requires BF16.
  • 48 GB VRAM enables multi-model residency: Multiple SDXL models (~7 GB each) can coexist in VRAM, enabling fast hot-switching without reload latency.

6.2 Core Differentiators

  1. AMD / ROCm Native: Truly runs on AMD Radeon PRO W7900 with ROCm inference — not a CUDA port, not a wrapper. Demonstrates the open GPU ecosystem's viability for production AI workloads.
  2. Canvas Interaction = Low Barrier + Creative Feel: Unlike ComfyUI's node complexity or text-box generators' lack of engagement, the canvas provides an intuitive, creative entry point.
  3. Dual-Mode = Speed + Quality: One product covers rapid prototyping (4-step distilled, ~2s) and high-fidelity rendering (50-step full model, ~20s) — no tool switching.
  4. Multi-Model + LoRA = User Control: Style control is in the user's hands, not a black box. Every model and LoRA displays its license and commercial-use status for compliance transparency.
Bottom line: NodeFlow proves that a full-featured, multi-model AI image generation tool — with canvas interaction, LoRA support, and a model store — can run entirely on AMD Radeon hardware via ROCm, without compromising on features or user experience.
