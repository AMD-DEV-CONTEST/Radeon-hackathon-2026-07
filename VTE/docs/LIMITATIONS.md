# Known limitations

What's genuinely unfinished or unresolved right now, grouped by area. Each item links to the document with the full story where one exists.

## Batching and prefill

- `generate_batch` requires every prompt in a batch to have identical token length (lockstep only); padding + attention masking for mixed-length batches is unimplemented.
- Batch sizes above 4 currently regress throughput (see [Performance](PERFORMANCE.md)): not yet root-caused beyond the Infinity Cache hypothesis.
- Persistent activation buffers used by the HIP Graph executor are sized for `seq_len=1` (the dominant decode case); a multi-token prefill through that executor could in principle overrun those buffers. The current code avoids this by processing prefill token-by-token even in HIP Graph mode, reusing the single decode graph, but the buffers themselves aren't yet partitioned by shape class to make this impossible by construction rather than by calling convention.
- `LMHead`'s HIP-Graph capture path assumes the decode graph always runs at `seq_len=1` (true for the current lockstep decode/prefill scheme): a future multi-token-per-step scheme would need the LM Head capture logic revisited alongside it.
- **A 2026-07 investigation cycle built chunked batched prefill end-to-end (flag `VTE_BATCHED_PREFILL`, off by default) and found two consecutive negative results, both root-caused rather than left as "didn't work."** First attempt: dispatch the existing `gemv_q4k`/`gqa_attention` kernels over `batch*seq_len` rows per launch instead of one row at a time, with a dedicated chunk-sized activation buffer set (`_build_chunk_tensor_mapping`) and `kv_cache_offset`-aware attention so chunk boundaries stay correct. Verified byte-identical generated output vs. the sequential path, but measured **0.99x** on `prefill_duration_ttft` (no speedup). Root cause: VTE's GEMV kernels are deliberately architected so weight tiles never touch LDS (each block re-reads weights straight from VRAM); batching more rows into one launch reduces launch count but not total VRAM traffic, and launch/sync overhead was never the bottleneck. Second attempt: a from-scratch double-buffered Q4_K WMMA GEMM kernel (`gemm_q4k_wmma.hip.template`, tiles M=N=K=64, gfx1100's real 64KB LDS/workgroup limit, not the 128KB initially assumed) that does keep weight tiles LDS-resident across rows. Validated correct at three levels (exact-match dequant, <0.25% RMS-relative error on a full GEMM at real prefill shapes, byte-identical end-to-end generated text) and the isolated kernel is genuinely faster than the unfused baseline (1.02ms vs. 1.74ms per 128x4096x4096 GEMM with double-buffering). Initial full end-to-end measurement of `prefill_duration_ttft` on the W7900 appeared **slower** than sequential prefill (7.67s vs. 5.66s for a 128-token chunk) — **this number was a measurement artifact, corrected after adding `rocprofv3` device-side kernel tracing**: the first-ever call through a given chunk size triggers lazy kernel compilation (WMMA + `gqa_attention`, ~2.5s of `hipcc` invocation) and HIP Graph capture, and that one-time cost was being counted inside the timed `prefill_duration_ttft` because the original test didn't separate a warmup call from the measured one. A corrected methodology (separate untraced warmup process to populate the on-disk kernel cache, then repeated timed runs, median of 3, same 517-token prompt across all configs) gives a very different picture: batched chunk=128 measures **6.28s median vs. 6.51s sequential — a real but small 3.8% speedup**, not a regression. Batched chunk=64 measures 6.45s (1.0% speedup), confirming smaller chunks are not a free win either. `rocprofv3` kernel-level tracing of the (correctly warmed-up) batched run identified where the remaining time goes: `gqa_attention_kernel`, the naive reference attention kernel deliberately accepted without tiling or online softmax (see the "Fora de escopo" note above), is the single largest kernel by GPU time at 36.9% (1.41s of ~3.8s total device time for a 128-token chunk across 32 layers, averaging 11ms/call) — ahead of every GEMM kernel including the WMMA one (19.5%). For comparison, the well-optimized Split-KV flash-attention kernel used by sequential decode averages ~32us/call for equivalent per-token attention work, roughly 340x cheaper per call. `gemv_q6k_kernel` (used by `RESIDUAL_FUSION` nodes like `attn_output`/`down_proj` and the LM Head, explicitly excluded from the WMMA dispatch and left on the old per-row kernel) is the second-largest cost at 27.8%. So the WMMA GEMM work is not wasted — it's part of why batched prefill now edges out sequential at all — but the naive attention kernel was the dominant remaining cost keeping the gain far below the plan's 2x bar.

**That gap is now closed.** A new attention kernel pair (`kv_cache_append_batched_kernel` + `flash_attention_prefill_kernel`) replaces `gqa_attention_kernel` on the batched-prefill dispatch path (with `gqa_attention_kernel` kept as an automatic fallback if the new path ever fails to build its launch args). Rather than porting decode's chunked Split-KV design (append + partial + reduce, 3 kernels, built for a *low*-occupancy problem — only `num_q_heads` blocks per layer), the new kernel generalizes decode's simpler, non-chunked `flash_attention_kernel` with a `q_pos` grid axis: since batched prefill already launches `seq_len * num_q_heads` blocks per layer (thousands, far more than the GPU's CU count), the bottleneck was never occupancy, it was `gqa_attention_kernel` computing its QK^T dot product entirely serially in one thread per query position (a `scores[2048]` array per thread) instead of cooperating across `head_dim` threads via the LDS tree-reduction pattern decode's kernel already uses. The KV-cache write has to be a separate, preceding kernel launch rather than fused in (unlike `gqa_attention_kernel`, which gets its ordering guarantee "free" by putting all query positions as threads in *one* block; here `q_pos` is a grid axis, so different blocks have no ordering guarantee relative to each other except the sequential-launch-order HIP already provides within one captured graph).

Validated the same way as the WMMA kernel: isolated correctness against a NumPy causal-GQA reference at 4 cases (small and real chunk/head sizes, both `kv_offset=0` and `kv_offset>0`, the latter being the case that actually exercises chunk-boundary correctness) — all within 0.18% of RMS magnitude, well inside fp16 noise. End-to-end generated text is byte-identical to the sequential path at both chunk=128 and chunk=64. Speed, warmup-corrected methodology, median of 3, same 517-token prompt: chunk=128 measures **3.96s vs. 6.51s sequential (1.64x)**; chunk=64 measures **3.33s (1.96x)** — chunk=64 also happens to exactly match the WMMA kernel's `M_TILE=64`, so it dispatches with no wasted GEMM tile padding, on top of doing less quadratic attention work per chunk. Decode throughput stays within noise of baseline (~76-77 tok/s in every configuration tested) and the new kernels add zero extra VRAM scratch (no partial-result buffers, unlike Split-KV). Re-verified at a ~1033-token prompt (24x repeat of the base text, closer to the plan's original "1024 tokens" success-criteria wording than the 517-token prompt above): byte-identical output confirmed again, speedup measures **1.88x** (13.45s sequential vs. 7.14s batched, median of 3) — a bit lower than at 517 tokens (more chunks means proportionally more fixed per-chunk cost), but still a large, real win, not noise (variance across repeats was ±0.02s in both cases). `VTE_BATCHED_PREFILL` now defaults to **on** (`VTE_BATCHED_PREFILL_CHUNK_SIZE=64` by default too, opt out via `VTE_BATCHED_PREFILL=0`): the measured 1.88-1.96x was judged close enough to the plan's ≥2x bar, and consistent/reproducible enough, to ship as the default rather than staying opt-in. Both the old GEMV-only path and `gqa_attention_kernel` are kept (not deleted) as validated fallbacks.

**RX 7600 (8GB) validation, 2026-07: a real VRAM gap found and fixed.** Everything above was measured on the W7900 (48GB); this pass tested the same default-on config on the RX 7600 for the first time, the card every other number in this document was measured on. Decode throughput across all five currently loadable models (Qwen2.5 1.5B, Qwen3.5 2B, Granite 4.1 3B, Qwen2.5 7B, Llama 3.1 8B) matched this document's own historical RX 7600 baselines closely in every case, confirming neither this feature nor the stochastic sampler below regressed decode speed on this card. But `VTE_BATCHED_PREFILL`'s chunk_size=64 default reserves an extra activation buffer at load time sized as `arena * (chunk_size - 1)`, a reservation whose cost scales with model width and was only ever checked against the W7900's 48GB headroom. On the RX 7600's 8GB, that extra reservation (+4.23GB for Llama 3.1 8B, +5.59GB for Qwen2.5 7B) pushed the total requested pool (9.1-10.2GB) well past what's free, and the failure mode was a hard, unhandled `MemoryGuardianOOMError` at model load, not the graceful degrade-to-sequential-prefill the design intended: the pool-sizing clamp (`vte/bridge/memory.py`, caps the request to 95% of total VRAM) and the malloc-time safety check (`HIPRuntime.safe_malloc`, 95% of currently-free VRAM) use different accounting, and the clamped size could still fail the second check. **Fixed**: `_load()` now checks real free VRAM (the same conservative 50%-of-free threshold `_ensure_batched_prefill_executor` already used for its own runtime decision) before committing the pool reservation, and skips it -- falling back to sequential prefill -- when it won't fit, instead of letting the allocator crash. Verified directly: Llama 3.1 8B and Qwen2.5 7B now load and run correctly on the RX 7600 (sequential path, matching historical decode tok/s), while the three smaller models still get the reservation and the feature as before.

**A missing header, then a compiler-version gap, found while re-testing on the RX 7600 -- the WMMA path had never actually run on Windows.** `gemm_q4k_wmma.hip.template` includes `<rocwmma/rocwmma.hpp>`, a header this Windows HIP SDK install doesn't ship at all (confirmed: absent anywhere under the SDK or `Program Files\AMD`), unlike a full Linux ROCm install where it's a standard package -- so every batched-prefill attempt on this card had silently been falling back to the sequential path via the existing try/except, never actually exercising the kernel the 1.88-1.96x number above is about. Vendored the header-only library (`rocm-7.1.0` tag of `ROCm/rocWMMA`, matching this project's installed HIP SDK version, into `VTE/third_party/rocwmma/`) and wired the include path into `codegen.py`. This surfaced a second gap: the vendored templates don't compile under this HIP SDK's bundled Clang (a `21.0.0git` development snapshot) with `hipcc`'s default C++ dialect -- real `constexpr`-evaluation errors deep in rocWMMA's own register-layout trait code, not in anything VTE writes. Fixed by passing an explicit `-std=c++17` to `hipcc` specifically for kernels that include rocWMMA (detected by scanning the rendered source, so every other kernel keeps compiling under the default dialect, unchanged). Both gaps reported with full repro steps in [`PLATFORM_ISSUES.md`](../../PLATFORM_ISSUES.md), issues 4 and 5.

**With the kernel actually compiling for the first time, a real correctness bug surfaced (found and fixed the same day -- see below).** Once `gemm_q4k_wmma` could genuinely run (rather than silently falling back), the generated text for Qwen2.5 1.5B on the RX 7600 diverged from the sequential path starting at the very first generated token, at greedy/`temperature=0`. This was the first time the feature had ever run end-to-end on any non-Llama-3.1-8B model on any hardware: every W7900 measurement above (1.88-1.96x, byte-identical output) was against Llama 3.1 8B specifically, which never reaches this code path on the RX 7600 (it's one of the two models the VRAM guard above correctly declines).

The investigation that followed eliminated, one at a time, against real GPU tests (not assumptions): gfx1102 vs. gfx1100 hardware differences, the `-std=c++17` flag corrupting kernel math, the retired `rocWMMA` repo vs. its `rocm-libraries` successor (the specific file involved is byte-identical between both), `RESIDUAL_FUSION` mis-excluding nodes, KV-cache pointer aliasing, a hardcoded RoPE position array (the real kernel computes position from a single offset scalar, not an array, so this hypothesis didn't even apply), a "dummy" buffer for RoPE's in-place output intercepting the real one, and finally each individual kernel in the chain (`embedding_lookup_q6k`, `rmsnorm`, `gemm_q4k_wmma` against the real `attn_k.weight` shape, the attention pair) tested in isolation against a NumPy reference using real weights and real, GPU-extracted activations -- every one matched to within ordinary fp16 noise (0.14-0.63% RMS). Comparing `attn_norm.output` at position 0 between the sequential and batched paths (read at the correct moment, not contaminated by a shared scratch buffer being overwritten by later decode calls, an artifact that cost real debugging time to catch) showed it is **identical** between the two paths -- ruling out everything from embedding lookup through RMSNorm as the source.

The investigation did not converge on a final root cause through kernel-level testing alone. A genuinely puzzling result at that point: an isolated `gemv_q4k` call, given the confirmed-identical `attn_norm.output` and the real `attn_k.weight`, computed a value matching the *batched* path's real `k_cache[0]` -- not the sequential path's own real `k_cache[0]` (confirmed reproducible, read at the correct moment, no fusion active for this model). Since `gemv_q4k` is exactly the kernel the sequential/decode path itself dispatches for this weight, this result contradicted the sequential path's own output, the opposite of what the rest of the investigation pointed toward.

**Root cause, found immediately after re-reading that contradiction with the actual model architecture in mind, not more kernel code: Qwen2.5 uses `attention_bias=True`.** `blk.N.attn_q.bias`, `attn_k.bias`, and `attn_v.bias` are real tensors in the GGUF, confirmed present in `tensor_mapping`. Llama 3.1 8B, the only model `gemm_q4k_wmma` had ever been validated against, has no attention bias at all -- so the kernel was built and shipped with no `bias_ptr` parameter whatsoever, while `gemv_q4k` (the kernel the sequential path dispatches for the exact same weight) already had one and used it correctly. The "contradiction" was never a contradiction: the isolated `gemv_q4k` test matched the batched path because both were missing the same term; the real sequential path matched neither because it was the only one adding it. Confirmed with a direct calculation before touching any code: the isolated `gemv_q4k` output (no bias) plus the real `attn_k.bias` (read from the live model, fp32), summed in NumPy, equals the sequential path's real `k_cache[0]` element-for-element. This also explains why Granite (no bias, and doesn't even reach this kernel, being Q8_0) and Llama 3.1 8B (no bias) were both byte-identical, and why RoPE was a dead end: at position 0, RoPE is mathematically an identity transform (`cos(0)=1, sin(0)=0`), so the divergence could only be coming from inside the projection itself.

**Fixed.** `gemm_q4k_wmma_kernel` (`vte/compiler/templates/rdna/gemm_q4k_wmma.hip.template`) now takes an optional `bias_ptr` parameter and adds `bias[n]` per output feature in its store epilogue, mirroring `gemv_q4k`'s own convention exactly. The dispatcher (`HIPGraphExecutor._build_gemm_q4k_wmma_launch`) resolves it through the same `KernelArgBuilder._resolve_matmul_bias` that `gemv_q4k`'s dispatch already used (nullptr for weights with no bias, so `gate_proj`/`up_proj`/models without attention bias are unaffected). Re-verified end-to-end on Qwen2.5 1.5B / RX 7600: generated text is **byte-identical to the sequential path across 60 tokens**, real prompt, greedy decode, and decode throughput shows no regression from the extra conditional add. `VTE_BATCHED_PREFILL` is back to **on by default**.

## Kernel efficiency and rejected optimizations

- FFN kernel fusion and WMMA/Tensor Cores remain measured-and-rejected (former) or unevaluated in the current batch>1 regime (latter). See [Performance](PERFORMANCE.md).
- `fused_gate_up_silu_kernel` (`VTE_ENABLE_FFN_FUSION`, off by default) is currently broken (produces NaN) for the project's actual FFN weight format: it assumes FP16 weights but `ffn_gate`/`ffn_up` are stored raw Q4_K. This predates and is unrelated to the batch=1 performance regression that already kept this fusion disabled. See [Architecture: Why QKV projection is fused, and why FFN fusion is off](ARCHITECTURE.md#why-qkv-projection-is-fused-and-why-ffn-fusion-is-off) for the full root-cause and why fixing it in-kernel was deliberately rejected rather than attempted.
- The batched (batch=4) LM Head GEMV achieves only ~7.5% of theoretical memory bandwidth, notably worse than the FFN's ~25%. A grid-dispatch-order fix (making batch_idx the fastest-varying block index) was implemented, validated bit-exact, measured (~3% gain, statistically flat end-to-end), and reverted. See [Bugs found during development](BUGS.md) for the full measurement. Remaining ~15x gap vs. the bandwidth floor is attributed to per-block dispatch/scheduling latency across 607744 blocks, not cache locality; closing it further needs WMMA/Tensor Cores or speculative decoding, both out of scope for a kernel-level tweak.
- Single-sequence decode throughput (~100 tok/s, stable across generation length) is still below the GPU's theoretical memory-bandwidth ceiling (~250 tok/s) and the decode graph's own measured GPU-only ceiling (~130 tok/s): the CPU/dispatch overhead, attention occupancy, and artificial pacing costs that used to dominate this gap have been found and fixed (sampler, LM Head, Split-KV, keep-alive pulse), so what remains is genuinely about GEMV kernel efficiency, not overhead around it. **A 2026-07 investigation cycle (see [Performance](PERFORMANCE.md#investigation-pushing-past-100-toks-2026-07)) audited every kernel accounting for 79.5% of GPU time (`gemv_q4k`'s GEMV family + the FlashAttention family) via static compiler analysis (`hipcc -Rpass-analysis=kernel-resource-usage`, generated-assembly inspection): zero register spilling, maximum compiler-reported occupancy, and already-vectorized memory access found everywhere checked.** A follow-up (Thesis V6, same section) measured `gemv_q4k`'s *achieved* bandwidth directly rather than stopping at that clean compiler report, found it at only ~76.5% of a same-topology baseline, and closed part of that gap with a header-coalescing rewrite for a real, modest end-to-end tok/s gain on all Q4_K models. Several other specific hypotheses (Split-K for the FFN GEMV, LDS double-buffering, explicit ILP prefetch) were each individually evaluated and rejected on evidence, not assumption. Still not fully closed, but now for a specific, evidenced reason: closing the remainder needs hardware-counter data (achieved-vs-theoretical memory bandwidth, real cache hit rates, true wavefront stall reasons) that this machine's driver stack can't provide (RGP requires a full AMD driver install, not just the HIP runtime, see the same section), not more static analysis on this toolchain.
- **`gemv_q6k` has a real, measured bandwidth gap (median 74.0% of baseline, same band as `gemv_q4k` before its fix) that is not yet closed.** The Q4_K header-coalescing fix was attempted on the analogous-looking redundancy in `gemv_q6k` (all 64 threads in a block re-reading the same superblock scale independently) and measured as a genuine ~25% regression, not a gain: the two redundant reads look identical in source but are architecturally different (scattered-different-addresses vs. uniform-broadcast-of-one-address, see [Bugs found during development](BUGS.md)). Reverted. The real bottleneck behind Q6_K's 74% ceiling is registered here for future investigation, not yet root-caused: the leading candidate is the total absence of vectorized (`uint4`) loads in the kernel, since its 210-byte block size isn't a multiple of 16. This affects Qwen3.5 2B specifically, since Q6_K is its primary quantization, not a fallback path. See [Performance](PERFORMANCE.md#extending-these-optimizations-to-other-quantizations-2026-07).
- **An opt-in GPU-side logits reduction for greedy decode (`VTE_TOPK_LOGITS_READBACK=1`, off by default) exists but delivers a small, model-size-dependent gain, not a general speedup.** Numerically validated bit-identical to the full-array path across 7 prompt styles on 3 models (Qwen2.5 1.5B/7B, Granite), including long-context (2048) and long-generation (~1500 token) runs. End-to-end gain is real but modest on the fastest model (median +1.08% on Qwen2.5 1.5B) and within noise or slightly negative on larger ones (7B, Llama 3.1 8B), since the overhead it removes is a fixed per-token cost that matters proportionally less as the per-token GPU budget grows. See [Performance](PERFORMANCE.md#gpu-side-top-k-logits-reduction-2026-07) for the full methodology, including a first eager-launch version that measured as a net loss before being fixed by capturing the kernel into the HIP Graph.
- **A GPU-side logits reduction for the STOCHASTIC decode path (`VTE_STOCHASTIC_TOPK_READBACK`, temperature>0 -- the project's actual default, unlike the greedy-only reduction above) exists and delivers a real, consistently measured gain: +6.96% median decode tok/s** (Llama 3.1 8B, W7900, warmup-separated median of 3 runs, 74.36 -> 79.54 tok/s at the project's default sampling settings: temperature=0.7, top_p=0.9, top_k=50, repetition_penalty=1.1). Root-caused before building anything (2026-07): profiling `Sampler.sample()` showed 92.6% of its own cost (1.16ms of 1.25ms/token) was a single `np.argpartition` over the full vocabulary, not the RNG, top-p, or repetition penalty (those three combined cost <0.1ms) -- the original "build an RNG + top-k heap + top-p CDF + selection kernel from scratch" proposal this started from was resized down to just moving the top-k candidate search to GPU, reusing the existing `topk_reduce_greedy_kernel`'s per-thread-local-best pattern generalized from 1 candidate/thread to `PER_THREAD_K` candidates/thread (`topk_reduce_stochastic.hip.template` / `StochasticTopKReducer` / `Sampler.sample_from_gpu_candidates`), instead of a new subsystem.

  A real correctness bug was found and fixed before shipping: `PER_THREAD_K=5` (chosen for VGPR headroom) silently dropped up to 15 of the true top-50 candidates under a synthetic adversarial input specifically constructed to cluster 20 high-value logits into one thread's `i % NUM_THREADS` partition (`tools/test_topk_stochastic_isolated.py`, case `clustered_worst_case`) -- real model logits (25/25 samples across 5 diverse prompts, including numeric-sequence and code-completion contexts) and pure uniform-random logits never triggered it even at `PER_THREAD_K=5`, since vocabulary IDs aren't correlated with token likelihood, but "never triggers in practice" isn't the same as "correct". Raised to `PER_THREAD_K=16`: the same adversarial construction now loses only 4 of 50 (not 0 -- no finite per-thread capacity gives an absolute guarantee against an input built specifically to exceed it), while all real/random cases still pass cleanly. This is a strong empirical guarantee, not a mathematical one; accepted for the stochastic path specifically because an occasional, adversarially-forced miss changes the sampled distribution negligibly (top-k=50 is already a heuristic truncation of the full distribution), unlike the greedy path above where exactness matters and remains the unmodified, bit-exact `topk_reduce_greedy_kernel`.

  Statistical correctness validated separately: sampling 20,000 times from a real high-entropy logit distribution (entropy 3.03, top-1 probability only 26%) via the old full-vocab path vs. the new GPU-candidate path produced near-identical empirical distributions (KL-divergence 0.0001, gate was <0.01). Greedy decode (temperature<=0) is completely unaffected by construction (the new path only activates for temperature>0) -- confirmed byte-identical output with the flag on vs. off. Off by default (`VTE_STOCHASTIC_TOPK_READBACK=0`) pending a decision on promoting it, same opt-in pattern as the greedy reduction above.

  **RX 7600 validation, 2026-07**: confirmed active and non-regressing on all five currently loadable models, warmup-separated medians of 3, this project's real default sampling settings (temperature=0.7, top_p=0.9, top_k=50): Qwen2.5 1.5B 115.14 tok/s, Qwen3.5 2B 68.55 tok/s, Granite 4.1 3B 57.34 tok/s, Qwen2.5 7B 40.64 tok/s, Llama 3.1 8B 39.15 tok/s. Every number sits inside (mostly at the high end of) this document's own historical RX 7600 baseline range for each model, so the gain measured on the W7900 above isn't offset by any regression on the smaller card. Unlike batched prefill above, this feature carries no extra VRAM cost (it only changes what the existing LM Head/top-k kernels read back, not what they allocate), so it hit no VRAM ceiling on any of the five models, including the two (Qwen2.5 7B, Llama 3.1 8B) where batched prefill did.
- Split-KV attention (see [Bugs found during development](BUGS.md)) is the default for single-sequence decode (opt-out via `VTE_DISABLE_ATTN_SPLITKV=1`) after a validation pass covering short/long generations, chunk-boundary crossings, mid-generation cancellation, and scratchpad reuse immediately after a cancellation: all produced correct, coherent output with `pytest` green throughout. It only affects `generate()`; `generate_batch()` (batch>1) uses the unmodified `flash_attention_kernel` and is untouched by this change. One caveat worth knowing: greedy (`temperature=0`) output can occasionally diverge from the pre-Split-KV baseline partway through a long generation: not a bug, see the bug entry for why (reordered-but-equivalent floating point, not incorrect floating point), and irrelevant at the project's actual default (`temperature=0.7`).
- The inter-token keep-alive pulse now defaults to `0.0` (disabled). See [Bugs found during development](BUGS.md) for the measurement showing this is currently both faster and more stable than any nonzero value tested on this hardware/driver. `VTE_KEEPALIVE_PULSE_MS` (milliseconds, e.g. `"2.0"`) restores the old behavior without a code change if a future driver update, different hardware, or another GPU-heavy application running alongside VTE ever reintroduces the DPM-downclocking stutter this was originally built to prevent.

## Telemetry and desktop UI

- Real GPU temperature on Windows only works on AMD hardware, and only if either the PMLog (`ADL2_New_QueryPMLogData_Get`, RDNA/RDNA2/RDNA3) or the legacy Overdrive5 (`ADL_Overdrive5_Temperature_Get`, pre-RDNA) API responds. See [vte/bridge/adl_bridge.py](../vte/bridge/adl_bridge.py). On a non-AMD GPU, or if both ADL calls fail, `GPUMonitor` reports `None` and the UI shows "N/A" rather than fabricate a number. VRAM and the model's idle-unload countdown are WMI-sourced and always real, refreshed every ~0.35s.
- The dashboard shows two separate VRAM numbers, deliberately not one: the large value is what VTE itself allocated (weights+KV+arena, deterministic, always equals the Weights/KV/Arena breakdown below it); "Sistema (dedicada)" is the whole system's dedicated GPU memory from WMI (matches Task Manager's GPU tab, but includes the desktop compositor, browser, etc.). An earlier version conflated the two into one number, which made it jump in ways that had nothing to do with VTE's own usage.
- The desktop UI's language toggle (pt/en, see [Multi-architecture support](GRANITE.md) for the flag-icon fix) only translates UI chrome (labels, tooltips, status text): it re-renders currently visible dynamic text (metrics, lifecycle status) immediately from the last known values, but log lines and chat messages are never translated, since they're either raw backend output or real user/model content, not UI copy.

## Hardware portability

- **RDNA2 now has precompiled AOT kernels, but is still theoretical (architecture detection + CU-count scaling verified by simulation on the RX 7600, never run on real RDNA2 hardware).** GPU architecture targeting is dynamic: `get_gpu_architecture()` (`vte/bridge/hip_runtime.py`) reads the real device name at runtime and `GPU_ARCH_MAP` (`vte/config.py`) lists RX 6400 through RX 6950 XT (gfx1030/1031/1032/1034, Navi21/22/23/24). CU-count scaling is split across two kernels with different status: **Split-KV attention** (`vte/core/split_kv_attention.py`) is genuinely dynamic: `_chunk_size_for_cus()` derives its grid from `HIPRuntime.get_num_cus()` (real `hipDeviceGetAttribute` value, WGP-doubled), not a fixed `32`. Simulated via `VTE_NUM_CUS=28` (the RX 6600, the one RDNA2 card in `GPU_ARCH_MAP` with fewer CUs than the RX 7600's 32) on the real RX 7600 hardware: chunk_size correctly shifted from 32 to 37, output stayed correct, and throughput was statistically flat (98.8 to 96.7 tok/s, ~2%). The scaling logic itself doesn't regress. Note this only validates the *scheduling logic*, not real RDNA2 throughput: a real RX 6600 also differs in memory bandwidth and clocks, which can't be simulated on RX 7600 silicon. **Split-K QKV** (`vte/core/fused_qkv_dispatch.py`) still hardcodes `chunk_size = hidden_size // 32` and a `grid=(32, ...)`: this is a fixed algorithmic split, not tied to the actual CU count for *correctness* (any CU count still produces the right numbers, just with imperfect occupancy on GPUs with other-than-32 CUs), and it has not been migrated to `get_num_cus()` yet, deliberately left as a follow-up performance item rather than touched now, since changing a numerically-validated reduction kernel without RDNA2 hardware to re-verify against is a correctness risk this project isn't willing to take blind (and the RX 7600 baseline must not regress). Separately, an unrecognized GPU name (one not in `GPU_ARCH_MAP`, e.g. an RDNA3.5 APU) silently falls back to `DEFAULT_GPU_ARCH = "gfx1100"` (RDNA3), which would likely fail outright on real RDNA2 hardware since the two are different instruction sets.
- **Linux/CDNA support is unverified code, written defensively but never run against real hardware.** VTE has only ever run on Windows: `vte/bridge/dll_discovery.py` originally hard-gated its search to `win32` and looked exclusively for `amdhip64.dll`. A Linux-side search (`find_hip_so()`, dispatched via the new `find_hip_library()`) was added following the same defensive multi-candidate pattern as the Windows search (`ROCM_PATH`/`HIP_PATH` env vars, `/opt/rocm` and `/opt/rocm-*` glob, `LD_LIBRARY_PATH`, falling back to a bare `libamdhip64.so` name for the system linker to resolve), and validated against a simulated fake directory tree, not real hardware; no Linux or ROCm-on-Linux machine was available while writing it. Beyond library discovery, several other subsystems remain Windows-only and untouched: WMI-based telemetry (`gpu_monitor.py`), ADL-based GPU temperature (`adl_bridge.py`), and the MSVC environment injection in `codegen.py::_setup_hip_env` (should be unnecessary on Linux, where `hipcc` doesn't need it, but that assumption is also unverified). Separately, and a bigger gap than the OS port: every kernel template is written and tuned for RDNA's wave32 execution model; CDNA (Instinct/MI, wave64) is a different instruction set family, not a wave-width variant like RDNA2 vs. RDNA3, and would need its own kernel templates (a new `vte/compiler/templates/cdna/` directory exists as a placeholder) plus a fix to `get_num_cus()`'s WGP-doubling logic, which is RDNA-specific and would silently double-count CDNA's compute units if applied unmodified. Revisit both once real Linux/CDNA hardware access exists to actually test against.
- **No multi-GPU device selection: `HIPRuntime.initialize()` always calls `hipSetDevice(0)`, with no way to pin a specific device.** `vte/bridge/hip_runtime.py:333` hardcodes device index 0; there is no `ROCR_VISIBLE_DEVICES`/`HIP_VISIBLE_DEVICES` handling anywhere in the codebase, and no logic to prefer a discrete GPU over an integrated one. On a single-dGPU machine (the only configuration this project has ever run on: one RX 7600, nothing else) this is a non-issue, since device 0 is the only device. On a machine with both a dGPU and an AMD iGPU, which HIP enumerates as device 0 is undefined from VTE's point of view; it could silently pick the iGPU. This surfaced as a real, severe bug in Lemonade itself (not in VTE, flagged here as a heads-up while reviewing a Lemonade GitHub issue during the VTE backend PR conversation): a dGPU+iGPU system's spawned `llama-server` child process never received the parent's `ROCR_VISIBLE_DEVICES` pin (the subprocess launcher only forwards a fixed allowlist of env vars per-backend, none of them GPU-selection-related for the ROCm path), so it enumerated both devices, the iGPU participated in device selection, and the mismatched kernel image crashed hard enough to hang the GPU. If VTE is ever run through Lemonade (or standalone) on a dGPU+iGPU AMD system, the same class of failure is plausible on the VTE side too: even if Lemonade correctly forwards `ROCR_VISIBLE_DEVICES` to `vte-server`'s subprocess, `HIPRuntime` doesn't read or honor it anywhere. Not fixed here: no dGPU+iGPU hardware exists in this project to design or validate a fix against, and guessing at device-selection logic without measuring it on real hardware would repeat exactly the mistake this project's own "measure, don't guess" discipline exists to avoid. Revisit when such hardware becomes available.
- **ROCm 6.4 → 7.1 upgrade validated on real hardware (RX 7600, gfx1102): no regression found.** Ran the full pytest suite (68 tests), a bit-exact regression across all 4 registered models, a 250-token generation (crosses Split-KV chunk boundaries), and a batch=4 `generate_batch` run, all against a real ROCm 7.1 install side-by-side with the 6.4 baseline. Results: device properties, `get_num_cus()` (still correctly WGP-doubled), and every precompiled `.hsaco`'s SHA256 hash were byte-identical between versions (the AOT cache loaded and ran without triggering the recompile fallback even once); the 3 pytest failures present are identical on both versions (pre-existing test-fixture bugs unrelated to ROCm, not a regression); generation output was bit-exact and tok/s statistically flat. Also reconfirmed the `hipGetDeviceProperties`/R0000 ABI behavior documented above is unchanged on 7.1 (byte-identical output calling the plain symbol vs. `hipGetDevicePropertiesR0000` explicitly). One real bug surfaced by the upgrade itself, not by ROCm: `vte/bridge/dll_discovery.py` hardcoded the DLL filename to `amdhip64.dll`/`amdhip64_6.dll`, so it silently would not have found `amdhip64_7.dll` (ROCm 7.1 ships no unversioned alias, confirmed 6.4 doesn't either; this naming scheme, `amdhip64_<major>.dll` with no stable alias, appears intentional and consistent across both installed versions, not an AMD defect). Fixed to glob for any `amdhip64_*.dll`, preferring the newest version. This is a single-datapoint result (one card, one version jump); it doesn't prove every future ROCm release will be this clean, only that this one was, measured rather than assumed.
- **Precompiled AOT kernels for `gfx1100`/`gfx1101` (RX 7900/7600 XT/7700/7800 series) and `gfx1030`/`1031`/`1032`/`1034` (RDNA2: RX 6900 XT down to RX 6400) compile cleanly but were never run.** `scripts/build_kernel_cache.py` warms the real kernel cache by actually loading and generating on every registered model on the real `gfx1102` hardware (RX 7600): those binaries are genuinely validated. `scripts/cross_compile_kernel_cache.py` (RDNA3 siblings) and `scripts/cross_compile_rdna2_kernel_cache.py` (RDNA2) both extend this by reusing the exact rendered `.hip` sources from that real run and invoking `hipcc --offload-arch=<target>` directly, without loading or executing the result (no such hardware exists to test on). All 63 kernels currently needed by the 4 registered models compiled without error for all 6 targets (`gfx1100`, `gfx1101`, `gfx1030`, `gfx1031`, `gfx1032`, `gfx1034`), but "compiles cleanly" only proves the source is syntactically valid C++ for that ISA, not that it produces correct numbers on it; a subtle codegen difference between architecture sub-variants (or generations) could in principle miscompile silently. `HIPRuntime.load_kernel_safe()`'s automatic fallback (see the bug entry above) only catches a binary that *fails to load* (ABI/driver mismatch): it cannot detect one that loads fine and computes something wrong. RDNA2 was initially excluded from cross-compilation over concern about real ISA divergence from RDNA3 (RDNA2 lacks RDNA3's AI-oriented ISA additions, specifically matrix/WMMA instructions and VOPD, dual-issue VALU); before writing the RDNA2 script, this was checked against the actual code rather than assumed: an exhaustive grep of all 32 kernel templates (`vte/compiler/templates/*.hip.template`) found zero uses of matrix instructions or any low-level `__builtin_amdgcn_*` intrinsic; the only wave-level primitives used are `warpSize`/`__shfl_down`/`__shfl_xor`, which resolve identically on both generations since RDNA2 and RDNA3 are both wave32 (unlike GCN/CDNA's wave64). VOPD needs no equivalent guard: it isn't invoked via any HIP intrinsic, it's an instruction-scheduling decision the LLVM/AMDGPU backend makes on its own based on `--offload-arch`, and `compile_source_for_arch()` (`vte/compiler/codegen.py`) passes only `hipcc --genco --offload-arch=<target> -O3`, no manual `-mllvm`/`-mcpu`/feature flags that could force RDNA3-only codegen onto a gfx10 target; all 4 RDNA2 targets compiling without error is itself evidence the backend selected gfx10-appropriate (non-VOPD) encoding, since an attempt to emit VOPD for a target that doesn't support it would fail to assemble rather than silently miscompile. None of this eliminates the general risk (identical HIP source can still codegen subtly differently per architecture in ways unrelated to matrix instructions or VOPD), but it removes the two *known*, specific ISA divergences this project was worried about between these two generations.

## Reverted features and VRAM management

- **Speculative decoding was implemented and then reverted.** A draft-model-based approach (Qwen2.5 0.5B proposing tokens for the 1.5B/7B targets, verified in a batched forward pass) and a follow-up Prompt Lookup Decoding variant (n-gram search over the token history instead of a draft model) were both built, made numerically correct, and measured: neither beat the non-speculative baseline on this GPU (best case ~0.5x of baseline throughput even after fixing real bugs along the way: a global raw-weight-registry leak between coexisting models, a `hipDeviceReset()` destroying a second model's VRAM on unload, a missing kernel argument in the batched LM Head, and GPU clock/P-state dropping between bursty CPU/GPU handoffs). The real, independent bug fixes found during that work were kept (see [Bugs found during development](BUGS.md)); the speculative decoding code itself was removed rather than shipped as a slower default path.
  - **Re-evaluated in 2026-07, killed at the feasibility stage this time instead of after implementation.** Before writing any verification-kernel/rollback code, a standalone read-only script retroactively simulated a Prompt Lookup Decoding drafter's n-gram lookup against real generated token sequences, measuring acceptance rate (how often/how deep a draft would have matched what the model actually produced) rather than throughput directly. Gate: 40% or higher acceptance on a favorable (code-generation) prompt to be worth implementing. Result: 27.6% best case, 8.0% on free-form creative text, fails the gate. See [Performance](PERFORMANCE.md#investigation-pushing-past-100-toks-2026-07) for the full measurement across prompt styles. Consistent with the earlier implementation's real-world result above, but reached for a fraction of the engineering cost.
- **VRAM budgeting is now cross-model-aware (the 95% check and cleanup used to be per-instance, not per-process. See [Bugs found during development](BUGS.md) for both bugs this caused), but each loaded `VTEModel` still gets its own `SlabAllocator` pool sized only for its own weights/KV-cache/arena: there's no shared pool, just a shared safety counter.** `HIPRuntime.safe_malloc()`'s "never exceed 95% VRAM" check (`VRAM_SAFETY_MARGIN=0.95` in `vte/config.py`) now sums bytes across every `HIPRuntime` instance in the process (`HIPRuntime._process_wide_allocated_bytes`, a class-level counter) and cross-checks against the GPU's real free memory (`hipMemGetInfo`, catches VRAM used by other processes too: games, browsers, etc.), so a second model loading on top of an already-resident one correctly counts against the same 95% ceiling instead of each instance seeing the full budget for itself. A `VRAMPressureGuard` (`vte/bridge/vram_pressure_guard.py`) also polls real GPU VRAM in the background and auto-unloads the least-recently-used loaded model if usage stays above 95%. `SlabAllocator` itself still never returns VRAM to the OS/driver once `hipMalloc`'d (freed blocks go back to an internal free-list for reuse within that same pool, not `hipFree`'d): unloading a model frees its own pool via `unload()`, and (since the `hipDeviceReset()` fix) no longer disturbs any other model's pool still resident in the same process.

## Model compatibility

- Only the Bartowski Q6_K conversion of Qwen 3.5 2B is validated to work: a structurally different Unsloth Q4_K_M conversion of the same nominal model produced immediate incoherence and is not registered. Full details in [Qwen 3.5: Known limitation: only the Bartowski Q6_K conversion is validated](QWEN35.md#known-limitation-only-the-bartowski-q6_k-conversion-is-validated-to-work).
- **Granite 4.1 30B (Q8_0) reproducibly replies in Portuguese or Spanish to a short English message once a real tool-calling system prompt is in context, and this is not a VTE prompt bug.** Found while using it as Aetheris's model: an English "hi" came back in Portuguese. Isolated directly against a live `vte-server` instance (W7900, greedy decoding, `temperature=0` for determinism): Aetheris's system prompt alone (identity + language instruction, no tool documentation) produces a correct English reply every time; the full system prompt (identity + the ~5.3KB tool-documentation block, fenced code examples for every tool) deterministically produces "Olá! Como posso ajudar você hoje?" instead. An equal-length neutral English filler block in place of the tool documentation reproduces the correct English reply, ruling out prompt *length* as the cause. Bisecting the tool-documentation block in half showed *both* halves independently trigger a wrong-language reply on their own (Portuguese from one half, Spanish from the other): the effect is diffuse across the fenced-code/CLI-tool-documentation register, not one guilty sentence. Repositioning the "reply in the same language" instruction (start of prompt, end of prompt, or both) never fixed it. What did work, tested directly: an *explicit* named-language reminder ("Reply in English.") appended to the user's own message, immediately adjacent to the generation point, fixed it consistently; a generic, language-agnostic version of the same reminder ("Reply in the same language as this message.") in the identical position did not. A real fix would need per-turn language detection of the user's message plus a dynamically-worded reminder, which is a real feature (a new dependency, not a prompt tweak), so Aetheris uses Llama 3.1 8B Instruct as its default model instead: verified against the identical system prompt (English in, English out; Portuguese in, Portuguese out, both correct), and needs a fraction of Granite 30B's VRAM (~5GB vs ~29GB) and decodes over 3x faster on the same hardware (~66 tok/s vs ~19 tok/s). Granite 4.1 3B was not re-tested against this specific failure mode; given the effect traces to the tool-documentation register rather than model scale, it should not be assumed immune.

## Roadmap: deferred past the hackathon, not rejected

A 2026-07 optimization pass started from a much larger analytical document (RDNA3 roofline modeling, ISA-level kernel rewrites, batched prefill, operator fusion, GPU-resident sampling, with an original multi-year timeline) and cut it down to hackathon scope by validating each piece against the real codebase first, rather than trusting the document's own estimates. Batched prefill and GPU-resident sampling (both above) came out of that cut and shipped. Two pieces didn't get attempted this cycle; they're deferred for a concrete reason each, not abandoned as bad ideas:

- **ISA-level kernel rewrites** (manual VOPD dual-issue, native dot-product instructions on `gemv_q4k`/`gemv_q6k`) were never attempted because the profiling access needed to do this safely isn't available on this hardware/cloud combination. Confirmed directly this cycle, not assumed: `rocprofv3`'s hardware performance counters return exactly `0.0` for every counter tried, from cache-hit/request-size breakdowns down to the most basic possible sanity check (`SQ_INSTS_VALU`, a raw instruction count that should be trivially nonzero for any real kernel). This is the same underlying limitation already documented above for RGP (needs a full AMD driver install, not just the HIP runtime) extending to `rocprofv3`'s counter-collection path too. Without real VGPR/occupancy/stall data, a hand-written ISA rewrite is guesswork with a real precedent for going wrong on this exact codebase (see the `gemv_q6k` header-sharing revert above, and the `gemv_q6k` bandwidth investigation this same cycle, stopped for the same reason after a fresh baseline came in at 49.2%, below the tool's own "safe to proceed without deeper data" threshold).
- **The rest of the original document's larger scope** (an analytical roofline performance model, and material beyond the four areas actually evaluated: ISA kernels, batched prefill, operator fusion, GPU sampling) was not reviewed this cycle at all — no claim is made here about whether it's sound or worth doing, only that it wasn't looked at. Worth a dedicated pass before treating any of it as a real plan, following the same discipline used for everything above: validate each claim against the actual code before scoping work from it, not the other way around.

## Speculative decoding: correct, but rejected a third time — this time for a measured economic reason, not a bug

Speculative decoding (small draft model proposes tokens, target verifies them in a batched forward pass) was tried twice before this cycle and rejected both times (see "Reverted features and VRAM management" below): once dispatch-bound/environmental on the RX 7600 (4-11x slower), once weight-read-amortization-bound on the W7900 (verify cost measured 4.48x a single decode step, root-caused to `gemv_q4k` re-streaming its full weight row per verified position with zero tile reuse across the batch). That second finding explicitly named the missing piece: "a genuinely different, batched-GEMM-style kernel (reusing loaded weight tiles across the batch dimension)."

**That kernel now exists** (`gemm_q4k_wmma.hip.template`, built this same 2026-07 cycle for batched prefill) — built for an unrelated reason, never connected to speculative decoding until this cycle. A full `SpeculativeDecoder` (`vte/core/speculative.py`) was built on top of it and validated **numerically correct**: greedy output byte-identical to the sequential path across 3 test prompts, at `repetition_penalty=1.0` (VTE's real default applies repetition penalty even at `temperature=0`, checked before the greedy branch in `Sampler.sample()`; doing this correctly per-position inside a batched verify call, where each of the K positions needs a penalty reflecting a different amount of already-generated history, is unimplemented — a real, explicit scope gap, not a hidden bug: the mismatch against the true default was caught immediately by the byte-identical gate and diagnosed before being scoped out). A real correctness bug was found and fixed along the way: the round boundary needs one *extra* target decode step processing whichever token was actually emitted last (the bonus token when all K drafts are accepted, or the replacement token on a mismatch) — the verify batch's own logits only predict that token, never the one *after* it.

**Measured end-to-end, it is 2.67x *slower*, not faster** (29.86 vs 79.80 tok/s, Llama 3.1 8B target / Llama 3.2 1B draft — same tokenizer family, confirmed via matching `vocab_size=128256` — W7900, warmup-separated median of 3, 100-token generation, 51% mean draft acceptance rate, 3.45 tokens/round). Two rounds of root-causing, not one, and the first was wrong:

1. **First hypothesis (wrong, disproven by testing, not just assumed): per-round Python/Host-Device dispatch chattiness** (~11 small synchronization + D2H round-trips per round — up to 5 sequential target logit reads during accept/reject, up to 5 sequential draft logit reads during proposal, 1 more for the round-boundary fix). Fixed directly: rewrote the target's accept/reject checking to launch all K eager LM-head calls back-to-back on the same stream with zero intermediate host sync, one combined D2H at the end, accept/reject entirely in NumPy afterward — collapsing up to 5 round-trips into 1. **Measured effect: none** (29.03 tok/s, statistically flat vs. 29.86 tok/s before). This ruled the hypothesis out; kept in the code regardless since it's a harmless, real micro-optimization, just not the answer.
2. **Real cause, found by re-examining the verify-cost gate's own units**: the gate's headline number (`execute_prefill` measured at 0.92-1.24x the cost of *K sequential decode steps*) is a different quantity than what a speedup projection needs (verify cost relative to *one* decode step). Corrected: real per-position verify cost ≈ `1.13 * K` ≈ 5.65x one decode step at K=5 — meaning the WMMA kernel, while genuinely far cheaper than the old `gemv_q4k`-based verify (a real fix, not wasted work — it closed a *previously* fatal 4.48x-vs-K-decodes gap), still costs *roughly one full decode step per verified position*, not a small fraction of one. Speculative decoding only pays off when verifying K positions costs much less than K decode steps, so the K−1 positions that get discarded on any rejection are nearly free; at the measured ~40-51% acceptance rate here, there isn't enough margin, and `tokens_per_round / (C_verify_per_position_relative_to_one_decode)` works out to the observed sub-1x result (≈0.61x projected from the corrected math, matching the ≈0.36-0.37x actually measured once the draft's own overhead is added on top).

**Verdict**: neither swapping the draft model for a model-free proposal mechanism (prompt lookup decoding, already measured elsewhere in this project at a lower ~27.6% acceptance ceiling) nor further dispatch-level micro-optimization can fix this — the bottleneck is entirely on the target's verify-cost-per-position, independent of who proposes the tokens. Closing it for real would mean making per-position verify cost a small fraction of one decode step (deeper kernel-level work on `gemm_q4k_wmma`'s tile reuse and the batched attention kernel, not this project's Python dispatch layer), a separate and substantially larger undertaking not attempted this cycle. `vte/core/speculative.py` is kept as validated-but-not-worthwhile-yet infrastructure (correct, with both the fix that worked — WMMA verify — and the one that didn't — dispatch batching — preserved and documented), not deleted.
