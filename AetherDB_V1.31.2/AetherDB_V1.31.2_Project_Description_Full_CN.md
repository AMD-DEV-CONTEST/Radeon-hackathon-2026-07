## 一、项目概述

AetherDB V1.31.2 是一套面向长篇小说、游戏叙事、IP 世界观管理和多模态创作流程的本地优先桌面应用。

它的核心目标并不是单独提供一个 AI 对话框，而是把以下能力整合进同一个可管理、可检索、可审核的创作环境中：

- 长篇作品和章节管理；
- 人物、地点、组织、事件、物品、规则等世界观实体管理；
- 关系、时间线和实体状态记录；
- 本地全文检索和向量检索；
- RAG 上下文召回；
- AI 辅助分析、抽取、润色、扩写和创作；
- 图像、音频和其他媒体资产管理；
- 多模态内容生成、检索、审批和绑定；
- 本地模型、Ollama 和云端 API 的统一模型路由；
- 模型资源调度、Worker 隔离和运行证据记录；
- AMD Radeon GPU / ROCm 环境下的真实模型执行验证。

AetherDB 的设计重点是：

> 让作者能够在一个桌面应用中完成“创作—检索—生成—审核—绑定—归档”的完整流程，而不是把正文、设定、图片、音频和 AI 工具分散在多个互不关联的软件中。

## 二、项目解决的问题

### 1. 世界观资料容易分散

人物设定、事件、关系、地点、规则和时间线通常分散在正文章节、临时笔记、聊天记录、表格、图片、音频和不同版本的文档中。

随着章节和角色数量增加，创作者很难持续确认“当前有效设定是什么”。

AetherDB 使用结构化数据库、章节绑定、实体关系、时间线和状态记录，把这些内容整理成可检索的本地知识库。

### 2. AI 容易遗忘长篇上下文

当作品内容越来越长时，模型不一定能够稳定读取或调用全部相关设定。

即使模型拥有较长上下文，也可能出现：

- 遗漏角色状态；
- 忽略时间线变化；
- 混淆人物关系；
- 错用旧版本设定；
- 用看似合理但未经确认的内容补充信息。

AetherDB 使用本地 BGE-M3 文本向量、全文检索、结构化作用域过滤和 EvidencePack 上下文包，把当前任务真正需要的信息筛选出来，再交给模型处理。

### 3. AI 结果不能直接成为正式设定

模型输出可能包含错误、幻觉或不完整结果。

因此 AetherDB 不允许模型直接修改正式数据库。

模型生成的实体、关系、章节分析、视觉内容或音频内容，首先进入预览、临时结果、pending ChangeSet 或待审批资产；只有经过用户确认后，才会进入正式数据库或正式媒体资产。

### 4. 多模态内容缺少统一管理

很多创作工具可以生成图片或音频，但生成结果往往只是单独文件，无法可靠回答：

- 这张图属于哪个作品？
- 对应哪个章节？
- 对应人物的哪个时期或状态？
- 是否已经经过作者确认？
- 使用了哪个模型、Prompt 和参数？
- 是否可以在后续章节中继续检索和复用？

AetherDB 将图像、音频和其他媒体内容作为正式资产管理，并绑定作品、章节、人物、场景、时间线和状态。

## 四、核心工作方式

典型工作流程：

```text
创建作品或导入已有作品
→ 章节拆分和记录
→ 本地文本向量化
→ 世界观实体、关系和时间线管理
→ 用户发起创作或检索任务
→ AetherDB 按作品、章节、人物和时间范围筛选上下文
→ 本地模型、Ollama 或云端 API 执行任务
→ 结果进入预览或临时区
→ 用户审核和确认
→ 正式写入章节、数据库或媒体资产
```

多模态流程：

```text
选择章节或世界观设定
→ 提取人物、场景、风格和关键元素
→ 生成图像或音频任务
→ 调用本地模型、Ollama 或云端 API
→ 生成临时图片或音频
→ 预览、比较、重试和修改
→ 用户确认
→ 绑定到章节、人物、场景或世界设定
```

## 五、系统架构

AetherDB 采用分层架构：

### 1. 桌面前端

技术：

- Vue 3；
- Vite；
- Pinia；
- Vue Router；
- vue-i18n；
- Tauri 2。

职责：

- 写作工作台；
- 世界观管理；
- AI 设置与管理；
- 模型和运行状态展示；
- 媒体资产管理；
- 图像和音频创作交互；
- 用户审批和确认。

### 2. 后端控制面

技术：

- FastAPI；
- Pydantic；
- 本地回环服务；
- Header-only API Key；
- capability 权限控制。

职责：

- 数据访问；
- 权限判断；
- 模型路由；
- 任务管理；
- Worker 管理；
- 资源调度；
- 上下文构造；
- 输出验证；
- 正式写入；
- 日志和证据记录。

### 3. 本地数据层

技术：

- SQLite；
- WAL；
- FTS5；
- sqlite-vec；
- 独立 registry 数据库；
- 每作品/世界独立数据库。

### 4. 模型执行层

执行路径包括：

- AetherDB 自有原生模型 Worker；
- Ollama 本地模型运行时；
- OpenAI-compatible API；
- 其他云端 Provider；
- 图像和音频专用 Worker。

所有模型任务都必须经过统一模型路由、资源调度和任务状态管理。

### 5. Worker 隔离

每个模型或 replica 使用独立 Worker 进程。

系统负责：

- 加载和卸载；
- 心跳；
- IPC；
- 取消；
- 崩溃回收；
- GPU lease；
- 运行设备识别；
- 显存和内存准入；
- 执行证据记录。

模型崩溃不应导致数据库和桌面应用整体崩溃。

## 六、本地 RAG 与 BGE-M3

AetherDB 的文本向量检索不依赖 Ollama，也不依赖云端服务。

项目使用自主管理的 BGE-M3 模型作为默认多语言文本向量核心。

BGE-M3 主要负责：

- 章节向量；
- 实体说明向量；
- 世界观资料向量；
- 跨语言语义检索；
- RAG 上下文召回；
- 章节创作时的相关设定查找。

AetherDB 自己管理模型文件、SHA-256、模型 revision、tokenization、pooling、归一化、向量维度、向量任务、向量空间、后端选择和 ROCm/CUDA/CPU 证据。

核心原则：

> Ollama 和云端模型可以承担生成任务，但不能替代 AetherDB 的核心文本向量模型。

## 七、Ollama 与云端 API 的定位

### 1. Ollama

Ollama 是 AetherDB 支持的本地模型运行时之一。

用户可以使用 Ollama 安装和运行自己的模型，例如用于：

- 章节润色；
- 扩写；
- 续写；
- 改写；
- 翻译；
- 摘要；
- 视觉理解；
- 其他本地创作任务。

AetherDB 不限制用户安装什么模型。

AetherDB 限制的是模型执行时的权限：

- 可以读取哪些文本；
- 可以接收哪些 RAG 上下文；
- 可以使用多少硬件资源；
- 是否允许调用工具；
- 输出是否可以进入正式数据。

Ollama 是执行插件，不是 AetherDB 的数据控制面。

### 2. 云端 API

用户也可以配置：

- 本地自行部署的 OpenAI-compatible API；
- 局域网模型服务；
- 自建服务器；
- 云端大模型 API；
- 云端图像服务。

云端模型不是 AetherDB 的必要依赖。

系统应明确显示本次任务将发送的内容，避免默认上传完整数据库或整本作品。

## 八、多模态创作能力

### 1. 图像生成

支持将章节、人物、场景和世界设定整理成图像生成任务。

执行后端可以是：

- Ollama 支持的本地图像能力；
- 本地图像模型 Worker；
- 用户配置的云端图像 API。

生成结果先进入 temporary asset，用户确认后才成为正式视觉资产。

### 2. 图像检索

支持：

- 文本找图；
- 图片找图；
- 图文组合搜索；
- 按作品、章节、人物、场景和时间状态过滤。

图像模型卸载后，已经生成并保存的视觉向量仍然有效。

### 3. 音频和 TTS

音频模块面向：

- 章节朗读；
- 语音预览；
- 分段生成；
- 发音词典；
- 局部重试；
- 音频合并；
- 采样率和响度规范化；
- 正式音频资产绑定。

### 4. 媒体资产管理

支持：

- temporary/final 状态；
- 审批；
- 章节绑定；
- 人物绑定；
- 场景绑定；
- 时间线绑定；
- 文件哈希；
- 说明和 transcript；
- Range API；
- 清理和迁移。

## 九、AMD Radeon GPU / ROCm 适配

AetherDB 对 ROCm 的要求是：

> 可证明、可阻断、可复现。

项目不会仅凭配置项或 UI 标签宣称模型运行在 AMD GPU 上。

验证包括：

- `/dev/kfd`；
- `/dev/dri/renderD*`；
- `rocminfo`；
- `amd-smi`；
- PyTorch HIP；
- 真实 GPU 矩阵运算；
- 模型 Worker 实际 backend；
- 执行证据；
- 峰值显存；
- 模型 hash；
- 是否发生 fallback。

比赛模式采用 fail-closed 策略：

```text
REQUIRE_ROCM=true
ALLOW_SILENT_FALLBACK=false
ALLOW_UNVERIFIED_MODEL=false
```

如果模型不能在指定 ROCm 后端运行，任务应失败，而不是悄悄改用 CPU 后继续显示“GPU 成功”。

# 十、项目主要优点

## 1. 本地优先和数据主权

用户的小说正文、世界观设定、人物关系、时间线、未发布内容、图像和音频资产默认保存在本地。

核心数据库和文本 RAG 不依赖云端服务。

## 2. 不把 AI 输出直接写入正式设定

模型只负责分析、生成、提议、抽取和分类。

正式写入由 AetherDB 通过校验、ChangeSet、用户确认和原子事务完成。

## 3. 世界观、正文和多模态资产处于同一系统

章节、人物、地点、事件、关系、时间线、图片、音频和模型执行记录位于同一个作品作用域中。

## 4. 模型运行时可替换

用户可以选择 AetherDB 自有模型、Ollama、本地 OpenAI-compatible 服务、云端 API 或远程服务器。

## 5. 用户可以使用自己的 Ollama 模型

高级用户可以使用微调模型、大参数模型、自定义 Modelfile、本地服务器和高性能硬件。

## 6. 资源调度和 Worker 隔离

独立 Worker 降低模型崩溃、显存残留、依赖污染、任务无法取消和多模型抢资源等问题。

## 7. AMD 适配不是展示标签

项目通过实际设备探针、真实运算和 Worker 证据确认 ROCm 运行路径。

## 8. 面向长期创作而非一次性生成

系统关注生成内容来自哪个章节、使用哪些设定、是否有效、是否审核、能否再次检索和复用。

## 9. 前后端和权限边界清晰

数据库写入、权限、模型路由、资源策略和正式审批由后端控制。

## 10. 支持多语言和跨语言检索

系统拥有中英文界面和多语言文本向量能力。

# 十一、当前缺点与已知限制

## 1. 开发环境稳定，但发行版本在不同环境中可能出现运行异常

当前项目在开发环境和已经验证的测试环境中能够稳定运行。

但是，打包后的发行版本在不同用户环境中可能因为以下差异出现异常：

- Windows 版本不同；
- 系统权限不同；
- 安装目录不同；
- 路径包含中文、空格或特殊字符；
- 防火墙或安全软件拦截；
- 端口冲突；
- 缺少运行依赖；
- GPU 驱动版本不同；
- ROCm/CUDA 环境不同；
- Python sidecar 或本地后端启动失败；
- 模型目录或缓存目录权限异常；
- 已有 Ollama 实例占用资源；
- 用户设备上存在其他 AI 程序。

典型表现可能包括：

- 前端打开但后端未正常启动；
- 本地 API 连接失败；
- 模型 Worker 无法加载；
- 动态端口或本地服务被安全软件阻断；
- 模型在某些机器上回退到 CPU；
- 部分多模态功能无法执行。

项目已经在补充动态端口、启动握手、健康检查、进程状态、错误分类、日志导出、Worker 恢复、模型探针和跨环境测试，但当前仍不能保证所有未经测试的系统环境都能像开发环境一样稳定。

## 2. 多模态创作需要用户自行提供模型运行能力

当前发行版本不会默认捆绑所有大型生成模型。

用户进行章节润色、扩写、续写、图像生成、图像优化、视觉理解和其他生成式多模态任务时，需要自行选择至少一种执行方式：

### 方式 A：安装 Ollama

用户可以在本机或服务器安装 Ollama，并安装自己需要的模型。

### 方式 B：配置本地 API

用户可以配置本机 OpenAI-compatible 服务、局域网推理服务、自建服务器或其他本地模型接口。

### 方式 C：配置云端 API

用户可以配置云端大模型或图像生成服务。

因此，AetherDB 提供的是模型路由、数据边界、上下文管理、任务控制、结果审批和资产管理，而不是默认附带所有生成模型和全部推理算力。

## 3. 高质量模型需要较强硬件

较大的文本、视觉和图像生成模型可能需要较大内存、显存、存储空间以及正确的 ROCm/CUDA 环境。

普通用户设备可以运行核心数据库和部分本地检索，但不一定能流畅运行大型生成模型。

## 4. 模型能力和质量不由 AetherDB 完全保证

用户安装的模型可能存在输出质量差异、幻觉、不稳定格式、中文能力不足、资源需求不准确和运行时不兼容。

AetherDB 可以限制数据、资源和正式写入，但无法保证所有第三方模型的生成质量。

## 5. Ollama 是外部运行时

当用户使用自己的 Ollama 实例时：

- AetherDB 可以控制自己发出的任务；
- 不能完全控制其他应用发给 Ollama 的任务；
- 不能随意终止用户自己的模型；
- 不能保证外部 Ollama 更新后所有行为不变。

## 6. 多模态模型仍需要逐个平台实测

一个模型能在 CUDA 环境运行，不代表一定能在 ROCm 环境运行。

BGE-VL、图像生成和 TTS 都需要分别验证 Windows、Linux、ROCm、CUDA、CPU、模型版本、精度、许可证、输出质量和加载卸载稳定性。

## 7. 当前 UI 功能密度较高

项目包含写作、世界观、时间线、AI 设置、模型、向量、媒体、音频、任务和系统状态等功能。

第一次使用可能需要一定学习时间，项目仍需继续优化新手引导、空状态、错误说明、推荐配置和一键诊断。

## 8. 模型下载和许可证需要用户确认

部分模型体积较大，且许可证、再分发和商业使用边界不同。

项目不会在没有确认的情况下自动下载或捆绑全部模型。

## 9. 云端模型仍存在外部数据风险

当用户主动配置云端 API 时，选中的文本、参考图或上下文可能被发送到外部服务。

AetherDB 会尽量显示发送摘要、最小化数据、要求确认、不默认上传完整数据库，并避免记录完整 API Key；但外部服务的数据处理规则仍由该服务提供商决定。

## 10. 当前不是完全成熟的商业发行版

AetherDB V1.31.2 已具备较完整的工程架构和测试体系，但仍处于快速迭代、赛事准备、多环境验收以及安装和发布流程完善阶段。

它更接近一个功能完整、架构清晰、可继续演进的开发版本，而不是已经覆盖所有硬件、系统和普通用户场景的成熟商业产品。

# 十二、部署与使用要求

## 1. 核心数据管理

核心数据库、章节、世界观、文本检索和本地 BGE-M3 能力由 AetherDB 管理，不要求用户配置云端 API。

## 2. 文本生成和创作辅助

用户需要安装 Ollama 并配置本地模型，或配置本地 OpenAI-compatible API，或配置云端 API。

## 3. 图像生成

用户需要本地图像运行时、Ollama 支持的对应能力，或云端图像 API。

## 4. 音频和 TTS

需要安装经过 AetherDB 模型包和 Worker 合同支持的 TTS 模型。

## 5. AMD ROCm

需要支持的 Linux 环境、正确的 AMD GPU 驱动、ROCm、可访问设备节点和经过验证的模型后端。

# 十三、项目安全边界

AetherDB 的安全原则包括：

- API Key 不通过 URL 参数传递；
- 私有 Key 不进入发行包；
- 前端不直接访问模型运行时；
- 模型不能直接访问数据库；
- 模型不能直接执行 Shell；
- 模型不能直接修改正式数据；
- 媒体通过受认证 API 访问；
- 用户数据不进入源码包；
- 日志和诊断信息进行脱敏；
- 模型权重需要 manifest、SHA-256 和许可证门禁；
- ROCm/CUDA 状态以实际证据为准。

# 十四、项目差异化价值

与普通 AI 写作工具相比：

```text
普通 AI 写作工具：
输入文字
→ 模型生成
→ 用户复制结果

AetherDB：
作品数据库
→ 章节和世界观作用域
→ 本地检索
→ 上下文审批
→ 模型执行
→ 临时结果
→ 用户确认
→ 正式章节或媒体资产
→ 后续继续检索和复用
```

AetherDB 的重点不是替代所有模型，而是让不同模型在一个有数据边界、有上下文、有资源治理、有审批流程的创作系统中工作。

---

# 十五、赛事展示重点

建议赛事演示突出：

1. 打开作品和章节。
2. 展示结构化人物、关系和世界设定。
3. 使用本地 BGE-M3 检索相关上下文。
4. 将作者确认的上下文交给本地模型或 API。
5. 生成或润色文本。
6. 生成视觉内容并进入临时资产。
7. 审批并绑定章节或人物。
8. 生成章节音频或语音预览。
9. 展示 Worker、模型、设备和 ROCm 执行证据。
10. 展示模型失败不会直接污染正式数据库。

# 十六、结论

AetherDB V1.31.2 的核心优势是：

- 本地优先；
- 数据主权；
- 原生文本 RAG；
- 结构化世界观；
- 可审核 AI 流程；
- 多模态资产绑定；
- 可替换模型运行时；
- Worker 隔离；
- AMD ROCm 真实执行证据；
- 面向长期创作的完整工作流。

当前主要缺点是：

- 开发环境较稳定，但发行版本在不同系统环境中仍可能出现运行异常；
- 多模态生成和高级创作需要用户自行安装 Ollama、配置本地 API 或配置云端 API；
- 大型模型对硬件、驱动、存储和运行环境有较高要求；
- 不同模型和平台仍需要持续验证；
- 当前版本仍处于快速迭代和跨环境完善阶段。

项目不会通过隐藏这些限制来夸大成熟度。

AetherDB 当前更准确的定位是：

> 一套已经形成完整工程闭环、具备真实本地模型和 ROCm 验证能力，并正在完善跨环境发行稳定性与多模态执行器的本地优先创作系统。
