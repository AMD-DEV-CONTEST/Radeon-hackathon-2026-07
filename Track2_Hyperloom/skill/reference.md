# Reference — toolkit + hard-won gfx-specific switches

All scripts are in `scripts/`. They are arch-generic (pass the gfx target); the notes below are what they solved so you don't lose a week to the same wall.

## scripts/scan-isa-gfx.sh `<gfx>`  — Step-0 ISA capability census (L1 ground truth)
`llvm-mc`-based PRESENT/ABSENT classification of every matrix/dot/scale/convert instruction. The assembler cannot lie. **Bypasses the clang builtin arity-before-target-feature false positive** — a bare `(void)__builtin_amdgcn_...` compiles even for a GATED builtin, so a compile-probe is NOT proof of availability; `llvm-mc` assembling the mnemonic for the arch IS.

## scripts/disasm-gfx.sh `<kernel.hip> [gfx] [regex]`  — verify emitted ISA (L4/L5)
Compiles with `hipcc --offload-arch=<gfx> --save-temps` and shows the real device ISA — so you VERIFY which instruction a matmul resolves to instead of asserting it (catches silent compiler fallbacks). NB: the common gfx90a/`amdphdrs`/Code-Object-v1 recipe is stale — modern ROCm is COv5 via lld; use `--save-temps` / `clang-offload-bundler --unbundle`.

## scripts/unused-isa-sweep.sh `<build_dir> [gfx]`  — the reverse audit
Recompiles every compute kernel in a build with `--save-temps` and cross-references emitted ISA against the PRESENT census → the definitive "in silicon, 0 uses" list. Reliable per-kernel recompile via `compile_commands.json`; do NOT trust `roc-obj`/.so unbundle for this (flaky). Grep the `.s` directly for mnemonics — the `.s` IS the human-readable ISA (do not run `llvm-objdump` on a `.s`).

## scripts/magpie.sh `<analyze|compare> ...`  — kernel evaluation (AMD Magpie)
Compile + correctness + rank implementations vs a baseline. USE THIS instead of hand-rolling a bench harness. **RDNA4 closed-loop recipe:**
- Perf backend = `metrix` (NOT the default `rocprof-compute`, which is CDNA-only/dead on gfx12xx). metrix has a `gfx1201` backend and wraps `rocprofv3` → duration + HBM BW util + L2 hit.
  `pip install "metrix @ git+https://github.com/AMDResearch/intellikit.git@<sha>#subdirectory=metrix"`
- One-time gotcha: the SDK `rocprofv3` shebang is `#!/usr/bin/env python3`; if it resolves to a python without pyyaml, `metrix` fails `No module named 'yaml'` → `<that-python> -m pip install --no-user pyyaml`.
- `magpie compare` correctness works on gfx1201; its auto-winner scoring weights CDNA `MFMA_FLOPs` (=0 on RDNA4), so **rank by metrix duration**, not the auto-winner label: `metrix profile --profile quick -- ./binary | grep -oE 'avg=[0-9.]+'` and mean the dispatches. (Tracking: AMD-AGI/Magpie#70.)

## scripts/profile-datapath-gfx.sh `<app...>`  — rocprofv3 counters (perf-level-aware)
Sets the compute GPU to **`profile_peak`** (NOT `profile_standard`) so the memory counters un-gate, then runs `rocprofv3` with a working gfx1201 counter set (GL2C_EA_RDREQ/WRREQ, FETCH_SIZE, GL2C_HIT, GRBM/SQ/TA). Restores AUTO on exit. **Why `profile_peak`:** the counter gating (rocm-systems#5953) unlocks under *any* fixed DPM profile — but `profile_standard`/STABLE_STD throttles the GPU to ~1593 MHz (vs ~2472 boost), silently suppressing any benchmark run alongside it; `profile_peak` un-gates the same counters at *peak* clocks (verified: GL2C_EA_RDREQ_sum 0→1.32M @ 2332 MHz). Use the SDK-matched `rocprofv3` (version skew vs the app runtime segfaults). rocprof-compute/Omniperf are CDNA-only — do not use on RDNA4. **General rule: bench at perf-level=auto; only ever use a fixed profile for counter collection, and restore auto after.**

## gfx1201 (RDNA4) instruction cheat-sheet (llvm-mc-verified PRESENT)
Matrix: `v_wmma_f32_16x16x16_{f16,bf16,fp8,bf8}`, `v_wmma_i32_16x16x{16_iu8,32_iu4}`, `v_swmmac_f32_16x16x32_fp8`, `v_swmmac_i32_16x16x64_iu4`. Dot: `v_dot8_i32_iu4`, `v_dot4_i32_iu8`, `v_dot4_f32_fp8`, `v_dot2_f32_f16`. GATED/ABSENT (do not chase): `v_dot2c_f32_f16` (dual-issue), all `v_cvt_scalef32_*` scale-units (gfx950/1250-only). Builtins: `__builtin_amdgcn_sudot8` → `v_dot8_i32_iu4`; `__builtin_amdgcn_sudot4` → `v_dot4_i32_iu8`; `__builtin_amdgcn_swmmac_i32_16x16x64_iu4_w32`.
**2:4 SWMMAC — BUILT + TUNED on gfx1201 (2026-07-27):** `Sparse=2` weight-compression via TensileLite-generated `v_swmmac_i32_16x16x32_iu8`/`_iu4` (K=32 tile) BEATS dense hipBLASLt **+7–18%**, live through the hipSPARSELt API (270 TFLOPS, exact; 97.5% HellaSwag on Sparse-Llama-8B-2of4). Silicon quirk: `swmmac_iu4` reads the 2 per-group idx fields **SWAPPED + XOR-1** (pos(HIGH)=idx1^1, pos(LOW)=idx0^1). PREFILL/GEMM only — 2:4 is a NO-GO for batch-1 decode/GEMV (gather can't amortize at M=1). Build tree `/aipool/hipsparselt-build/`; how-to = the "generator" section below.

## Whole-substrate levers — detect the part, reach for what it actually has
The HIP toolkit above targets the GPU rows; the assembler-ground-truth discipline is the same everywhere, but the lever changes with the silicon. Never apply a gfx1201 conclusion to a part that has different units.

**CDNA GPU (gfx908/90a/942 — MI100/MI250/MI300):** Wave64 + **MFMA** (`v_mfma_*`), NOT WMMA — a WMMA-shaped kernel won't emit anything here. Throughput/batch-oriented (huge HBM), not batch-1 latency. Profiler: rocprof-compute/Omniperf DO work here (the opposite of RDNA4). Runtime lever = vLLM/SGLang tensor-parallel.

**CDNA4 gfx950 (MI350) + RDNA-next gfx1250:** the **native-MX** parts. `v_cvt_scalef32_*` scale-convert units + MX-WMMA (MXFP4/6/8 with hardware block-scale) + fp4-cvt are PRESENT here — **exactly the mnemonics `scan-isa-gfx.sh` reports GATED/ABSENT on gfx1201.** The arch check must FLIP: on gfx1201 MX is convert-only/software (pack in ggml, ride the fp8 dot path); on gfx950/gfx1250 it's a native matrix+scale lever. Re-run the ISA census per-part before assuming a lever ports.

**Zen CPU (znver3/4/5 — EPYC · Threadripper · Ryzen):** matmul lever is **AVX-512-VNNI** int8 (`vpdpbusd`) + AVX-512-BF16 on Zen4/5; Zen3 is AVX2-only (lower int8 throughput). Framework = **zentorch** (AMD torch backend) or **vLLM-CPU**. Bandwidth+SIMD-bound → single-socket pinning (`numactl --cpunodebind=0 --membind=0`; vLLM scales poorly across sockets). Threadripper/TR-PRO = the many-core + quad/octa-channel tier (higher throughput than desktop Ryzen, single-socket so no cross-socket penalty). Ref: `amd/skills serving-llms-on-epyc`.

**Ryzen AI NPU (XDNA1/2 — Phoenix→Strix):** int8/int4 on the **AIE** tiled array (~10–16 TOPS XDNA1, ~50 TOPS XDNA2). No HIP — path is **Ryzen AI SW / ONNX-Runtime / Lemonade**; quantize to the NPU's supported types. Power-efficient decode offload, not a GEMM firehose.

**APU (Strix Halo / Strix Point / Phoenix — CPU+iGPU+NPU, one chip):** the distinguishing lever is **unified memory** (up to 128 GB LPDDR5X, zero-copy between engines → big models fit, no PCIe hand-off) + **hybrid partition** (NPU = power-efficient decode, iGPU = parallel prefill via the gfx WMMA path, CPU = orchestration/overflow). The wall is *shared* LPDDR bandwidth → byte-width is everything: aggressive int4/mxfp quant + spec-decode. Decompose the APU into its `engines[]` (e.g. Strix Halo = znver5 + gfx1151 iGPU + xdna2 NPU) and apply each engine's row above; **Lemonade** auto-routes across them.

## When the library doesn't ship your silicon's capability — go up a layer to the GENERATOR (gfx1201 2:4, verified 2026-07-27)
The L1 census can report a matrix/sparse instruction **PRESENT in silicon** that **NO shipping library exposes** for your part — the vendor scoped the tuned kernels to a different arch. That gap is not a dead end; it's a build target one layer above the kernel:
1. **Confirm the real gap — don't trust the status line.** `scan-isa-gfx.sh` says the instruction exists (e.g. `v_swmmac_i32_16x16x32_iu8` on gfx1201); the shipped library (hipSPARSELt/hipBLASLt) returns NOT_SUPPORTED / 0 solutions for your gfx. Verify BOTH ends yourself — the library's arch allow-list, the Logic/asm catalog (`grep` the sparse configs for your gfx), a runtime probe. "Present in silicon, absent in library" is the signature.
2. **Build it from the vendor's own kernel GENERATOR.** hipBLASLt/hipSPARSELt kernels come from **TensileLite** (CK from `ck_tile`); the generator often has a *generic* path covering your arch even when no tuned Logic ships (gfx1201: the wave-32 `HasSWMMAC` path at K=32, vs gfx1250's K=64). Adapt a neighboring arch's config to your tile, generate, correctness-gate on silicon.
3. **Be ready to FIX the generator's bugs** — the untrodden path is buggy precisely because no one shipped it. Two real, general, upstream-worthy gfx1201 examples: a **RegisterPool checkIn/checkOut predicate mismatch** leaking a VGPR that blocked ALL `Sparse=2` codegen whenever A/B widths diverge; a **dense int8 WMMA accType** taken from ComputeDataType(f32) instead of i32 → invalid mnemonic. Vendor-tool codegen bugs, not your arch's fault.
4. **This is a portable METHOD, not a portable CONCLUSION.** gfx1201's *answer* ("2:4 beats dense at K=32, +7–18%") does NOT transfer: gfx942/950 already SHIP tuned 2:4 (verify it's tuned for YOUR shapes; don't rebuild it); gfx1100/1151 have different WMMA and **no SWMMAC at all**. Each part re-runs the playbook (census → library-coverage check → generator build → measure) for its OWN truth.

## Two sparsity/quant sub-lessons that generalize (verified 2026-07-27)
- **Compress the DOMINANT byte-mass, not the convenient operand.** A whole 2:4 campaign LOST because it compressed operand A (activations ≈ 1.5% of GEMM bytes); switching to `Sparse=2` (operand B = WEIGHTS ≈ 98.5% of bytes → 1.76× total byte reduction) is what made sparse BEAT dense. Before compressing anything, compute which operand owns the bytes at your M/N/K — roofline arithmetic, not defaults.
- **Beat the TOUGHEST baseline, then prove it isn't hobbled.** "Sparse beats dense" is meaningless if "dense" is a weak same-tool kernel. Integrity move ("does dense have the same issue?"): compare against the vendor's STRONGEST dense (hipBLASLt-dense beat our own TensileLite-dense by 11.6–18.4% — we still won vs the strongest → the win is real, not a hobbled-baseline artifact). Always name the baseline and show it's the hard one.
- **The narrative layer lies even when the runs don't — recompute the comparison.** Two failure modes observed in ONE session (gfx1201 IU4 decode GEMV, 2026-07-29), both with *correct, reproducible raw runs* but *wrong written verdicts*, in OPPOSITE directions:
  1. **Strawman over-claim** — dot8 measured 1.5–1.7× vs a baseline labeled "dp4a" that was actually a naïve scalar unpack loop (the code comments admitted it). Fix = the toughest-baseline rule above + label baselines by the instruction disasm proves they emit.
  2. **Ratio-inversion under-claim** — same agent then built a REAL dp4a baseline, measured correctly (dot8 0.086 ms vs 0.115 ms), but computed `candidate/baseline = 0.75` and reported dot8 as "0.75× slower." Truth: `baseline/candidate = 1.34×` → dot8 is FASTER. **Speedup = baseline_time ÷ candidate_time; faster = less time.** State which kernel is faster in words, then the ratio, and reject any verdict whose direction contradicts its own printed times.
  ⇒ Trust the raw per-shape times + `max_err`; do NOT trust the written speedup/verdict until recomputed from those times. When driving a sub-agent (esp. a local model), have it emit raw times for both arms and recompute the ratio yourself — its execution is reliable, its arithmetic/narrative is not.
- **Three MORE comparison failure modes, one batch (gfx1201 Phase-1 shortlist, 2026-07-29 — a local agent, 4 kernels).** The raw execution (running code, `max_err=0` gates) was trustworthy every time; the comparison/verdict layer failed every time, a DIFFERENT way each:
  1. **Broken/pathological baseline** (fp8 dot4): reported 28×; the "baseline" ran ~9 GB/s (vs candidate's sane ~247 GB/s) and threw **Inf** at one shape. ⇒ disqualify any baseline with nonzero error; treat a >2–3× bandwidth-bound speedup as a baseline bug, not a candidate win.
  2. **Analysis substituted for measurement** (Q4_K dot8): no timing table at all, and the two compared kernels were identical software code (no inline-asm, same disasm) with different labels — a reasoned "the scale/min ALU dominates" dressed as a verdict. ⇒ no measured times = no verdict; disasm-confirm the arms actually emit DIFFERENT instructions.
  3. **Unverified "shipped" baseline** (2:4 SWMMAC occupancy sweep): a clean, reproducible grid that correctly found WARPS=16/ILP=2 fastest — but claimed "1.5× over shipped" where the "shipped WARPS=32/ILP=4" was assumed, never read from the dispatcher. ⇒ a production baseline must be the config actually instantiated in source, or labeled unverified.
  (Also banked: opencode headless auto-rejects agent access to `/tmp` — a run lost its deliverable to `/tmp` scratch. Set `TMPDIR` inside the sandbox and keep all scratch under the working dir.)
- **The reviewer's OWN measurements failed the same discipline — twice — until forced honest (gfx1201 2026-07-30).** Chasing "is anything better than the committed kernel?":
  1. **False gap → reinvention.** The whole hunt started from "IU4 decode is at ~50% of roofline, ~2× to gain." Wrong: that 50% was measured on the AGENT's naive reinvented PoC, while the LIVE committed kernel (`mmvq_iu4.cu`, T170) was never benched. Always measure the *dispatched* kernel, not a stand-in.
  2. **Cache-warm bandwidth.** Re-benching the committed kernel on a small buffer gave 336 GB/s AND **147% of roofline** at another shape — the >100% flag proved it was measuring Infinity Cache, not DRAM. Re-run with a 130–150 MB working set (≫ cache) → the committed kernel is **95–97% of the 631 GB/s roofline**: already near-optimal, NO ~2× headroom. The entire premise for a "better" kernel was a measurement artifact.
  ⇒ Compute % of roofline on EVERY bandwidth number specifically so `>100%` trips as a self-alarm; size buffers to real decode (cold DRAM), not to whatever fits. A negative, honestly measured ("the committed code is already good") is the correct result — do not manufacture a gap to have something to build.

## Failure signature to self-check: the pessimistic bound declared from an untested coordinate
The most common false verdict here is not an over-claim — it's a **premature KILL**: declaring a lever dead ("washes to ~1%", "not worth it", "loses on every axis") from a coordinate never actually measured (a buggy kernel, the wrong operand, an unread source). gfx1201 2:4 was called dead ~5× and reversed to a WIN each time once measured under the fixed coordinate. Rule: a KILL is a MEASURED result under the current coordinate, or it is an **ASSUMPTION wearing a verdict's badge** — as inadmissible as a fabricated win. When you catch yourself closing a door, ask: *have I measured THIS coordinate, or an adjacent one?*

## Environment traps
- `ROCR_VISIBLE_DEVICES` overrides `HIP_VISIBLE_DEVICES`; setting it (even empty) can force silent CPU fallback. Pin with `HIP_VISIBLE_DEVICES` and leave `ROCR` unset.
- ROCm = two decoupled layers: kernel `amdgpu-dkms` (own version) vs userspace SDK (pip/TheRock — don't assume `/opt/rocm-X`). `ldconfig` may resolve an old shadow — LD-force the right libs.

## Measurement integrity — a number is a TUPLE, not a scalar
Every measured t/s is valid ONLY relative to `{ binary-sha, GPU/HIP_VISIBLE_DEVICES, perf-level, load, ROCm-hip-lib, model+dtype, prompt-class, n/batch }`. Change **any** coordinate and the number is **stale** (unverified), not wrong — and a stale number looks identical to a fresh one. This is the single biggest source of false conclusions in this work (numbers vacated for exactly this: `47.8` hot vs `50.9` cold = load; GPU1-with-Xorg vs GPU0 = +9.4% spec; a 10-hr-stale binary that faked "async broken"; F32-vs-native head +9.6%; perf-level `high` −17%). Four rules:
1. **Co-measured A/B only** — never compare a fresh number to a *cached* baseline; re-measure BOTH arms back-to-back, identical tuple except the one variable.
2. **Provenance stamp** — record the tuple with every number (`hardware.provenance(binary, model)` captures binary-sha/mtime + which `libamdhip64` it resolves + perf-levels + power + load + HIP/ROCR devices). An unstamped number is inadmissible.
3. **Cold-gate** — `hardware.cold_gate()` first; load > ~8 depresses t/s ~6% → refuse to record.
4. **Invalidation cascade** — on any global change (rebuild, ROCm bump, GPU reassignment), treat ALL prior numbers under the old coordinate as stale.

The one number that does NOT drift is the **roofline** (`bytes/token ÷ bandwidth` = physics — a kernel edit can't move it). Grade **%-of-roofline**, never "faster than last time": anchor to the fixed ceiling, measure everything else relative. Measurement discipline and the roofline method are the same defense.

## Spec-decode vs the roofline (verified — cards 147/145)
The memory roofline bounds **single-token** decode only. MTP/DFlash verify N draft tokens per weight-read, so their ceiling ≈ `roofline × mean-accept-length`, **discounted** by draft+verify+dispatch overhead and **hard-capped** by accept rate. Whether spec-decode EXCEEDS the roofline depends on the raw regime:
- **Memory-bound raw** (fp8-27B at 18.6 = its roofline): spec-decode blows past — but the multiplier is **content-class-dominated, not a hardware constant**: code prompt **3.50× (64.9 t/s, n9)**, technical-explain **1.67× (n5)** — measured range **1.67–3.5×**.
- **Dispatch-bound raw** (Bonsai Q2_0 = 51 ≪ 77 roofline): draft+verify pay the **same** launch tax, so gains are partly eaten → trained MTP head reached **~64–65 t/s, still below the 77 roofline** (closed the gap, did NOT exceed it). ⇒ cutting the dispatch tax first is the **precondition** for spec-decode to break the roofline here.
- **Batch-1 kernel wins compound only weakly into spec-decode** (measured): the dedup dispatch cut lifted MTP just **+0.67%** because its `ne11==1` gate fires on the batch-1 **draft** step, not the **batched verify** pass that dominates spec-decode compute. ⇒ the **verify-pass forward** (batched N-token, still single-stream latency) is the distinct lever for further single-stream spec-decode gain — a different target than batch-1 dedup/fusion.

Accept rate is the real lever: a cheap 1-block MTP head structurally caps ~62–71% single-step (130× smaller approximation of the backbone); 100% accept is self-draft-only (same model, expensive). **Self-learning caveat (verified dead ends):** online/recursive/multistep refinement of the 1-block head DEGRADES accept (on-policy 87→76%, multistep 68→58). The ONLY capacity lever is a **multi-block head** (`n_layer_nextn>1`) — llama.cpp hard-asserts `==1`, so it's train-from-scratch + llama.cpp surgery. Do NOT online-refine the 1-block head.

## Requant-routing, M-curves, and the serving lever (prefill + L7, verified gfx1201 2026-07-31)
A whole quant-routing campaign (route every quant onto the library GEMM, PPL-gate, M-sweep, then serve) produced five PORTABLE method lessons. The arch-specific route table + MTHRESH values live in the gfx1201 agent file; the METHOD is here.

1. **Requant-onto-GEMM is the prefill route, and it is RANGE-DEPENDENT.** To run a sub-8-bit quant on a tuned library GEMM (hipBLASLt/Tensile), dequant the weight then re-quant it to a hardware-GEMM type: per-channel **int8** or **fp8-e4m3**. The choice is set by the source's per-block dynamic RANGE, not its bit-width: low-bpw narrow-range (binary/ternary) → int8 wins (fits, near-lossless); wide per-block scale variation (k-quant, 8-bit-with-per-block-scale) → **fp8 wins because its EXPONENT preserves the range that folding many per-block scales into ONE per-row int8 scale COLLAPSES** (measured: int8 was FASTER on Q4_K/Q8_0 but FAILED the PPL gate; fp8 passed). ⇒ **int8 is always the fastest and silently breaks correctness on wide-range quants — the PPL gate is MANDATORY on every requant route; never ship int8 on speed alone.** (Predicting "int8 wins on an 8-bit source" was FALSIFIED — it's range, not mantissa.) The requant byte-win does NOT help *compute-bound* prefill via an int4/WMMA path (that stays a decode-only lever); the win is that a low-bit quant gets to ride the same tuned GEMM every float quant already uses.

2. **M is a curve, not a point — one M is not a verdict.** The GEMM's M = `min(prompt_len, n_ubatch)`, and `llama-bench pp1024` runs at M=512 — so a "pp1024 win" is a SINGLE M=512 reading, mislabeled. Heavy-unpack requant routes (binary/2-bit/k-quant) REGRESS at small M (unpack+requant not amortized over few rows against a strong small-M mmq) and win monotonically at large M; cheap-dequant routes (int8×scale, native-fp8, nibble-int4) win at every M. **Sweep M (e.g. 64…2048) and gate each heavy route behind a measured-crossover threshold (MTHRESH); leave cheap routes ungated.** The regression here was found only by an independent review AFTER a single-M bench had declared a real +17/+26% victory — the win was true at M=512 and a −44% loss at M=64. The discriminator is dequant COMPLEXITY vs a strong small-M mmq, NOT int8-vs-fp8 (a fp8 k-quant route still regresses). A too-HIGH threshold never regresses (the route soft-fails to mmq below it) — it only leaves wins on the table, so err high.

3. **Calibrate a crossover at GRAPH level, never in an isolated tight loop.** An in-kernel micro-timer that A/Bs the route vs mmq in a few-iteration loop PIPELINES the route's kernels (act-quant/GEMM/scale overlap across iters) and HIDES the per-call dispatch overhead that dominates small-M in a real graph → it mis-fires and engages the route in its regression regime. A graph-level A/B (a real forward pass with real dispatch gaps and a downstream consumer) sees the TRUE end-to-end cost and correctly abstains. Two measurement facts fall out: **ratios are stable within a clock state (<1% back-to-back) but absolutes swing ~3× under DPM clock bounce → pin perf-level for measurement (or rely only on the back-to-back on/off RATIO), and the crossover MOVES with clock (the sign can flip: a route that wins at pinned-high loses at a throttled clock).** And the crossover is **per-model, tracking HIDDEN-SIZE (bigger model → higher crossover), roughly independent of FFN-K** — it refutes any `1/(N·K)` shortcut. ⇒ a fixed hand-tuned threshold is fine within a validated model-size range; a NEW/larger model needs an in-situ graph-level warmup calibration at the production clock before you trust it.

4. **The serving layer (L7) is a first-class throughput lever, often the biggest and cheapest.** When a decode-bound model is at its single-stream kernel floor, the remaining 3–14× is **continuous batching**: the parallel-slot count (`-np`/`--parallel`) is PER-MODEL and VRAM-coupled to ctx-per-slot, so pick it by the **MEASURED throughput KNEE — argmax of aggregate t/s, then stop at the first step whose marginal gain <3% (the flat tail, just before the over-subscription cliff)** — NOT the blind VRAM-fit maximum. Measure the sweep clock-pinned with adequate generation length (a too-short ntg makes the aggregate number garbage). A smaller model batches far wider than a bigger one (measured: an 8B knee ~np96 with a hard cliff at 128 vs a 27B knee ~np16–48). This is near-free (the scheduler already exists) and worth more than any remaining kernel micro-opt on a batchable workload.

5. **Know which artifact you're editing — advisor vs engine — and prove the passthrough.** A config-ADVISOR (picks/writes a knob) is not the serving ENGINE (the compiled binary that reads it). Before trusting that a knob reaches the launched process, verify the passthrough EMPIRICALLY: does the engine actually forward that arg? (Here: the launcher sweeps and caches `-np`; a separate advisor consumes the cache and injects `--parallel` into the one arg-string the server binary forwards — two different programs, and the injection is worthless if the forward path is wrong.) Same discipline as "verify the gap is open in the LIVE dispatched kernel," applied to serving config.

6. **Strategic stop rule: know when the lane is saturated.** When the committed decode kernels sit at 95–97% of the measured (cache-honest) roofline, the kernel lane is DONE — further ISA work is <5% for disproportionate effort. The next 20–40% lives one level UP: accept-rate (multi-block MTP), active-bytes-per-token model co-design, or serving throughput (continuous batching / data-parallel across GPUs). Polishing a saturated kernel is the inverse error of manufacturing a gap — both waste the budget. Relatedly, a huge speedup that merely RESTORES a self-inflicted slow default path (e.g. a model that was dispatching to an experimental slow kernel getting routed to the path every sibling quant already used) is **baseline-repair, not a net-new optimization** — real and worth shipping, but do not report it as a novel kernel win.
