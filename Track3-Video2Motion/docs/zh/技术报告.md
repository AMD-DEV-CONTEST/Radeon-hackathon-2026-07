**一段普通视频 → 一个可部署的人形机器人控制策略，全流程运行在 AMD ROCm 上**

AMD AI DevMaster Hackathon 2026 · 赛道三 物理 AI

## 摘要

用户上传一段人做动作的普通视频，系统自动完成**姿态估计 → 动作重定向 →
强化学习训练 → 三层跨仿真器验证**，产出一个可以通过 DDS 直接下发给
Unitree G1 的控制策略。全程带网页界面，不需要写一行代码。

整条流水线运行在 **Radeon Pro W7900（gfx1100）+ ROCm 7.2.1** 上。
这不是把 CUDA 代码换个后端就能完成的移植 —— 这个领域的主流工具链
（Isaac Lab、Isaac Sim、MuJoCo Warp、unitree_rl_mjlab、以及 BeyondMimic
的官方实现）**全部只支持 CUDA**，我们必须重新选型并补上缺失的环节。

**核心结果**：训练出的策略在三层递进验证中全部通过，其中第三层运行在
**宇树官方仿真器 + 官方 G1 模型 + DDS 通信**上，与真机完全同一套代码路径。

| 验证层 | 物理引擎 | 机器人模型 | 推理 | 接口 | 完成度 | body 位置误差 |
|---|---|---|---|---|---|---|
| 零动作基线 | — | — | — | — | 44/156 (28.2%) | 0.0772 m |
| **层 1** | MuJoCo MJX (JAX/GPU) | Playground G1 | brax 网络 | 直接读内存 | **156/156 (100%)** | **0.0269 m** |
| **层 2** | MuJoCo 原生 C (CPU) | Playground G1 | **纯 NumPy** | 直接读内存 | **156/156 (100%)** | **0.0273 m** |
| **层 3** | MuJoCo 原生 C | **宇树官方 G1** | 纯 NumPy | **DDS** | **156/156 (100%)** | 关节误差 4~5° |

## 一、问题与产品定位

### 1.1 要解决什么

让人形机器人学会一个新动作，目前的门槛是三重的：

1. 需要动捕设备或现成的动捕数据集；
2. 需要懂强化学习的人为每个动作调奖励和超参；
3. 训完还要处理 sim2real，这一步失败率极高。

我们的目标是把它压缩成：**上传视频 → 等 → 拿到能用的策略**。

### 1.2 一个关键的产品判断：不做统一策略

一个自然的想法是训练一个能做所有动作的通用策略。我们**明确不这么做**，
因为它和产品形态冲突：用户传进来的是一段**任意**视频，
不可能事先把所有动作枚举进训练集。

我们要的是另一件事 —— **一套超参数，让大多数动作都能收敛**。
每条动作训出自己的策略，但**不需要人为每条动作调参**。
这两件事正交，容易混淆：

| | 一套策略做多个动作 | 一套超参训多条动作 |
|---|---|---|
| 产物 | 1 个权重 | N 个权重 |
| 加新动作 | 要重训全部 | 独立训练，互不影响 |
| 对我们的意义 | ❌ 与「任意视频」冲突 | ✅ 自动化的前提 |

BeyondMimic 走的也是「每条动作一个策略 + 同一套超参」。我们参照它的
方法论，但实现完全独立（原因见第二节）。

## 二、平台约束：为什么必须重搭技术栈

### 2.1 主流方案在 AMD 上全部不可用

| 方案 | 阻塞点 |
|---|---|
| Isaac Lab / Isaac Sim | 闭源，仅 CUDA |
| MuJoCo Warp | 依赖 NVIDIA Warp，仅 CUDA |
| unitree_rl_mjlab | 依赖 MuJoCo Warp，间接仅 CUDA |
| BeyondMimic 官方实现 | 依赖 Isaac Lab 2.1.0 + Isaac Sim 4.5.0 |
| BeyondMimic 的 mjlab 复现 | 依赖 MuJoCo-Warp |

**唯一可行的大规模并行仿真路径是 MuJoCo MJX（JAX 后端）**，配 JAX-ROCm
和 Brax PPO。这意味着 BeyondMimic 的算法我们只能**照着源码在 MJX 上重写**，
逐项对齐奖励公式、权重、std 和终止阈值。

### 2.2 gfx1100 上实测到的两个硬限制

**(1) XLA 编译图规模上限。** 当

```
num_minibatches × num_updates_per_batch > 32
```

时 XLA 在代码生成阶段段错误，Python 层没有任何异常。已排除显存
（48 GB 只用了 28 MB）、`pmap` 本身、环境实现 —— 是 gfx1100 后端的编译器
限制。本项目用 `16 × 2`。

**(2) brax 与 JAX 0.11 不兼容。** brax 0.14.2 调用了 JAX 0.11 已随 pmap
迁移移除的 `jax.device_put_replicated`。NVIDIA 用户可以降级 JAX 绕过，
**AMD 用户不能** —— JAX 版本被 `jax-rocm7-plugin` 锁定。只能打兼容垫片，
且必须在 `import brax` 之前注入。

两条都已整理为上游贡献素材。

## 三、系统设计

```
  用户视频 (mp4)
       │
       ▼  GVHMR                        62 秒 / 3.2 秒视频（AMD GPU）
  SMPL-X 人体姿态序列
       │
       ▼  GMR (CPU / 逆运动学)
  G1 29 自由度关节轨迹
       │
       ▼  gmr_to_mjx.py + motion_prep.py
  MJX 格式动作文件（含 14 个 body 的位姿与速度）
       │
       ▼  Brax PPO on MJX             357 分钟 · 4096 并行环境 · 371M 步
  策略权重
       │
       ▼  纯 NumPy 导出                251,066 参数，零 JAX 依赖
       │
       ├──▶ 层 2  原生 MuJoCo 验证
       └──▶ 层 3  unitree_mujoco + DDS ── 同一套代码可直接接真机
```

### 3.1 训练环境：BeyondMimic 配方的 MJX 移植

**为什么不能沿用「跟踪上肢关节角」的简单做法**

我们最初的方案继承 MuJoCo Playground 的 G1 Joystick 环境，把速度指令固定为
零来复用它的站立能力，再叠加一个上肢关节角跟踪奖励。指标很漂亮：
「500/500 步不摔，上肢跟踪误差 19.66°」。但视频里机器人一直踉跄、
手臂做不出动作。

原因是**两个错误的成功标准**：

- 「没摔倒」—— 站着不动也满分；
- 「关节角误差」—— 和视觉上「像不像」的相关性很弱，而且摔倒后手臂
  仍在动，误差照样小。

更根本的是**奖励结构让「站着不动」成为最优解**：环境只在摔倒时终止，
所以不摔 → episode 跑满 → 累计奖励高，跟踪项只占单步奖励的一小部分。

**BeyondMimic 的做法与之完全不同**

| | 旧方案 | BeyondMimic 配方 |
|---|---|---|
| 跟踪对象 | 上肢 14 个**关节角** | 全身 14 个 **body link 的三维位置/朝向/线速度/角速度** + 根节点 |
| 下肢 | 只有「靠近默认站姿」正则 | 一起跟踪 |
| **终止条件** | 只在摔倒时终止 | **跟踪误差超阈值即终止** |
| reset | 永远从站姿、动作第 0 帧 | **RSI**：参考轨迹随机时刻的完整状态 |
| 奖励 | 继承 joystick 一堆 locomotion 项 | 6 项跟踪 + 3 项惩罚，无残留 |

**逐项对齐的奖励**（对照 `tracking_env_cfg.py`，形式统一为 `exp(−误差/std²)`）：

| 项 | 权重 | std |
|---|---|---|
| `motion_global_anchor_pos` | 0.5 | 0.30 |
| `motion_global_anchor_ori` | 0.5 | 0.40 |
| `motion_body_pos` | 1.0 | 0.30 |
| `motion_body_ori` | 1.0 | 0.40 |
| `motion_body_lin_vel` | 1.0 | 1.00 |
| `motion_body_ang_vel` | 1.0 | 3.14 |
| `action_rate_l2` | −0.1 | — |
| `joint_limit` | −10.0 | — |

终止：`anchor_z > 0.25 m`、anchor 朝向 > 0.8、四个末端 `z > 0.25 m`、超时。

### 3.2 为部署而做的观测取舍

宇树 SDK 的 `LowState` 只提供四项：

```
motor_state[i].q        29 个关节角
motor_state[i].dq       29 个关节速度
imu_state.quaternion    骨盆姿态
imu_state.gyroscope     骨盆角速度
```

**没有躯干线速度**（IMU 只给角速度和姿态），
**没有世界位置**（机器人没有全局定位）。

所以策略观测里必须去掉两项，否则训完了根本没法部署：

| 观测项 | 为什么去掉 | 代价 |
|---|---|---|
| 躯干线速度 | IMU 不提供 | 实测：同策略同仿真，仅把它置零，存活从 500/500 掉到 190/500 —— 必须重训 |
| `anchor_pos_b` | 需要躯干世界位置 | 重训一次 |

两项都挪进 critic —— **非对称 actor-critic**：价值网络训练时可以用特权信息，
策略网络不能。BeyondMimic 官方也提供了同样思路的
`Tracking-Flat-G1-Wo-State-Estimation-v0` 配置。

最终策略观测 **154 维**：

```
参考关节角+速度 58 | anchor_ori_b 6 | 陀螺仪 3 | 关节角 29 | 关节速度 29 | 上一步动作 29
```

**这个取舍必须在训练前做完** —— 训完再裁维度就得重训。

### 3.3 一个必须处理的坐标系问题

策略在 **torso_link** 坐标系上训练（Playground 的 `gyro_torso` /
`orientation_torso` 传感器），而 G1 的 IMU 装在 **pelvis** 上，
中间隔着三个腰关节。腰一动，骨盆姿态就不等于躯干姿态。

解法是用已有数据做一次正运动学传递：把骨盆姿态和测到的关节角放进一个
只做运动学的 MuJoCo 模型，`mj_forward` 之后读出躯干位姿；角速度用
`mj_objectVelocity`。**不需要任何额外传感器**，仍然是纯 SDK 部署。

实测精度：姿态误差 **0.0000 度**，角速度误差 0.031 rad/s（约 3%）。

### 3.4 部署

策略导出为纯 NumPy 前向（**251,066 参数**，四层 MLP + swish + tanh），
**完全不依赖 JAX**。同一份权重可以跑在原生 MuJoCo、unitree_mujoco、
以及真机的机载计算单元上。

## 四、三层验证

单看训练曲线不足以说明策略可用。我们设计了三层递进验证，
**每一层只换掉一样东西**，出问题才能定位。

| 层 | 换掉了什么 | 过了说明什么 |
|---|---|---|
| 1 | — | 训练收敛了（**仅此而已**） |
| 2 | 物理引擎 + 推理栈 | 策略是独立的数字，不绑定 JAX/MJX |
| 3 | 机器人模型 + 通信 + 信息约束 | 与真机同一套代码路径能跑通 |

**「都是 MuJoCo」这个前提本身不成立**：MJX 是用 JAX 把物理重新实现了一遍
（为了在 GPU 上并行几千个环境），求解器、接触处理、积分都是另一套代码。

层 3 换掉的三样都很实质：

**(1) 宇树官方 G1 模型** —— 动力学参数是另一套：

| 参数 | 宇树官方 | Playground | 差异 |
|---|---|---|---|
| 关节阻尼 | 0.05 统一 | 0.2 ~ 2.0 | **最多 40 倍** |
| 电枢 | 0.01 统一 | 0.0036 ~ 0.0251 | ~3 倍 |
| 总质量 | 35.11 kg | 33.34 kg | +5% |
| 执行器 | `motor`，`ctrl` 是**力矩** ±88 N·m | `position`，`ctrl` 是**角度** ±2.5 rad | 语义完全不同 |
| 碰撞几何 | 全身 | 仅脚部 | — |

**(2) DDS 通信** —— 走宇树 SDK 的 `LowState`/`LowCmd`，引入真实时序。

**(3) 信息约束** —— 只有上面那四项传感器数据。

详细论证见 [`三层验证为什么这么设计.md`](三层验证为什么这么设计.md)。

## 五、最难的部分：把 BeyondMimic 移植到 MJX

移植过程共查出 **8 个 bug**，全过程记在
[`BeyondMimic移植记录.md`](BeyondMimic移植记录.md)。这里只讲最有价值的两个。

### 5.1 根因：Playground 的 auto-reset 不还原 `info`

前 7 个 bug 都是真 bug，但修完之后训练**仍然单调劣化** ——
三轮训练（61M / 61M / 51M 步）全部是：未训练的网络最好，越训越差。

**决定性线索来自消融实验**：

| 组 | 配置 | `ep_len` 走势 |
|---|---|---|
| 基线 | 有惩罚 + entropy 1e-3 | 36 → 19.4 |
| A | 关掉两个惩罚 | 36 → 22.4 |
| B | 关惩罚 + 零熵 | 36 → 20.9 |
| C | 有惩罚 + 零熵 | 36 → 22.5 |

**三组差异很大的配置给出几乎重合的曲线** —— 这说明劣化与奖励构成无关，
问题在所有组**共享**的东西上。

查 Playground 的 `BraxAutoResetWrapper`，文档字符串直接写着：

> If `full_reset` is disabled (default):
>   * the environment will reset to a cached first state.
>   * **only data and obs are reset, not the environment info.**

我们的参考帧索引存在 `info["motion_idx"]` 里。于是第一个 episode 结束后，
**机器人物理状态回到起点，参考索引却继续往前走** —— 两者永久错位。
再加上终止条件里有 `motion_idx >= T−1`，索引走到末帧后每步都 done，
之后全是 1 步的垃圾样本。PPO 从头到尾在拿废数据训练。

修法是一个布尔值：

```python
wrap_env_fn=functools.partial(wrapper.wrap_for_brax_training, full_reset=True)
```

同一份代码、同一套超参，只改这一个值：

| step | reward | `ep_len` | body_pos |
|---|---|---|---|
| 0 | 129.39 | 36.0 | 0.0993 m |
| 12M | 223.50 | 56.6 | 0.0842 m |
| 30M | **311.04** | **76.9** | **0.0773 m** |

### 5.2 动作幅度物理上够不到

这一条与奖励设计完全无关，但单独就足以让手臂动作做不出来。

位置执行器稳态下 `q ≈ ctrl`，而 `ctrl = default_pose + action × action_scale`。
brax 的 `NormalTanhDistribution` 把 action 压在 **[−1, 1]**，
所以关节可达范围就是 `default_pose ± action_scale`。

实测参考轨迹要求的峰值偏移：

| 动作 | 最大需求 | `action_scale=0.5` 能给 | 缺口 |
|---|---|---|---|
| 敬礼 | 右肘 **1.709 rad (98°)** | 0.5 rad (28.6°) | **3.4×** |
| 网球 | 肩滚 **2.051 rad (118°)** | 0.5 rad | **4.1×** |

网球有 **24% 的上肢目标够不到**。手臂物理上抬不起来，训多久都没用。

BeyondMimic 没这个问题是因为它用 rsl_rl，策略是无界高斯、动作不截断。
brax 有 tanh，必须自己保证可达性。修法是目标位置改成相对**参考姿态**：

```python
motor_targets = ref_joint_pos[t] + action * action_scale
```

策略只需输出**修正量**，可达性由构造保证。

### 5.3 验收环境的正确方式

把状态精确设成参考轨迹某一帧，此时**六项跟踪奖励必须全部 = 1.0000**。
任何一项偏离，就说明坐标系/参考点/单位约定还有 bug ——
在这种环境里策略再好也拿不到分。

这个检验应该在写完奖励函数的第一时间就做，比事后看曲线便宜得多。
我们靠它抓到了两个约定错误：`cvel` 的参考点是 `subtree_com` 而非 body 原点
（手腕线速度差 1.0 m/s）、自由关节 `qvel[3:6]` 是机体系角速度而非世界系
（速度奖励恒为 0）。

## 六、层 3 的两个发现

### 6.1 unitree_mujoco 的 PD 算在 DDS 回调里

`unitree_sdk2py_bridge.py` 在 `LowCmdHandler`（DDS 回调，50 Hz）里直接算出
力矩写进 `mj_data.ctrl`。两条指令之间的 20 ms，那个力矩被当成**常量**保持。

| 场景 | PD 闭环频率 |
|---|---|
| 训练（position 执行器） | MuJoCo 每个子步重算 → **500 Hz** |
| 真机（电机驱动器固件） | **1~2 kHz** |
| unitree_mujoco 桥接层 | **50 Hz 零阶保持** |

同策略同模型，只改这一项：

| PD 闭环 | 存活（上限 500） |
|---|---|
| 50 Hz 零阶保持，kd = 2 / 5 / 10 | 18 / 24 / 18 ❌ |
| 200 Hz 子步闭环 | **500** ✅ |

**加大阻尼救不回来** —— 不是阻尼不够，是采样率不够。把 PD 移进仿真循环
后立刻通过。这是仿真器的实现失真，真机的电机驱动器不是这样工作的。
已整理为对 `unitreerobotics/unitree_mujoco` 的 PR。

### 6.2 起始姿态必须是动作首帧

第一次跑层 3，第 31 步就摔。排查发现不是策略问题：unitree_mujoco 默认从
通用站立 keyframe 起步，而它与动作首帧差 **0.624 rad（36°）**，
`base_z` 也差 2.9 cm。策略训练时的 RSI 扰动只有 ±0.1 rad，
等于一上来就被丢进没见过的状态。

改成从参考首帧起步后立刻 156/156。真机流程本来也是先把机器人摆到起始
姿势再交给策略，所以这才是正确做法。

> 排查时我们先验证了自己新写的躯干正运动学（姿态误差 0.0000 度），
> 确认不是新代码的问题，才往下查环境。

## 八、网页界面

Gradio 四步向导，用户不需要写代码：

1. **上传视频，提取人体动作** — 命名项目，所有产物按名字走
2. **重定向到 G1** — 出运动学回放视频
3. **训练策略** — 时长自选（无上限），四条实时曲线，可中途停止，
   checkpoint 间隔可调且全部保留可下载
4. **物理仿真执行** — 左参考右策略并排对比

后端把三个**互不兼容**的 Python 环境包成统一接口：

| venv | 关键依赖 | 不能有 |
|---|---|---|
| `gvhmr_env` | PyTorch 2.9.1+rocm、pytorch3d | jax |
| `GMR/gmr` | 重定向依赖 | — |
| `mjx` | JAX 0.11、MuJoCo、MJX、brax | torch |

三者装在一起会互相踩，只能子进程 + 文件交换。这个约束对 Docker 分层
也是决定性的。

## 十、局限与后续

**当前局限**

- 动作库规模小。「一套超参覆盖大多数动作」这个主张需要更多动作来支撑。
- 下肢跟踪已纳入奖励，但未验证需要移动重心的动作（跳跃、行走）。
- 单条动作训练 6 小时，对交互式产品仍然偏长。
- 网页的长训练不支持断线重连（训练进程不会死、checkpoint 照写，
  但页面日志流会断）。

**后续方向**

- 用 LAFAN1 等数据集扩充动作库，量化「一套超参」的覆盖率。
- 预训练基座 + 单动作微调，把 6 小时压到 ~20 分钟。
- 域随机化 + 通信延迟建模，为真机部署加固。
- Docker 打包。**注意**：GVHMR 依赖的 SMPL/SMPL-X 是注册授权的，
  许可证禁止再分发，不能打进公开镜像，需要引导用户自行下载。

**真机说明**：赛事 FAQ Q66/Q69 明确所有工作须在云端完成、真机结果不计入
评分。我们的层 3 验证全部在云端 `unitree_mujoco` 上完成。
`deploy_track.py` 与真机共用同一套 DDS 接口和同一份 NumPy 权重，
换个网卡名即可上真机 —— 但仅作为个人学习，不作为参赛成果。
