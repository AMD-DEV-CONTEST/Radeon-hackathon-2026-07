## 贡献 1：MuJoCo Playground 在 AMD 上无法开箱运行 ⭐ 含金量最高

**目标仓库**：[`google-deepmind/mujoco_playground`](https://github.com/google-deepmind/mujoco_playground)

**类型**：Bug report + 文档 PR

### 问题

`registry.load()` 默认使用 MuJoCo Warp 后端，而 Warp 是 CUDA 独占的。
在任何 AMD GPU 上直接崩溃：

```python
from mujoco_playground import registry
env = registry.load("G1JoystickFlatTerrain")
```

```
File "warp/_src/jax/__init__.py", line 46, in device_from_jax
    return warp.get_cuda_device(jax_device.id)
File "warp/_src/context.py", line 7715, in get_cuda_device
    return runtime.cuda_devices[ordinal]
IndexError: list index out of range
```

报错完全没有提示"这是 CUDA 专用后端"，`IndexError: list index out of range`
对使用者毫无指向性。

### 根因

`joystick.default_config()` 里硬编码了 `impl="warp"`。

### 修复

```python
cfg = registry.get_default_config("G1JoystickFlatTerrain")
cfg.impl = "jax"                     # ← AMD 必须显式指定
env = registry.load("G1JoystickFlatTerrain", config=cfg)
```

### 建议的 PR 内容

1. **文档**：在 README / 安装说明里增加 "Running on AMD GPUs (ROCm)" 小节，
   说明必须设 `impl="jax"`
2. **代码**：在 `impl="warp"` 且检测不到 CUDA 设备时给出可读的报错，例如
   ```
   RuntimeError: impl="warp" requires an NVIDIA GPU (MuJoCo Warp is CUDA-only).
   Set config.impl = "jax" to run on AMD/ROCm or CPU.
   ```

### 补充：命令行入口同样受影响

`train-jax-ppo` 也需要显式 `--impl jax`。README 里应一并说明
**Python API 和 CLI 是两个独立入口，都要设**。

## 贡献 2：gfx1100 上 Brax PPO 的计算图规模上限 ⭐ 数据独有

**目标仓库**：[`google/brax`](https://github.com/google/brax) 或
[`jax-ml/jax`](https://github.com/jax-ml/jax)（XLA ROCm 后端）

**类型**：Bug report（附完整复现）

### 问题

在 Radeon Pro W7900 (gfx1100, ROCm 7.2.1, JAX 0.11.0) 上，
Brax PPO 训练在**第一次评估完成后立刻 Segmentation fault**，
没有任何 Python 层异常。

`python -X faulthandler` 抓到的崩溃点：

```
File "jax/_src/interpreters/pxla.py", line 420 in __call__
File "jax/_src/pjit.py", line 1222 in _pjit_call_impl_python
File "jax/_src/pmap.py", line 319 in wrapped
File "brax/training/agents/ppo/train.py", line 685 in training_epoch_with_timing
```

### 排除项（均已验证不是原因）

| 假设 | 验证方法 | 结果 |
|---|---|---|
| 显存不足 | `rocm-smi` | GPU 51GB 仅用 28MB；系统内存 503GB 剩 477GB |
| pmap 在 ROCm 上损坏 | 单独测 pmap / pmap+pytree / pmap+grad | **全部通过** |
| 环境实现有 bug | 换用官方 Playground 环境 | 同样崩溃 |

### 真正的触发条件

**计算图规模**。逐档扫描结果：

| num_envs | unroll_length | num_minibatches × num_updates_per_batch | 结果 |
|---|---|---|---|
| 512 | 20 | 4 × 1 = 4 | ✅ |
| 1024 | 20 | 8 × 2 = 16 | ✅ |
| 2048 | 20 | **16 × 2 = 32** | ✅ **可用上限** |
| 2048 | 20 | 32 × 4 = 128 | ❌ 段错误 |

> **结论：`num_minibatches × num_updates_per_batch ≤ 32`。**
> 超过该值时，128 个梯度步被展开进同一张 XLA 图，
> gfx1100 的代码生成阶段直接段错误。

### 最小复现

```python
# 环境：ROCm 7.2.1 / JAX 0.11.0 / jax-rocm7-plugin / gfx1100
# brax 0.14.2 + mujoco-mjx
ppo.train(
    environment=env,
    num_envs=2048,
    unroll_length=20,
    num_minibatches=32,      # 改成 16 即可正常
    num_updates_per_batch=4, # 改成 2 即可正常
    ...
)
```

### 价值

RDNA3 (gfx1100) 是 Radeon Pro W7900 / RX 7900 系列的架构，
是目前最容易获得的 AMD 工作站/消费级 GPU。
这条数据能让后来者少走弯路，也给 XLA ROCm 后端提供了明确的复现案例。

## 贡献 3：brax 与 JAX 0.11 的 API 不兼容

**目标仓库**：[`google/brax`](https://github.com/google/brax)

**类型**：Bug report + 小 PR

### 问题

brax 0.14.2（当前最新版）的 PPO/SAC/APG 训练器仍在调用
`jax.device_put_replicated`，该 API 已随 pmap 迁移在 JAX 0.11 中移除：

```
AttributeError: jax.device_put_replicated is deprecated; use jax.device_put instead.
See https://docs.jax.dev/en/latest/migrate_pmap.html#drop-in-replacements
```

受影响文件：

```
brax/training/agents/ppo/train.py:756
brax/training/agents/sac/train.py:111
brax/training/agents/apg/train.py:313
brax/training/pmap.py:27
```

### 为什么这在 AMD 上尤其致命

ROCm 平台的 JAX 版本由 `jax-rocm7-plugin` 绑定，**不能随意降级**
（降级会丢失 GPU 支持）。因此 NVIDIA 用户可以用旧版 JAX 绕过，
AMD 用户只能打补丁。

### 临时解法（可作为 PR 的实现思路）

```python
def _device_put_replicated(x, devices):
    n = len(devices)
    stacked = jax.tree_util.tree_map(
        lambda y: jnp.stack([jnp.asarray(y)] * n), x
    )
    return jax.device_put(stacked, devices[0]) if n == 1 else stacked
```

## 贡献 4：ROCm 版 PyTorch wheel 的依赖陷阱

**目标**：AMD ROCm 文档 / 训练营官方仓库

**类型**：文档补充

### 问题

镜像自带的 ROCm PyTorch wheel 在 metadata 里钉死了本地版本号的 triton：

```
triton==3.5.1+rocm7.2.1.gita272dfa8
```

这个版本号 **PyPI 上不存在**。只装 torch 不装 triton 会报：

```
ERROR: Could not find a version that satisfies the requirement
       triton==3.5.1+rocm7.2.1.gita272dfa8
ERROR: No matching distribution found for triton==3.5.1+rocm7.2.1.gita272dfa8
```

整个 torch 安装回滚，最终 `import torch` 报 `ModuleNotFoundError`，
**报错信息完全没提示是 triton 的问题**。

### 正确做法

四个本地 wheel 必须一次性一起装：

```bash
pip install \
  /torch-2.9.1+rocm7.2.1*.whl \
  /torchvision-0.24.0+rocm7.2.1*.whl \
  /torchaudio-2.9.0+rocm7.2.1*.whl \
  /triton-3.5.1+rocm7.2.1*.whl
```

## 贡献 5：GVHMR 在 AMD/ROCm 上的完整适配路径

**目标仓库**：[`zju3dv/GVHMR`](https://github.com/zju3dv/GVHMR)

**类型**：文档 PR（"Running on AMD GPUs"）

`requirements.txt` 完全针对 CUDA 编写，AMD 上需要以下调整
（**全部实测通过**，最终在 gfx1100 上完成 187 帧视频的推理，
GVHMR 本体推理耗时 2.46s / 6.2s 视频）：

| 依赖 | 问题 | 解法 |
|---|---|---|
| `torch==2.3.0+cu121` | CUDA 专用 | 换 ROCm wheel（注意贡献 4 的 triton 陷阱） |
| `pytorch3d`（cu121 预编译 wheel） | CUDA 专用 | 源码编译：`MAX_JOBS=8 FORCE_CUDA=0 pip install --no-build-isolation -e .` |
| `numpy==1.23.5` | Python 3.12 编译失败 | 移除版本钉死 |
| `chumpy` | 构建系统损坏，报 `No module named 'pip'`，**且会导致整批依赖安装失败** | `pip install --no-build-isolation chumpy` + 两处补丁（见下） |
| `ultralytics==8.2.42` | 与 PyTorch ≥2.6 的 `weights_only=True` 默认值冲突 | `pip install -U --no-deps ultralytics` |
| `yacs` / `tkinter` | **requirements.txt 里没列但实际必需** | `pip install yacs` + `apt install python3-tk` |
| DPVO | 需要 CUDA 扩展 | **默认就不启用**，加 `--static_cam` 明确跳过 |

### chumpy 的两处必需补丁

```bash
CH=<venv>/lib/python3.12/site-packages/chumpy
# 1. inspect.getargspec 在 Python 3.11 已移除
sed -i "s/inspect\.getargspec/inspect.getfullargspec/g" $CH/ch.py
# 2. numpy 已移除 bool/int/float 等别名
sed -i "s/^from numpy import bool, int, float, complex, object, unicode, str, nan, inf$/from numpy import nan, inf/" $CH/__init__.py
```

### 附带发现：缓存复用不校验内容

GVHMR 按**视频文件名**建输出目录并复用缓存，不校验文件内容。
同名不同内容的视频会静默拿到错误结果，日志看起来完全正常，
唯一破绽是 `[Preprocess] End. Time elapsed: 0.03s`（真跑不可能这么快）。

建议：对输入视频做 hash 校验，或在复用缓存时打印明确提示。

## 贡献 6：unitree_mujoco 的 PD 只在 DDS 回调里算，高刚度控制器必然失稳 ⭐⭐ 代码 PR

**目标仓库**：[`unitreerobotics/unitree_mujoco`](https://github.com/unitreerobotics/unitree_mujoco)

**类型**：Bug fix PR（有代码、有量化数据）

### 问题

`unitree_sdk2py_bridge.py` 在 `LowCmdHandler` 里直接算出力矩写进 `mj_data.ctrl`：

```python
def LowCmdHandler(self, msg: LowCmd_):          # ← DDS 回调
    for i in range(self.num_motor):
        self.mj_data.ctrl[i] = (
            msg.motor_cmd[i].tau
            + msg.motor_cmd[i].kp * (msg.motor_cmd[i].q - sensordata[i])
            + msg.motor_cmd[i].kd * (msg.motor_cmd[i].dq - sensordata[i + n])
        )
```

回调只在收到 `LowCmd` 时触发。典型控制频率 50 Hz，
而 `SIMULATE_DT = 0.005`（200 Hz）—— 也就是说算出来的力矩会被
**当成常量保持 4 个仿真步**。PD 闭环频率被压到了指令下发频率。

### 为什么这是失真

真机上 `kp` / `kd` 是**下发给电机驱动器**的，驱动器用本地编码器
在 1~2 kHz 上闭环。仿真里把 PD 提到回调层，行为与真机不一致，
而且是往最糟的方向偏 —— 高刚度 PD 配低频零阶保持必然失稳。

### 量化数据

Unitree G1 29 自由度，RL 策略，kp = 75~100，同一策略同一模型，
只改 PD 闭环位置：

| PD 闭环 | 存活步数（上限 500） |
|---|---|
| 50 Hz 零阶保持（现状），kd = 2.0 | 18 ❌ |
| 50 Hz 零阶保持，kd = 5.0 | 24 ❌ |
| 50 Hz 零阶保持，kd = 10.0 | 18 ❌ |
| 200 Hz 子步闭环（本 PR） | **500** ✅ |
| 500 Hz 子步闭环 | **500** ✅ |

加大 `kd` 救不回来 —— 不是阻尼不够，是采样率不够。

### 修复

回调只缓存指令，力矩在每个仿真步用当前状态重算：

```python
def LowCmdHandler(self, msg: LowCmd_):
    if self.mj_data is None:
        return
    for i in range(self.num_motor):
        mc = msg.motor_cmd[i]
        self._cmd_q[i], self._cmd_dq[i] = mc.q, mc.dq
        self._cmd_kp[i], self._cmd_kd[i], self._cmd_tau[i] = mc.kp, mc.kd, mc.tau
    self._cmd_ready = True

def ApplyPD(self):
    """在每个仿真步调用 —— 模拟电机驱动器的高频闭环。"""
    if self.mj_data is None or not self._cmd_ready:
        return
    q  = self.mj_data.sensordata[: self.num_motor]
    dq = self.mj_data.sensordata[self.num_motor : 2 * self.num_motor]
    tau = (self._cmd_tau
           + self._cmd_kp * (self._cmd_q - q)
           + self._cmd_kd * (self._cmd_dq - dq))
    lo = self.mj_model.actuator_ctrlrange[:, 0]
    hi = self.mj_model.actuator_ctrlrange[:, 1]
    self.mj_data.ctrl[: self.num_motor] = np.clip(tau, lo, hi)
```

```python
# unitree_mujoco.py 仿真线程
unitree.ApplyPD()
mujoco.mj_step(mj_model, mj_data)
```

### 为什么值得提

这个 bug 的现象极难归因：**策略在原生 MuJoCo 里 500/500，一接 DDS 就摔**。
使用者的第一反应必然是怀疑自己的策略、观测顺序、四元数约定、
域随机化不够 —— 我们把这些全查了一遍才找到真因。
任何在 unitree_mujoco 上做高刚度全身控制的人都会踩到。

## 贡献 7：unitree_mujoco 无法在无显示器环境运行

**目标仓库**：[`unitreerobotics/unitree_mujoco`](https://github.com/unitreerobotics/unitree_mujoco)

**类型**：Feature PR

### 问题

`simulate_python/unitree_mujoco.py` 的主循环条件是 `while viewer.is_running()`，
强依赖 GLFW 交互窗口。在容器 / CI / 云服务器上：

```
GLFWError: (65550) b'X11: The DISPLAY environment variable is missing'
ERROR: could not initialize GLFW
```

配了 Xvfb 也只能算勉强可用：软件 GL 下窗口经常不重绘，
`x11grab` 抓出来的视频**每一帧都一样**（实测 30 秒视频 750 帧全静止），
而且渲染线程和物理线程抢同一把锁。

### 修复

提供无头变体：去掉交互窗口，用 MuJoCo 离屏渲染（EGL）直接出 mp4，
DDS 桥接层行为完全不变。两个容易踩的点：

```python
# 1) 离屏画布默认 640×480，超了会报错让你去改 XML 的 <visual><global offwidth>。
#    直接改运行时模型字段，不用动第三方 XML。
mj_model.vis.global_.offwidth  = max(mj_model.vis.global_.offwidth,  width)
mj_model.vis.global_.offheight = max(mj_model.vis.global_.offheight, height)

# 2) 控制端连上之前不要推进物理 —— 桥接层在没有 LowCmd 时施加零力矩，
#    先跑物理的话机器人在等待期间就已经躺平了。
while not bridge._cmd_ready and not stop.is_set():
    time.sleep(0.01)
```

对 CI 回归测试、批量策略评测、以及把画面送进 Web 前端都是刚需。
