# 都是 MuJoCo，为什么还要分三层？

> 一句话：**因为「同一个 MuJoCo」这个说法本身就是错的。**
> 三层跑的是三套不同的物理实现、三套不同的机器人模型、三套不同的数据通路。
> 每一层只换掉一样东西，出问题才能定位到是哪一样。

---

## 一、直觉上的疑问

「训练在 MuJoCo，验证也在 MuJoCo，那不是自己考自己吗？」

如果三层真的是同一套东西，那确实没意义。但实际上它们只有名字里都带 MuJoCo，
底下的东西几乎没有重合：

| | 层 1 | 层 2 | 层 3 |
|---|---|---|---|
| **物理实现** | MJX（JAX 重写，GPU） | MuJoCo 原生 C 引擎（CPU） | MuJoCo 原生 C 引擎 |
| **机器人模型** | Playground 的 G1 | Playground 的 G1 | **宇树官方 G1** |
| **执行器类型** | position（模型内置 PD） | position | **motor（力矩）+ 软件 PD** |
| **策略推理** | brax 网络（JAX，GPU） | **纯 NumPy**（CPU） | 纯 NumPy |
| **状态获取** | 直接读内存 `qpos` | 直接读内存 `qpos` | **DDS 消息 `LowState`** |
| **可用信息** | 全知（含世界坐标） | 全知 | **只有 SDK 给的那几项** |
| **控制下发** | 直接写 `ctrl` | 直接写 `ctrl` | **DDS 消息 `LowCmd`** |
| **谁写的代码** | 我们 | 我们 | **宇树官方** |

**MJX 不是 MuJoCo 的封装，是用 JAX 重新实现了一遍物理**，为了能在 GPU 上
同时跑几千个环境。求解器、接触处理、积分都是另一套代码。两者结果接近，
但不是同一个东西 —— 这本身就值得验证。

---

## 二、每一层各自排除什么

设计原则只有一条：**每层只换一样东西**。

### 层 1 —— 训练环境内部

策略在它出生的地方跑。这一层只能回答「训练有没有收敛」，
**回答不了任何关于正确性的问题** —— 如果环境本身写错了，
层 1 会开开心心地给满分。

> 实际教训：旧版环境里「站着不动」是最优解，层 1 的指标是
> 「500/500 步不摔」，看起来完美，视频里机器人手臂根本没动。

### 层 2 —— 换物理引擎 + 换推理栈

把 MJX 换成原生 C 引擎，把 brax/JAX 换成纯 NumPy 前向。

**能抓到的问题**：
- 策略是不是过拟合到 MJX 的数值特性（接触求解、积分误差）
- 权重导出对不对、观测拼接顺序对不对
- 有没有偷偷依赖 JAX 的某些行为

**过了层 2 意味着**：策略是一组独立的数字，不绑定训练框架。
25 万个参数 + 几行矩阵乘法就能跑。

### 层 3 —— 换机器人模型 + 换通信 + 加信息约束

这一层换掉三样，是含金量最高的：

**1) 换成宇树官方的 G1 模型**

不只是文件名不同，动力学参数是另一套：

| 参数 | 宇树官方模型 | Playground 模型 | 差异 |
|---|---|---|---|
| 关节阻尼 | 0.05 统一 | 0.2 ~ 2.0 | **最多 40 倍** |
| 电枢 | 0.01 统一 | 0.0036 ~ 0.0251 | ~3 倍 |
| 总质量 | 35.11 kg | 33.34 kg | +5% |
| 执行器 | `motor`，`ctrl` 是**力矩** ±88 N·m | `position`，`ctrl` 是**角度** ±2.5 rad | 语义完全不同 |
| 碰撞几何 | 全身 | 仅脚部 | — |

> 执行器那一行害我栽过一次：验证脚本照着 Playground 写的，
> 往力矩接口里灌了弧度值 —— 0.3 rad 被当成 0.3 N·m，约等于零力矩。
> 破绽是**两个完全不同的策略都恰好在第 18 步摔倒**。
> 两个不同的输入失败在同一个点，那就不可能是输入的问题。

**2) 换成 DDS 通信**

不再直接读写内存，改走宇树 SDK 的 `LowState` / `LowCmd` 消息 ——
**和真机完全同一套代码路径**。这引入了真实的时序：消息有延迟、
控制端和仿真端各跑各的时钟。

> 这里抓到过一个更隐蔽的：宇树桥接层把 PD **算在 DDS 回调里**，
> 力矩因此被零阶保持 20 ms，闭环频率被压到 50 Hz。而训练环境是
> 每个仿真子步重算（500 Hz），真机电机驱动器是固件里 1~2 kHz。
> 高刚度 PD 配 50 Hz 零阶保持必然失稳 ——
> 实测 18 步摔倒，**加大阻尼完全救不回来**（kd=2/5/10 都是 18~24 步）。
> 把 PD 移进仿真循环后立刻 500/500。
>
> 这是仿真器的实现失真，真机不会这样。但**只有走到层 3 才可能发现**。

**3) 信息约束 —— 这一层最容易被忽略**

前两层策略是「全知」的：世界坐标、真实速度，想读什么读什么。
层 3 只剩 `LowState` 里的四项：

```
motor_state[i].q        29 个关节角
motor_state[i].dq       29 个关节速度
imu_state.quaternion    骨盆姿态
imu_state.gyroscope     骨盆角速度
```

**没有躯干线速度**（IMU 只给角速度和姿态），
**没有世界位置**（机器人没有全局定位）。

这个约束必须在**训练前**就体现到观测设计里，训完再裁维度就得重训。
我们为此做了两次调整：

| 观测项 | 为什么去掉 | 代价 |
|---|---|---|
| 躯干线速度 | IMU 不提供 | 实测：同策略同仿真，仅把它置零，存活从 500/500 掉到 190/500 —— 必须重训 |
| `anchor_pos_b` | 需要躯干世界位置 | 重训一次 |

两项都挪进了 critic（非对称 actor-critic：价值网络训练时可以用特权信息，
策略网络不能）。BeyondMimic 官方也提供了同样思路的
`Wo-State-Estimation` 配置。

**还有一个坑**：策略是在 **torso_link** 坐标系上训练的，
而 G1 的 IMU 装在 **pelvis** 上，中间隔着三个腰关节。
姿态不能直接拿来用，要用测到的关节角做一次正运动学传递过去。
好在这只用到已有数据，仍然是纯 SDK 部署。

## 三、为什么必须逐层，不能直接测层 3

因为**层 3 失败时你不知道该怪谁**。

失败可能来自：策略本身、MJX 与原生引擎的差异、权重导出、观测拼接、
机器人模型差异、执行器语义、DDS 时序、桥接层实现、信息约束……

逐层做，每一层只引入一个变量：

```
层 1 过了  →  训练收敛了
层 2 过了  →  策略不依赖 JAX/MJX，导出正确
层 2 过、层 3 挂  →  问题一定在「模型 / 通信 / 信息」这三样里
```

最后那一行就是实际发生的事。因为前两层是干净的，
我才能把范围缩到桥接层，最后定位到 PD 频率。
**如果一开始就只测层 3，这个 bug 大概率会被归因成「策略不够鲁棒」，
然后我会去调超参 —— 那是永远调不出来的。**

## 四、三层用同一套指标

三层报同一个数，才有可比性：

- **完成度** —— 走完参考动作的百分比（不是「活了多少步」）
- **body 位置误差** —— 14 个身体部位在三维空间里的平均偏差（米）

两个都不用「有没有摔倒」。原因前面说过：
**站着不动也能满分不摔**。

三层的误差如果彼此吻合，说明迁移过程没有引入额外失真；
某一层突然变差，就知道是那一层新引入的东西出了问题。

## 五、和「sim2real」的关系

严格说层 3 是 **sim2sim**：从我们的训练仿真，迁移到**宇树自己的**仿真。

它不能替代真机，但它是通往真机路上**信息量最大的一步**，因为它同时
换掉了模型、通信和可用信息 —— 剩下没换的只有物理引擎本身和真实硬件的
非理想性（电机延迟、齿轮间隙、传感器噪声、地面材质）。

赛事规则（FAQ Q66/Q69）明确所有工作须云上完成、真机结果不计分，
所以层 3 就是我们能做到的终点。而 `deploy_track.py` 与真机共用同一套
DDS 接口和同一份 NumPy 权重 —— 换个网卡名就能上真机。

## 附：一句话总结每层

| 层 | 换掉了什么 | 过了说明什么 |
|---|---|---|
| 1 | — | 训练收敛了（**仅此而已**） |
| 2 | 物理引擎 + 推理栈 | 策略是独立的数字，不绑定框架 |
| 3 | 机器人模型 + 通信 + 信息约束 | 和真机同一套代码路径能跑通 |
