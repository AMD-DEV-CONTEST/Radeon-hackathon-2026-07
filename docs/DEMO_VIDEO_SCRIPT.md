# XiangLens Demo Video Script

## Recording Objective

Tell one coherent story in four stages:

1. What XiangLens is, how its Agent architecture works, and how a user operates it;
2. A LinkedIn case proving privacy tools, source-backed RAG, and cached multi-turn interaction;
3. A GitHub-to-General case proving rights awareness, explicit memory consent, and cross-review
   recall;
4. An opt-in Private Lens case proving that proprietary knowledge can extend the public Agent
   without entering the browser or repository.

Target duration: **4 minutes 45 seconds**. The competition accepts 3–5 minutes, so the final export
must stay below 5 minutes.

The interface, narration, captions, prompts, and terminal output shown in the video should all be
in English.

## Demo Assets

Use these files from `data/case/` in the specified order:

| Stage | Target context | First upload | Second upload | Main proof |
|---|---|---|---|---|
| LinkedIn | LinkedIn | `person1.jpg` | `qr.jpg` | Privacy scan, citations, cached follow-up |
| Rights and memory | GitHub | `person2.jpg` | `dog.png` | Character resemblance, consent-first memory |
| Cross-review recall | General | `dog.png` | `yinyang.jpg` | Approved preference recalled in a new thread |
| Private tool | General | `yinyang.jpg` | — | Runtime-only private technique result |

Before recording, run every case once with the production model. Confirm that:

- `qr.jpg` produces a visible QR/privacy finding;
- `dog.png` produces a **Rights & provenance findings** warning using resemblance language;
- the approved cartoon/copyright preference appears in the next review;
- the private Lens is mounted and returns at least one technique reference for `yinyang.jpg`.

Do not improvise different assets during the final take.

## Timing Overview

| Time | Stage | Proof |
|---|---|---|
| 0:00–1:05 | Product, architecture, usage | Clear application scenario, Agent design, AMD boundary |
| 1:05–2:25 | LinkedIn privacy case | Tools, RAG, citations, safe copy, two follow-ups |
| 2:25–4:00 | Rights and long-term memory | Copyright warning, approval, cross-review recall |

When a live run takes longer than the available screen time, record the click and the first visible
workflow activity, then cut to that same run's completed result. Add the caption `Idle inference
wait removed · same run`. Never imply that a cached result was generated by a different click.

## Stage 2 — LinkedIn Privacy Case and Multi-Turn Interaction

### 1:05–1:25 — Configure the review

**Screen actions**

1. Click **New review**.
2. Select **LinkedIn**.
3. Confirm that Audience and Intended signals update automatically.
4. Keep `profile_basics`, `privacy_safety`, and `global_professional_context` enabled.
5. Leave **Private Lens Tool** disabled.
6. Upload `person1.jpg` first and `qr.jpg` second.
7. Replace the request with the exact prompt below.

```text

to recruiters and international collaborators. Prioritize privacy safety, small-size clarity, and
crop resilience.
```

**Narration**

> First, I select LinkedIn. The audience and signals update automatically. I upload a normal
> portrait and a second candidate containing a visible QR code. The private extension remains off.

### 1:25–1:55 — Run and explain the result

**Screen actions**

1. Click **Compare candidates**.
2. Show the live Workflow panel for two or three seconds.
3. Cut to the completed result from the same run.
4. Show the recommended image and the five comparison dimensions.
5. Show **Privacy findings** and identify the QR warning by filename.
6. Show `inspect_local`, `retrieve_evidence`, and `compare_candidates` in the trace.
7. Open one relevant official URL from **Retrieved sources**, then return to XiangLens.
8. Click **Safe copy** and mention its exact scope.

**Narration**

> Local inspection identifies the QR disclosure before model interpretation. The model compares
> both candidates with one five-dimension rubric. The report recommends the safer image and links
> its retrieved guidance. Safe copy removes metadata; it cannot erase a QR code visible in pixels.

**Must be visible**

```text
Privacy findings
Recommended image shown by filename
Retrieved source title + clickable URL
Workflow node names and durations
Total / Model / RAG performance metrics
```

### 1:55–2:25 — Ask two follow-ups

Use **Continue the conversation**. Send these exact questions one at a time:

**Follow-up 1**

```text
Why is person1.jpg safer than qr.jpg for this LinkedIn audience?
```

**Follow-up 2**

```text
Would Safe copy remove the visible QR code, or does it only remove metadata?
```

**Screen actions**

- Show Turn 2 and Turn 3 in the same conversation.
- Point to `recall_context`, `reuse_analysis`, and `answer_follow_up`.
- Point out the trace statement that the vision model was skipped.
- Keep the original full report visible above the follow-up area when practical.

**Narration**

> These are same-thread follow-ups. XiangLens recalls recent messages and reuses verified
> observations, privacy findings, comparison, and citations without inspecting the images again.
> The second answer demonstrates tool honesty: metadata removal cannot remove a visible QR code.

**Recording safeguard**

If the VLM does not produce the recognizable-character finding during rehearsal, do not narrate a
result that is absent. Re-run the complete case before recording; do not fabricate or overlay a
warning.

## Recording Preparation

### Application state

- Deploy the exact backend commit and restart FastAPI.
- Deploy the matching GitHub Pages frontend.
- Keep one browser tab and one access session for the full memory sequence.
- Confirm the session has enough time remaining for the GitHub and General reviews.
- Start with an empty Approved memory list; delete rehearsal memory before the final take.
- Keep Private Lens disabled until Stage 4.
- Run one unrecorded warmup before the take.

### Data and retrieval

- Rebuild or verify the Milvus Lite database with the production embedding provider.
- Run `uv run python scripts/run_rag_smoke.py` and confirm all queries pass.
- Confirm LinkedIn guidance appears for the LinkedIn case.
- Confirm a copyright/provenance source can be retrieved after the approved memory is recalled.
- Confirm QR scanning dependencies are installed on the recording backend.

### Radeon evidence

- Prepare a readable `rocm-smi` view without secrets or unrelated processes.
- Prepare `benchmarks/results/llama_cpp_w7900_optimized.md` at a readable zoom.
- Show the actual model name and llama.cpp/ROCm runtime once.
- Do not claim FP8 support or attribute all speed differences to a single unmeasured cause.
- Distinguish the standalone model benchmark from complete Agent workflow latency.

### Privacy and rights

- Hide `.env`, API keys, Bearer tokens, tunnel configuration, and browser storage.
- Close personal tabs, notifications, shell history, and unrelated applications.
- Describe the cartoon finding as resemblance and provenance uncertainty, not a legal conclusion.
- Do not show the private course source or its filesystem path.
- Use the supplied case assets only for the competition demonstration and verify their submission
  status before publishing the repository or video.

### Readability

- Record at 1920×1080 or higher.
- Use browser zoom around 110–125%.
- Keep filenames, panel headings, source titles, and trace nodes readable.
- Use one caption style and hard cuts rather than decorative transitions.
- Keep background music below narration or omit it.

## Final Scoring Checklist

The finished video should visibly prove all of the following:

- A clear problem and international application scenario;
- A bounded LangGraph Agent rather than a one-shot prompt;
- Deterministic tool calls and visible workflow traces;
- Milvus Lite RAG with clickable, source-backed evidence;
- Same-thread multi-turn interaction without repeated vision analysis;
- Explicit long-term memory consent and deletion controls;
- Cross-review recall in a genuinely new thread;
- Separate privacy and rights/provenance findings;
- An opt-in private Tool with filtered output;
- Core inference on AMD Radeon/ROCm;
- A reproducible, reviewed performance result.

If one of these elements is absent from the visible result, record that case again rather than
describing an outcome that the screen does not prove.
