# 跨本体：对外叙事与诚实边界

> 内部备忘。回答：「在宇树采了数据，别的机器人来了又要搞一次」这种说法，是否符合 BotverseX 愿景？能不能写进文档和 Deck？

## 一句话

**行业痛点是：场景知识和工程流水线被锁在「某一类机器人 + 某一套工具」里，换机型就要重录、重搭、重训。BotverseX 要做的是兼容层 + 统一网站流程，让「进闭环」和「装能力」不必每次从零造轮子。**

## 你的说法，哪里特别准

用「宇树采了三个月 → 换 SO-101 / 又来一台臂 → 又要重来」开场，比直接讲 **Runtime adapter** 更容易让非技术听众点头。这和纲领里写的完全一致：

- 不同机器人 → 不同关节、SDK、数据格式 → **碎片化**
- 开发者 **每个任务从零搭 pipeline，难以复用**（见 `platform-manifesto.md`、故事 Deck「开发者今天的问题」）
- 我们要 **把不同机器人抽象成 Runtime**，不是每来一款机器人就重做一套软件

所以：**方向对，可以放进愿景故事、纲领和口播**。

## 需要说清的三层「复用」（避免过度承诺）

| 层级 | 今天行业常况 | BotverseX 目标 | 诚实边界 |
|------|--------------|----------------|----------|
| **平台流程** | 换厂商 = 换 ROS/脚本/训练环境 | 同一网站：连接 → 录 → 训 → 装 Skill；**只换 Runtime** | 已用 SO-101、Reachy 验证「换适配器不换产品」 |
| **数据格式与工程** | 各家私有格式，难以进 HF / 难合并 | **LeRobot 兼容** episode + Workflow 节点可复用 | 不同本体的 **动作空间不同**，原始轨迹通常不能「字节级直接混训」 |
| **能力（Skill）** | 锁在仓库里的脚本 | **会做什么** + `compatible_types` + 版本；可安装、可更新 | **不吹**「一份 Skill 无脑跑遍所有机器人」；在声明机型间迁移，必要时微调 / retarget |

对外口播可以压成一句：

> 「我们反对的是 **重复造轮子** —— 每次换机器人就重搭一整条流水线。我们追求的是 **兼容层**：场景怎么采、怎么训、怎么装能力，尽量只走一遍；换机器时换适配器，而不是换人生。」

## 和「宇树」举例的用法

- **适合**：讲 **市场趋势**（四足/人形装机涨）+ **行业通病**（数据与工具绑死在单一生态）。
- **不适合**：暗示「我们已在 Unitree 上量产闭环、数据已跨机型共用」——路线图里 Go2/G1 仍是 **Runtime 预研 / 伙伴接入**，真机主线是 SO-101、Reachy Mini。

推荐说法：

> 「你在 A 厂商的机器上采了三个月 kitchen 数据，公司又进了 B 厂家的臂 —— 往往 **数据格式、训练脚本、部署方式都要重来**。BotverseX 不想让大家一直付这种『换机税』。」

## 兼容层指什么（对内对外统一）

1. **Runtime 适配器** — 接 SO-101、Reachy，路线图上的四足/人形等  
2. **统一数据与训练入口** — LeRobot 格式、Dataset / Training / Workflow  
3. **Skill 层** — 能力商品化；声明兼容机型，而不是 500 行关节角  
4. **Local Agent** — 真机控制留本机，云端做账号与分发  

「所有品类可以复用」在对外话术中 = **同一套平台能力与流程可复用** + **Skill 在声明机型间可分发**；不是声称「一份原始 dataset 文件直接喂给狗和人形」。

## Deck / 口播建议（故事版）

1. **痛点页**（你的宇树式故事）→ 换机器人为什么要从零再来  
2. **解法页** → 兼容层：一个网站 + Runtime + Skill  
3. **诚实小字** → 不同本体需适配；我们在扩展品类，不吹万能迁移  

**不要**在页脚写「非融资材料」——听众不关心材料分类；故事版收尾用产品链接 + 一句愿景即可。融资与否用 **口播控制**（「今天不讲条款，讲平台和未来」），不必印在幻灯片上自降气势。
