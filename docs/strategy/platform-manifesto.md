# BotverseX 最高纲领

> **执行层覆盖（2026-07-31）：** 本文是长期愿景与对外叙事。近期「先做什么 / 卖给谁 / 访谈门禁」以 [`2026-07-31-product-truth-and-next.md`](./2026-07-31-product-truth-and-next.md) 为准，勿用本文阶段口号直接排工程。

## 一句话定位

BotverseX 是具身智能的数据闭环入口。

更短的一句话：

我们降低真实世界机器人数据从采集、训练、部署到复用的成本。

产品层的一句话：

BotverseX 是机器人技能的开发平台、本地运行时和未来技能市场。

长期记忆点：

> 未来机器人智能的瓶颈，是高质量真实世界数据；BotverseX 要成为让更多人产生这些数据、训练这些技能、部署回真实机器人的入口。

## 核心判断

机器人行业不会只停留在“卖硬件”的阶段，也不会只停留在“谁模型更大”的阶段。

硬件会继续重要，模型会继续重要，但随着低成本机械臂、人形机器人、四足机器人、移动机器人、教育机器人和工业机器人不断出现，真正稀缺的会逐渐变成：

- 谁能把真实场景变成高质量机器人数据；
- 谁能让机器人获得更多可用能力；
- 谁能让开发者把能力做出来、跑起来、分发出去、持续更新；
- 谁能让用户、企业和硬件厂商围绕这些能力形成生态。

真实世界数据不在网页上。它在工厂、实验室、学校、仓库、厨房、桌面任务和各种具体场景里。很多场景拥有者甚至不知道：他们手里的动作、任务、失败案例、环境变化，本身就是未来机器人模型最有价值的训练数据。

BotverseX 要做的不是某一个机器人，而是把「场景 → 数据 → 模型 / 技能 → 真机运行 → 复用分发」这条链路做短、做便宜、做成默认入口。

## 核心类比

SpaceX 的意义不只是造火箭，而是降低了进入轨道的成本，让更多人、更多公司、更多载荷能被送上太空。

BotverseX 的目标不是造更多机器人，而是降低进入具身智能数据闭环的成本，让更多人、更多场景、更多硬件都能快速产生真实机器人数据，并把数据变成可运行、可复用的技能。

对外可以这样说：

> SpaceX 降低了进入轨道的成本；BotverseX 想降低真实世界机器人数据闭环的成本。

内部理解：

> 我们不垄断硬件，也不垄断模型。我们想占据的是：普通人从真实场景进入具身智能数据生产的第一站。

## 时代类比

机器人行业现在很像早期智能手机时代：硬件很多，系统很多，SDK 很碎，开发者很难把一个能力发布给更多用户。

诺基亚、黑莓、摩托罗拉等厂商不是没有应用商店，而是没有把开发、运行、分发、更新、支付和用户入口统一成一个完整生态。

iOS 和 Android 真正做对的是：

- 给开发者统一 SDK 和开发入口；
- 给用户统一 App Store / Google Play；
- 给应用统一审核、更新和分发；
- 给开发者清晰的触达用户和赚钱路径；
- 让硬件不只是硬件，而是生态入口。

机器人行业也会经历类似问题。不同机器人会有不同关节、坐标系、SDK、相机、夹爪、数据格式和任务场景。硬件会碎片化，平台层会变得更重要。

BotverseX 的机会是做这个中间层：

- 把不同机器人抽象成 Runtime；
- 把开发流程抽象成 Workflow；
- 把机器人能力抽象成 Skill。

## 我们现在的小开始

BotverseX 当前不是“只做了 SO-101 控制台”。

SO-101 是切入口，因为它足够便宜、开放、可验证，适合打通机器人应用生态的最小闭环：

1. 本地机器人接入；
2. 端口扫描和 Wiggle 识别；
3. Leader / Follower 遥操作；
4. 数据录制；
5. 训练 / 微调；
6. 模型部署；
7. 技能复用；
8. 未来上架技能市场。

现在的产品不是终局，而是 wedge，是切入口。它的价值不是“控制一个机械臂”，而是证明真实场景可以低门槛进入数据闭环：机器人能被接入，数据能被采集，模型能被训练，技能能被部署，能力最终能被封装、复用和分发。

## 从场景到技能的数据管道

| 模块 | 在大故事里的位置 |
|------|------------------|
| SO-101 / Reachy / 更多 Runtime | 低门槛真实数据采集端 |
| Local Agent / Realtime / Runtime | 让真实硬件接入平台并在本机运行 |
| Record / Dataset | 把场景变成可训练数据 |
| Training / Workflow | 把数据变成模型和技能 |
| Skills | 把能力封装、复用、分发 |
| AI Hub / HF | 接入开源模型和数据生态 |

主线不是“很多页面”，而是：

> 搭一条从真实场景到机器人技能的数据管道。

## 当前已具备的结构

BotverseX 已经有一些不是 demo 的架构骨架：

- Local Agent / Realtime：跑在用户本机，负责串口、相机、遥操作、录制、技能执行和浏览器通信。
- Runtime 抽象：用 RuntimeReader、RuntimeWriter、RuntimeInfo 把不同机器人接入到统一接口。目前已有 SO-101 和 Reachy Mini 两个方向。
- 端口扫描和 Wiggle：帮助用户不用猜 `/dev/ttyACM0`、`/dev/ttyACM1`，点一下让夹爪晃动，看到哪只臂动了就指派 Follower 或 Leader。
- Workflow 编辑器：未来把采集、转换、训练、评估、部署串成可视化 pipeline。
- Skill schema / Skill registry：已经有技能标准格式和注册表雏形，包括 skill_id、verb、robot_type、compatible_types、params_schema、训练后端和版本信息。
- BotClaw Spec：作为跨服务、跨前后端、跨运行时的协议基础。

## 诚实边界

当前不要对外说：

- 我们已经是机器人 App Store；
- 我们已经支持所有机器人；
- 机器人技能可以无脑跨硬件通用；
- 我们已经完成完整商业闭环。

当前应该说：

- 我们正在验证机器人应用生态的最小闭环；
- 我们先从 SO-101 这种低成本开放硬件切入；
- 我们已经定义了硬件层 Runtime 和技能层 Skill schema；
- 我们不追求一步到位，而是先让开发者连上机器人、录到数据、跑起技能，再逐步进入技能发布、复用和交易。

开发和运行链路已经跑通了最小闭环；分发层的数据结构和注册协议已经有了；市场、更新和变现是下一阶段。

## 面向不同对象的讲法

面对投资人：

BotverseX 是具身智能的数据闭环入口。我们从低成本开放机械臂切入，让更多开发者和场景拥有者能把真实任务变成数据，再把数据变成可运行、可复用的机器人技能。长期目标是成为机器人技能的分发网络和运行时标准。

面对开发者：

BotverseX 让你不用先学一堆 ROS、驱动、串口和训练脚本，也能在浏览器里连接机器人、遥操作、录数据、训练和部署技能，把自己的真实场景变成有价值的数据。

面对硬件厂商：

接入 BotverseX 等于接入开发者、数据闭环、Workflow 和技能生态，让硬件不只是硬件，而是可以持续产生数据、获得新能力的平台入口。

面对潜在收购方：

BotverseX 是机器人云、本地运行时、技能分发和具身智能数据闭环入口的早期形态。

## 最稳的总叙事

今天机器人行业的问题，不只是缺更好的硬件，也不只是缺更大的模型，而是缺一个让真实场景持续变成高质量机器人数据，再变成可运行技能的平台。

不同机器人硬件、SDK、数据格式都很碎片化，导致开发者每做一个任务都要从零开始。

BotverseX 从低成本机械臂切入，先打通连接、遥操作、数据采集、训练 workflow 和本地运行时，降低从场景到数据、从数据到技能的成本。

长期我们希望把机器人能力封装成 Skill，让开发者可以发布，用户可以安装，企业可以管理和部署。

我们不假设所有机器人技能天然通用，而是通过 Adapter、Workflow 和标准化 Skill 格式，让能力尽可能复用和迁移。

## 跨本体：痛点叙事（对外可照念）

行业常见情况：团队在 **某一类机器人**（四足、人形、教育臂）上采了很久场景数据，公司又引入 **另一家机型** —— 数据格式、训练脚本、部署方式往往要 **从头再来**，场景知识留在人脑子里，工程轮子却要 **重复造**。

BotverseX 的回应不是「一份原始 dataset 字节级跑遍所有机器人」，而是三层复用：

1. **平台流程**：同一网站，连接 → 录制 → 训练 → 装 Skill；换机器 **只换 Runtime**，不重做产品。  
2. **数据与工程**：LeRobot 兼容格式 + Workflow，减少每家一套私有 pipeline。  
3. **能力**：Skill 声明 `compatible_types`，在兼容机型间安装、更新；必要时微调，不吹无脑万能。

口播可先说痛点（换机税），再说兼容层；细节与诚实边界见 [cross-embodiment-narrative.md](./cross-embodiment-narrative.md)。
