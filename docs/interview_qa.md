# InventoryDoc Agent — 面试 Q&A

> 面向 AI 产品经理面试战项目 | 覆盖产品定位、Agent 设计、企业治理、AMD ROCm、端到端闭环

---

## Q1：这是 Agent 还是一个报表脚本？

**这是一个完整意义的私有 AI Agent**，不是传统脚本：

| Agent 必备能力 | InventoryDoc Agent |
|---|---|
| **Multi-step Planning** | 10 步确定性工作流，状态机编排，每步有明确输入输出 |
| **Tool Calling** | 调用文件加载器、噪音检测器、质量校验器、Excel/MD 生成器、LLM 报告 |
| **Memory** | `ConsistencyMemory` 跨文件数字校检，对话历史持久化 |
| **Grounding** | 所有结论基于 10 份上传文件，LLM 不编造外部事实 |
| **Local Deploy** | 零云端依赖，数据全程不出设备 |

脚本是"跑一次出文件"，Agent 是"能规划、有记忆、会校验、可对话、能解释"。评委问"为什么不是报表脚本"时，一条条对这 5 个能力说。

## Q2：为什么不让 LLM 做全部？为什么要确定性工作流？

**审计 Agent 的第一原则是可信，不是智能。** 确定性工作流保障可审计性。

理由有三：
1. **可追溯**：pandas 每行计算都有来源和公式。LLM 是黑盒，审计级场景不能用黑盒做事实。
2. **零幻觉**：差异金额差 1 元就要上会解释，LLM 做算术会出错。
3. **可验证**：Ground Truth 验收 7/7 通过，每次回归输出一致。

LLM 的角色：在确定性计算完成后，把结构化指标转译成管理层能看懂的表达，加风险判断和行动建议。LLM 是 **表达引擎，不是计算引擎**。

## Q3：如何防止 LLM 幻觉？

三层防线：

1. **确定性工作流隔离**：所有事实数字在 LLM 介入前算好，锁在 `analysis_result.json`。LLM prompt 只拿到结构化数据，不参与计算。
2. **Prompt 边界约束**：prompt 明确写 "所有结论必须严格基于下方分析数据，不得编造或推测"。Top-5 SKU 如果没有，LLM 只能说需查看 Excel。
3. **质量门禁**：LLM 报告前有 7 条自动校验，关键指标（差异率、金额）如果偏离 Ground Truth，阻断报告生成。

**面试回答金句**："我们不是在事后检查 LLM，而是在前端用确定性工作流消除 LLM 需要做事实判断的可能性。"

## Q4：换一个数据集还能跑吗？

**当前版本针对某供应链循环盘点场景做了模板化**，但架构支持扩展：

- `config/data_contracts.yaml`：定义每个文件的关键信息，多客户可以维护多套契约
- `config/ground_truth.yaml`：Ground Truth benchmark 可配置
- `config/settings.yaml`：噪音识别规则、质量检验规则可配置

换数据集需要：
1. 更新 `ground_truth.yaml` 的 benchmark 值
2. 确认文件命名和列名与契约匹配
3. 如果列名不一致，增加列名映射配置

这是架构上的设计，目前 MVP 只实现了一个客户模板。

## Q5：为什么选择 AMD ROCm 而不是 NVIDIA？

三个维度的理由：

| 维度 | AMD ROCm | NVIDIA CUDA |
|---|---|---|
| **黑客松要求** | 赛道二明确鼓励 AMD GPU | 非强制但非首选 |
| **企业部署** | 完全开源，无供应商锁定 | 闭源，授权限制 |
| **成本** | Radeon 显卡性价比更高 | 高端 GPU 昂贵 |

此外，赛道评分 40% 是 GPU 优化，选择 ROCm 本身就是加分项。

## Q6：如何衡量这个 Agent 的业务价值？

| 指标 | 人工 | Agent | 提升 |
|---|---|---|---|
| 分析耗时 | 2-3 天 | ~8 秒纯计算 | 99%+ |
| 质量校验 | 无 | 7 条自动规则，自动阻断 | 从 0 到 1 |
| 噪音识别 | 人工逐行筛选 | 自动识别 68 条 NOISE | 从 2 小时到 3 秒 |
| 基准选择 | 靠经验 | 三维论证自动判断 | 消除人为错误 |
| 是否可审计 | 无 | 每步 trace + hash | 从 0 到 1 |

核心 ROI：**把盘点差异分析从"2-3 天 + 可能算错"变成"8 秒 + 可审计 + 可上会"**。

## Q7：如果老板问"这是 AI Agent 还是自动化脚本"，怎么回答？

"它是披着脚本外衣的 Agent。它的核心是 10 步规划 + 5 种工具调用 + 跨文件记忆 + Grounding + 本地部署——全部满足赛道二的 Agent 定义。之所以看起来像脚本，是因为在审计场景里，确定性工作流比黑盒推理更可信。我们的 Agent 能力不是用在做计算上，而是在规划、校验、记忆、对话和报告生成上。"

## Q9：失败场景有哪些？如何处理？

| 场景 | 当前处理 | 备选方案 |
|---|---|---|
| LLM 服务不可达 | 明确报错，提示 --demo/--mock | 降级到纯规则报告 |
| 缺必需文件 | 输入验证阻断，不运行工作流 | 友好提示缺失文件清单 |
| 空文件 | 加载成功（0 行）或报错 | 后续步骤可能中断 |
| Ground Truth 不匹配 | 质量校验标记未通过 | 人工确认是否需要更新 GT |
| 列名不一致 | 列名匹配失败，step error | 需要适配配置 |

## Q10：这个项目最让你骄傲的产品设计是什么？

**"在确定性计算和 LLM 智能之间找到了正确的边界。"**

很多 AI Agent 项目的问题是：要么全用 LLM（不可审计），要么全用规则（不够智能）。我们把它拆开——事实计算交给可审计的确定性工作流，报告表达交给 LLM。

另一个骄傲的设计是 **质量门禁**：不是跑完再校验，而是在关键节点阻断——基准错了不继续算差异、差异错了不生成报告。这对企业级产品来说是底线设计。

## Q11：如果只有 1 分钟介绍这个项目，你怎么说？

> InventoryDoc Agent 是一个本地私有部署的库存差异审计 Agent。上传 10 份盘点数据，它用 10 步确定性工作流自动完成噪音识别、基准选择、差异计算、日志关联和质量校验，8 秒算出精确到 1 元的差异数据，再用本地 LLM 生成管理层报告。数据不出设备，结论可追溯，质量门禁自动阻断关键错误。把 2-3 天的人工分析变成分钟级的自动审计。
