# 一次把“头像解读”做成 AI Agent 的十二天

> 2026 AMD AI DevMaster 黑客松 · Track 2 · XiangLens 项目复盘  
> 记录日期：2026 年 8 月 7 日

比赛结束，Radeon 云机器被回收，最后准备挂载的私有 108 Lens 也来不及再操作了。
多少有一点遗憾，但回头看，这十二天真正留下来的并不只是一份提交材料，而是一套关于
Agent、RAG、记忆、隐私、部署和取舍的具体经验。

这篇笔记写给未来的自己：记住哪些事情真的有效，哪些坑是在最后一晚才被迫看清，以及下次
怎样把同样的十二天用得更好。

## 一、项目是怎样变化的

最初想参赛时，我准备复用以前的 `avatar-reader`：上传头像，再根据《微信头像直断 108 招》
给出象征解读。它有现成的视觉模型和私有课程知识，演示效果也足够特别。

但 Track 2 需要的不只是一次模型问答，而是一套具备任务规划、工具调用、RAG、多轮交互和
记忆管理的 Agent。直接把旧项目换个界面并不能证明这些能力；把中国文化课程当作主知识库，
还会同时面对国际评委的理解门槛、文化断言风险和课程版权问题。

于是项目逐渐变成了 XiangLens：

- 不再“通过头像判断一个人”，而是帮助用户为 LinkedIn、GitHub、Discord 等场景选择头像；
- 不评价人格、职业能力、财富、健康或命运，只分析可见事实、隐私风险和用户自己设定的目标；
- 用公开 Lens Packs 提供平台、构图、隐私和文化语境证据；
- 把 108 招降级为需要主动勾选的私有 Tool，既保留创意，又不把私有课程公开出去；
- 把最终判断拆成可观察、可验证、可拒绝和可删除的步骤。

这个转向是整个项目最重要的产品决定。真正的创新不一定是让模型“看得更玄”，而是重新定义
模型应该回答什么、不应该回答什么，以及证据和控制权属于谁。

## 二、最后真正做出来了什么

XiangLens 最后形成了一条完整的 LangGraph 工作流：

```text
Policy gate
  → Context and approved-memory recall
  → Local EXIF / QR / image tools
  → Self-hosted visual observation
  → Optional Private Lens Tool
  → Milvus Lite retrieval
  → Candidate comparison
  → Memory consent
  → Structured report
```

它包含了几类以前只“知道概念”、这次才真正串起来的能力：

- FastAPI、LangGraph、Milvus Lite 和 SQLite 组成的应用后端；
- GitHub Pages 上的纯静态 Nuxt 前端，以及静态页面与动态 Agent API 的清晰边界；
- 永久密钥只留在服务端、浏览器只获得短期 Token 的访问流程；
- EXIF、QR、尺寸、裁剪和安全副本等确定性工具；
- 同一 Thread 的追问和不重复视觉识别的 cached-analysis 路径；
- 必须由用户点击 Approve 才能写入、并能跨 Review 召回和删除的长期记忆；
- 独立于隐私问题的 Rights & provenance finding，避免把“像 Snoopy”直接说成侵权；
- 34 条可引用知识卡、120 张有来源记录的真实图片，以及 9 条 RAG smoke queries；
- 面向 AMD Radeon PRO W7900 和 ROCm 的 llama.cpp 部署与可复现 benchmark。

最终 benchmark 记录到 Q6_K 视觉模型约 **83.42 tok/s** 的中位生成速度和约 **11.92 秒**的
单次模型 workload 延迟。它并不等于完整 Agent 的响应时间，却让我第一次清楚地区分了模型
吞吐、首个 reasoning token、首个 final-content token 和端到端应用延迟。

## 三、最值得记住的工程经验

### 1. Agent 的价值来自边界，而不是节点数量

LangGraph 的价值不是架构图里多几个方框，而是把责任分开：规则负责阻止敏感推断，代码负责
检查文件，模型负责描述可见内容，向量检索负责提供外部依据，用户负责批准记忆。

如果所有决定最终仍交给一个 prompt，外面再套多少 Agent 框架也只是一次模型调用。

### 2. 概率模型不能独占应用协议

这次最反复的错误都是结构化输出：模型漏掉 `decision_rule`、`rationale`，甚至漏掉整组五维
分数；reasoning 又可能先耗尽输出预算，导致最终没有 JSON。

最后的正确方向不是无限增大 token，而是把能确定的部分交还给应用：

- 推荐规则由代码固定；
- 缺失字段使用透明、保守的 fallback；
- 明确偏好由本地规则生成待审批 proposal，不再额外调用模型提取；
- Pydantic 负责验证，错误必须可解释；
- 模型是概率型 worker，应用才是 control plane。

这个原则比任何一次 prompt 调优都更值得带到下一个项目。

### 3. 小型 RAG 的核心不是“数量多”，而是“能证明”

一开始设想写 100–200 张复杂知识卡，每张还有二十多个字段，甚至想为每个 motif 调博物馆
API。十二天内这完全不可行，而且评委真正需要看到的是：查询能召回相关内容、报告能引用、
链接能打开、来源和许可证说得清楚。

最后把知识卡缩成简单结构，并用 smoke queries 验证 LinkedIn、GitHub、Discord、隐私和版权
等关键问题。34 条可靠卡片比 200 条来不及审查的内容更有价值。

### 4. 记忆首先是权限设计

“系统记得我喜欢卡通头像”听起来只是一个字段，但真正实现时必须回答：

- 谁说过这句话？
- 它是当前对话状态，还是跨 Review 偏好？
- 模型能不能自行写入？
- Token 刷新后用户身份是否仍然一致？
- 新 Review 如何证明真的召回了它？
- 用户怎样删除一条记忆或全部私有状态？

因此长期记忆最后落在 SQLite，而不是为了技术名词强行再放进向量库。Memory 的难点不是存储，
而是 consent、identity、scope、recall 和 deletion。

### 5. 部署问题就是产品问题

本地测试通过并不代表公开 Demo 可用。实际过程中遇到了：

- GitHub Pages 只能托管静态前端；
- CORS 错误响应同样需要带允许来源的 Header；
- 长 SSE 连接会被公网隧道的 HTTP/2 链路中断；
- 短期 Token 在长任务期间过期会让追问突然失去权限；
- 云机器、模型服务、FastAPI 和前端构建可能分别处于不同版本；
- 最后一刻才挂载的私有文件，会随着临时机器回收一起失去演示机会。

为 SSE 增加 durable background run 和 polling、为 Token 增加保持同一身份的 refresh，都是
“基础设施故障”倒逼出来的产品能力。下次必须更早在最终网络拓扑中测试，而不是把部署留到功能
完成之后。

### 6. 性能优化必须先定义测量对象

llama.cpp 在 W7900 上比当时的 vLLM 配置更适合这个 Q6_K、batch-size-1 的交互工作负载，
但这不能简单归因于“显卡不支持 FP8”。模型格式、量化、KV cache、Flash Attention、上下文、
预热方式和请求结构都会影响结果。

更重要的是：单次模型 benchmark 很快，不代表包含视觉、比较、报告和多轮 repair 的 Agent 也
会同样快。没有先拆分节点耗时，盲目调整 reasoning budget 只会在速度、JSON 完整性和稳定性
之间来回摆动。

## 四、这次做得不够好的地方

最明显的问题是范围一度过大。数据集、图片、Agent、前端、认证、部署、PPT、视频、私有工具和
benchmark 同时推进，导致真正决定演示稳定性的路径太晚才被冻结。

另外还有几件具体的遗憾：

- 太晚才围绕最终录屏 case 做端到端 rehearsal；
- 一度追求更低延迟，连续修改 reasoning 和输出预算，反而破坏了已经可用的 JSON 链路；
- 过度相信模型会严格遵守 schema，没有一开始就为字段缺失设计 application fallback；
- Private 108 Lens 的代码、文档和适配都完成了，却没有在机器回收前完成最后一次真实挂载；
- 展示材料前期偏架构，真实软件截图和连贯故事补得太晚；
- 临时 GPU 环境没有做可恢复的部署快照和“一条命令恢复”清单。

这些不是“差一点运气”，而是下一次可以明确改进的工程流程。

## 五、如果再给我十二天

我会按下面的顺序工作：

1. **第一天确定评分证据**：每个评分点必须对应一个可见界面、日志或文件；
2. **第二天完成最小竖切**：一张图、一个工具、一次 RAG、一个报告，从前端真正跑到 GPU；
3. **第三天固定最终部署拓扑**：直接使用比赛时的域名、认证和传输方式；
4. **第四至六天只做三个 golden cases**：隐私、多轮记忆、私有 Tool；
5. **第七天冻结模型协议**：为所有结构化输出准备确定性默认值和失败降级；
6. **第八天完成数据与来源**：宁可 30 条高质量卡片，也不追求虚假的规模；
7. **第九天做性能测量**：把模型时间、工具时间、RAG 时间和全流程时间分开；
8. **第十天录第一次完整视频**：用真实成片暴露叙事和 UI 问题；
9. **最后两天只修阻塞问题**：不再更换框架、不再重写推理策略、不再扩展功能。

我还会在云机器可用时立刻打包以下可恢复信息：模型启动命令、ROCm/llama.cpp 版本、`.env`
模板、Milvus 数据构建命令、私有 Lens 文件挂载说明和一份去除密钥的状态快照。

## 六、写给比赛结束后的自己

最后没能在回收前把 `avatarKnowledge.ts` 挂上去，确实让人难受。可那份文件并没有失去意义：
它已经从一个直接驱动头像断语的 system prompt，变成了一个有 opt-in、有安全过滤、有版权边界、
不会把源文件发给浏览器的私有 Tool。这种变化本身就是学习成果。

更重要的是，十二天前只是“头像解读”的旧项目，十二天后留下的是一个有完整源代码、真实前端、
数据来源、测试、部署文档、benchmark、PPT 和演示脚本的 Agent 系统。比赛机器会被回收，临时
URL 会失效，但这些设计判断、失败记录和工程习惯不会。

所以这次黑客松值得纪念的，不只是最终有没有来得及展示某个功能，而是第一次真正走完了从
想法、边界、数据、模型、Agent、部署，到提交叙事的整条路。

下一次，先做可证明的最小闭环，早点录第一版视频，给最后一晚留一点余地。

然后继续做下去。
