# Live Science Re_0

`Re_0` contains a three-phase production pipeline:

```text
User concept or instructional flow
        ↓
Phase 1: procedural instructional video and Bridge
        ↓
Phase 2: realistic keyframes
        ↓
Phase 3: realistic continuous video and final compositing
```

Use `Phase 1`, `Phase 2`, and `Phase 3` naming consistently. New base files, scripts, and documents must not use the old phase naming. All GPU image and video tasks also follow [`GPU_GENERATION_POLICY.md`](GPU_GENERATION_POLICY.md).

## Run the full pipeline with one command

Save the natural-language request as Markdown, then run:

```bash
python3 run_pipeline.py --request REQUEST.example.md --run-id seed-demo
```

You can also pass short text directly or read from standard input:

```bash
python3 run_pipeline.py --text "How does a seed germinate and grow into a seedling?"
python3 run_pipeline.py --request - --run-id seed-demo
```

By default it uses `release` quality and automatically selects the path based on the Phase 1 route. Common control parameters:

- `--quality smoke`: run through all necessary segments with conservative specs and produce the final video;
- `--target realistic`: fail explicitly if Phase 1 determines the content is not suitable for realization;
- `--stop-after phase1|phase2`: stop at a phase boundary;
- `--resume --run-id <id>`: continue a failed or intentionally stopped run with the original input and configuration;
- `--dry-run`: only check the input and show the planned path without launching Agents or the GPU.

Orchestration state lives in `runs/<run-id>/pipeline.json`, milestones in `events.jsonl`, and the final deliverable is `runs/<run-id>/final_video.mp4`. Other historical runs are not read by default.

## Phase 1: procedural instructional video

Phase 1 converts the user-provided concept, rough flow, or detailed textbook document into a deterministic procedural animation and defines the key states needed for later realization.

Authoritative spec: [`phase1/PHASE1_PROMPT.md`](phase1/PHASE1_PROMPT.md)

### Running

```bash
cd phase1
cp REQUEST.example.md REQUEST.md
# Edit REQUEST.md
./run_phase1.sh REQUEST.md <run-id>
```

`run-id` may be omitted; a timestamp is used automatically when omitted.

### Output

```text
phase1/runs/<run-id>/
├── REQUEST.md
├── brief.md
├── app/
├── subtitles.srt
├── video.mp4
├── poster.png
├── agent-final.txt
└── bridge/
    ├── manifest.json
    ├── contact_sheet.png
    ├── presentation/
    ├── clean/
    └── overlay/
```

Phase 1 decides:

- the instructional thread and timeline;
- how the procedural visuals evolve continuously;
- the key objects, states, and events;
- the key moments before and after events occur;
- which moments are suitable to move into Phase 2.

`bridge/manifest.json` must be generated by the export tool from the program's `LIVE_SCIENCE_BRIDGE` and must not be written by hand.

## Phase 2: realistic keyframes

Phase 2 selects a small number of necessary states from Phase 1's Bridge and converts them into realistic keyframes in the same world and from the same viewpoint.

Authoritative spec: [`phase2/PHASE2_PROMPT.md`](phase2/PHASE2_PROMPT.md)

Phase 2 currently uses Fast Mode, aiming to output 4–5 anchors usable for subsequent video generation within a limited time.

### How to invoke

Provide the Agent with the Phase 1 run and a new Phase 2 output directory, for example:

```text
Follow phase2/PHASE2_PROMPT.md to execute Phase 2.

Phase 1 run: phase1/runs/<run-id>
Phase 2 output: phase2/runs/<phase2-run-id>

Use the existing FLUX.2 / ComfyUI environment; do not modify Phase 1.
```

### Input

By default, Phase 2 only reads:

```text
phase1/runs/<run-id>/brief.md
phase1/runs/<run-id>/bridge/manifest.json
phase1/runs/<run-id>/bridge/clean/
```

Only when the meaning of a key state is unclear should it additionally check presentation, overlay, video, or `renderFrame(t)`.

### Output

```text
phase2/runs/<phase2-run-id>/
├── selected_anchors.json
├── world_reference.png
├── contact_sheet.png
├── report.md
└── anchors/
    └── <anchor-id>/
        ├── input_clean.png
        ├── prompt.txt
        └── realistic.png
```

Phase 2 decides:

- which 4–5 anchors to select from the Phase 1 candidates;
- which stable frame is used to establish the world reference;
- how to naturalize the procedural materials;
- which failed frames need a single retry;
- which known issues can be carried into the later video-generation trial runs.

## Phase 1 → Phase 2 handoff

The Bridge is the only formal handoff layer between the two phases.

| Phase 1 artifact | Phase 2 use |
|---|---|
| `brief.md` | Understand the full instructional thread |
| `manifest.route` | Decide whether to proceed to realization |
| `manifest.keyMoments` | Generation anchor candidates |
| `manifest.events` | Understand the before/after relationships of events |
| `description` / `preserve` | Write the prompt for the current state |
| `worldContinuity` | Maintain environment and object identity |
| `clean/<id>.png` | Structural input for the current anchor |
| `presentation/` / `overlay/` | Only used as auxiliary judgment when semantics are unclear |

Route rules:

- `programmatic`: normally stops at Phase 1;
- `realizable`: Phase 2 can select from all key moments;
- `hybrid`: Phase 2 only selects key moments with `realizable: true`.

Phase 2 may reduce the number of anchors, but it must not change Phase 1's instructional order, object identity, or event definitions. Phase 1 decides "what happens"; Phase 2 decides "what it looks like in the real world".

## Phase 3: continuous video and final compositing

Phase 3 uses Phase 1's event definitions to control the motion process and uses Phase 2's realistic keyframes to constrain the start and end states of adjacent segments.

Authoritative spec: [`phase3/PHASE3_PROMPT.md`](phase3/PHASE3_PROMPT.md)

Phase 3 generates by segments between adjacent anchors: it first validates a representative smoke, then generates the remaining segments serially. It is responsible for removing duplicate end frames, concatenating `base_video.mp4`, and remapping Phase 1's overlay and subtitles to produce `final_video.mp4`. The source artifacts of Phase 1 and Phase 2 remain read-only.

## Naming conventions

- Phase directories: `phase1/`, `phase2/`, `phase3/`
- Authoritative prompts: `PHASE1_PROMPT.md`, `PHASE2_PROMPT.md`, `PHASE3_PROMPT.md`
- Phase 1 run script: `run_phase1.sh`
- Run artifacts: `phase1/runs/<run-id>/`, `phase2/runs/<run-id>/`, `phase3/runs/<run-id>/`
- New documents and logs uniformly use `Phase 1`, `Phase 2`, `Phase 3`
- Historical runs are existing artifacts; they are not bulk-rewritten for terminology consistency
