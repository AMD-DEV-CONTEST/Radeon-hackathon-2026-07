# Local Dev Evidence Agent（LDEA）项目规格说明书

> **赛道**：AMD DevMaster · Track 2 私有 AI 智能体的开发与本地部署  
> **产品一句话**：本地开发证据智能体——**拒绝未验证的完成叙事**。  
> **文档状态**：可提交版（2026-08-06）。视频 / ROCm 实测 / 交付路径已回填。

---

## 1. 项目概述

### 1.1 要解决什么问题

AI 辅助开发普及后，「做完了」变得廉价：

- 对话里模型说「已修复」；
- 开发者收工时随口说「今天都搞定了」；
- 复盘文案很完整，但**没有绑定到真实代码变更与测试结果**。

LDEA 不做聊天总结，而做**可核验的开发成果账本**：只有通过证据门禁的事项，才能公开表述为「已完成 / 已修复」。

### 1.2 产品定位

| 维度 | 说明 |
|------|------|
| 形态 | 本地 CLI 智能体 + 确定性证据核 |
| 推理 | AMD Radeon + ROCm + vLLM（OpenAI-compatible），数据默认不出公网 |
| 记忆 | Session 级 L0 事件账本 → L1 outcome 状态机 |
| 非目标 | 不自动写业务代码；不替代 CI；**不允许 LLM 把 outcome 写成 verified** |

### 1.3 与赛题能力映射（总览）

| 赛题能力 | LDEA 落点 |
|----------|-----------|
| 推理 / 规划 | `ldea run` / `demo --live`：含糊目标下多轮 tool-call |
| 使用工具 | git_diff、claim、run_tests / ingest_test_output、scan_privacy、show_outcomes、end_session、render_report |
| 管理记忆 | `.ldea/sessions/<id>/`：events、store、report、meta、trace |
| 执行任务 | 离线 `close`/`demo` 规则管道；在线 Agent 闭环出报告 |
| 本地私有 | 仅 `127.0.0.1` / SSH 隧道 endpoint，无云厂商强制依赖 |
| Radeon / ROCm | 见第 6 章优化说明与实测 |

## 2. 应用场景

### 2.1 主场景：个人 / 小团队「收工核验」

**触发**：一天或一个任务结束，需要回答「到底做成了什么」。

**流程**：

1. 在业务仓库目录执行 `ldea close --claim "…" --test "…"`（或先由 Agent `run`）；
2. 系统写入 claim，采集 git 变更与测试结果，重建 L1；
3. 生成五栏报告；仅 `verified` 进入「成果」。

**价值**：把「感觉做完了」变成「账本状态 + 证据路径」，适合日记、周报前的自我审计，以及隐私要求高、不便上传代码到云端 Agent 的环境。

### 2.2 对照场景：多证据门禁矩阵（竞赛主叙事）

| 故事 | 输入 | 期望 |
|------|------|------|
| A | 「今天全部做完了」+ 无 git/测试 | `abandoned`，成果栏空 |
| B | 「可上线」+ 仅 git diff、无测试 | `evidenced`，不得写已完成 |
| C | 「已修复」+ 测试仍失败 | `evidenced`，不得 verified |
| D | 登录错误分类 + diff + pytest fail→pass | `verified`，可写「已修复」 |

- 全景一条命令：`ldea demo --suite`（离线、无需 GPU，**录像推荐**）  
- 短对照：`ldea demo`（仅 A vs verified）

### 2.3 Agent 场景：含糊目标核验

**触发**：说法冲突——「应该修好了」vs「今天收工了」，需要智能体**自己侦查**再下结论。

**流程**：本地 Qwen 多轮调用工具 → 以 L1 为准 → `render_report`。

**命令**：`ldea demo --live` 或 `ldea run "<含糊目标>"`。

### 2.4 非场景（边界）

- 不是学习向长文复盘（那是 AiRecap 产品线）；
- 不是远程 SaaS 代码托管分析；
- 竞赛版不做跨 session 自动合并、不做完整 IDE 插件。

## 4. 核心能力简介

### 4.1 证据状态机（硬门禁）

Outcome 典型状态（由规则引擎推进，**非模型自由生成**）：

| 状态 | 含义 | 能否写「已完成」 |
|------|------|------------------|
| `claimed` | 仅有声称 | 否 |
| `evidenced` | 有代码等证据、验证未闭合 | 否（部分进展） |
| `verified` | 证据 + 验证锚点满足规则 | **是** |
| `abandoned` | 会话结束仍无足够证据 | 否 |
| `contradicted` | 存在反证 | 否 |

报告顶部固定门禁文案：

> 仅 `status=verified` 可写「已完成/已修复」；LLM 不得自证 verified；空口 claim → abandoned。

### 4.2 工具清单

| 工具 | 作用 |
|------|------|
| `claim` | 记录声称；**单独调用不会 verified** |
| `git_diff` | 采集 worktree/staged/commit 变更 → file_change |
| `run_tests` / `ingest_test_output` | 测试执行或注入日志 → test_result |
| `scan_privacy` | 邮箱 / API Key / 连接串等风险 |
| `show_outcomes` | 读取 L1，供 Agent 决策 |
| `end_session` | 收尾：无证据 claim 趋于 abandoned |
| `render_report` | 确定性 Markdown/JSON 报告 |

### 4.3 双路径执行

| 路径 | 入口 | 是否要 GPU | 用途 |
|------|------|------------|------|
| 规则管道 | `close` / `demo` / `demo --verified` | 否 | 日常收工、可复现 CI、竞赛对照故事 |
| Agent 循环 | `run` / `demo --live` | 是 | 含糊目标、规划与工具选择、赛题「智能体」展示 |

设计要点：**可验证的结论不依赖模型自觉**；模型负责探路与编排，账本负责真伪。

### 4.4 报告产品面

1. 成果（仅 verified）  
2. 代码证据  
3. 验证证据  
4. 决策依据  
5. 公开风险  
6. 未闭合 / 不可公开为完成  

### 4.5 日常 Ledger CLI

```text
ldea close --claim "…" [--test …] [--no-git]
ldea ls [--status verified|abandoned|…]
ldea show [sessionId] [--outcomes] [--json]
```

## 5. 模型介绍与本地部署方案

### 5.1 模型选择

| 项 | 值 |
|----|-----|
| 主模型 | Qwen2.5-7B-Instruct（或同系列 served name） |
| 选型理由 | 中英文指令好；工具调用生态成熟；7B 在消费级 Radeon 显存/速度可平衡 |
| 接口 | OpenAI-compatible Chat Completions + tools |
| 备选 | 任意兼容 endpoint（改 `LDEA_LLM_*` 即可）；竞赛演示以 ROCm vLLM 为准 |

### 5.2 软件依赖

**开发机**

- Node.js ≥ 20  
- npm  
- git  
- （可选）pytest / 业务测试 runner  
- SSH 客户端（连 GPU 机时）

**GPU 机**

- AMD Radeon GPU + 已安装 ROCm  
- vLLM（ROCm 构建）  
- 模型权重（本地路径）

**同级源码依赖**

- `AiRecap Plus`：先 `npm install && npm run build`  
- LDEA：`npm install && npm run build`

### 5.3 环境变量

| 变量 | 默认 | 说明 |
|------|------|------|
| `LDEA_LLM_BASE_URL` | `http://127.0.0.1:8000/v1` | 本地 / 隧道 |
| `LDEA_LLM_MODEL` | `qwen2.5-7b-instruct` | 须与 vLLM served name 一致 |
| `LDEA_LLM_API_KEY` | `local` | 本地可任意非空 |
| `LDEA_ROOT` | `.ldea` | 账本根目录 |
| `LDEA_CWD` | 进程 cwd | 被检查的业务仓库 |
| `LDEA_MAX_TOOL_ROUNDS` | （代码默认） | Agent 最大轮数 |

参见仓库根目录 `.env.example`。

### 5.4 启动步骤（标准路径）

**A. GPU 机**

```bash
rocm-smi   # 确认 AMD Radeon / gfx1100 等

export HF_ENDPOINT=https://hf-mirror.com   # 如需要
# 竞赛实测机亦可用: python -m vllm.entrypoints.openai.api_server ...
vllm serve /models/Qwen2.5-7B-Instruct \
  --host 127.0.0.1 --port 8000 \
  --served-model-name qwen2.5-7b-instruct \
  --attention-backend TRITON_ATTN \
  --enable-auto-tool-choice \
  --tool-call-parser hermes \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.85 \
  --enforce-eager
```

**B. 开发机**

```bash
ssh -L 8000:127.0.0.1:8000 <gpu-host>

cd "<path>/AiRecap Plus" && npm install && npm run build
cd "<path>/Local Dev Evidence Agent" && npm install && npm run build

# Windows PowerShell 示例
$env:LDEA_LLM_BASE_URL="http://127.0.0.1:8000/v1"
$env:LDEA_LLM_MODEL="qwen2.5-7b-instruct"

node dist/cli.js doctor
node dist/cli.js demo          # 离线双故事
node dist/cli.js demo --live   # 真推理
```

## 6. 在 AMD Radeon GPU 上提升推理速度的优化说明

> 本章对应评分 **40 分：本地推理 + 推理速度优化**。  
> 下表为 2026-08-03 真机预演数据（gfx1100 云主机 + 开发机隧道）。

### 6.1 硬件与软件基线

| 项 | 值 |
|----|-----|
| GPU | AMD Radeon · DID 0x744b · **gfx1100**（云主机单卡；SKU D7070910） |
| 显存占用 | vLLM `--gpu-memory-utilization 0.85`；rocm-smi 见 VRAM%≈85%（服务常驻） |
| ROCm | **7.2.1**（镜像名 `rocm7.2.1_navi`） |
| vLLM | **0.16.0**（镜像）/ 进程 `python -m vllm.entrypoints.openai.api_server` |
| 运行时镜像 | `vllm-dev:rocm7.2.1_navi_ubuntu22.04_py3.10_pytorch_2.9_vllm_0.16.0` |
| 模型 | `/models/Qwen2.5-7B-Instruct` · served `qwen2.5-7b-instruct` · dtype auto |
| 服务参数 | host `127.0.0.1:8000` · max-model-len **4096** · TRITON_ATTN · auto-tool-choice · hermes · enforce-eager |
| 实测生成吞吐 | **~24 tok/s**（开发机经 SSH 隧道；completion=25 · wall≈1.04s · 2026-08-03） |
| 端到端 | `demo --live` **verified=1** · session `demo-live-20260803T020605Z` · **8 tools** · 约 **12s**（2026-08-03） |

### 6.2 优化项说明（问题 → 手段 → 结果）

| # | 手段 | 要解决的问题 | 机制简述 | 结果（填实测） |
|---|------|--------------|----------|----------------|
| 1 | 推理进程仅绑定 `127.0.0.1` | 私有部署与误暴露 | 不走公网 API，链路最短 | 隧道后 doctor/models 200；无公网 API Key |
| 2 | `--attention-backend TRITON_ATTN` | ROCm/navi 上注意力后端 | 镜像推荐后端，避免错误 attention 无法起服 | 服务稳定常驻（实例已跑 60h+） |
| 3 | `--max-model-len 4096`（演示机） | KV 显存与多轮 tool | 当前实例用 4096 换稳定；文档默认亦兼容 8192 | VRAM%≈85% 常驻；live 多轮可完成 |
| 4 | `--enable-auto-tool-choice` + hermes parser | Agent 必须真 tool-call | 结构化 tools，减少纯文本假调用 | live 6 步均走 tool_calls（2026-08-03） |
| 5 | `--enforce-eager` + gpu-mem 0.85 | ROCm 图捕获/显存尖峰 | eager 降编译风险；0.85 留 OS/碎片余量 | 常驻可服务，tok/s≈24 |
| 6 | Agent 每轮 1 工具 + 确定性 close | 无效长生成 | GPU 只用于规划路径 | 离线 demo 秒级；live ~半分钟 |
| 7 | SSH 本地转发而非公网暴露 8000 | 安全与评测拓扑 | 开发机 `ssh -L 8000:…` | 本机 curl models 成功 |

### 6.3 推荐对比实验（预演时做一组即可）

在**同一模型、同一提示**下记录：

1. 基线：可启动的最小参数集；  
2. 启用 `TRITON_ATTN` + `max-model-len 8192` + tool parser；  
3. （可选）再降 `max-model-len` 或量化。

输出表：

| 配置 | 能否稳定 tool-call | tok/s | live 端到端 |
|------|-------------------|-------|-------------|
| 当前云主机演示配置（TRITON_ATTN + hermes + max-len 4096 + eager） | 是（doctor OK，多轮 tools） | ~24（隧道测） | ~20–40s |
| 文档推荐（max-len 8192，其它同左） | 视显存；本机未在 5h 余额内重测 | 【可选复测】 | 【可选】 |

### 6.4 工程侧「体感加速」（非内核算子，但属于端到端优化）

- **能规则化的不走模型**：收工账本 `close` 不消耗 GPU。  
- **测试可 ingest**：`ingest_test_output` 避免在演示环境重复跑重测试。  
- **报告确定性渲染**：不二次让模型「写总结」冒充账本。  

这些保证：评测时功能完整，同时把 GPU 预算花在「规划与工具选择」上。

### 6.5 已知限制

- 7B 在复杂含糊目标下可能偶发不按 tool schema 输出（代码侧有 Hermes 文本兜底解析）。  
- 吞吐受 PCIe/隧道/单并发 share 影响；演示建议单用户。  
- 云主机 **credits 告警约 5 小时**；证据与录像需在销毁前落盘到开发机。
- 实例 SSH：`root@36.150.116.206 -p 31065`（会变，以控制台为准）。
- 7B 若颠倒 claim/证据顺序，outcome 可能停在 claimed（已在 live goal 中固定绑定顺序）。
